# 当前产品决定与需求对齐记录

状态：当前有效
更新日期：2026-08-19

本文件只记录用户已经明确确认、会约束后续设计和验收的产品决定。2026-08-18 以前围绕 Evidence、Knowledge Factory、知识包和 Runtime 的 18 项访谈问题树已被“两阶段：数据抓取、数据清洗”的产品收口取代，原文保留在 Git 历史中，不得继续驱动当前实现。

## D001 两阶段产品范围

状态：已确认（2026-08-18）

项目只包含两个阶段：先抓取并保存真实原始数据，再讨论数据清洗。当前只实施阶段 1。Evidence、知识加工、知识包和 Runtime 不在当前生产组合根。

## D002 当前只服务标准商品

状态：已确认（2026-08-19）

采访 Skill 面向能够通过品牌、型号、规格、分类、国家/行业标准或其他稳定身份进行枚举和比较的标准商品，例如冰箱、电视机。手工制品、孤品、定制品等非标准商品不属于当前范围。

系统必须主动调查是否存在国标、监管备案、能效/认证和稳定市场分类；不能要求负责人预先提供完整品牌、型号、参数或来源清单。

## D003 专业引导式采访

状态：已确认（2026-08-19）

采访 Skill 参考 `grill-with-docs` 的推进方式，但服务于专业数据抓取。用户不是专业抓取工程师，Agent 必须用调查和专业判断引导用户理解过程，每次只推进一个真实取舍，并提供有依据的推荐答案和主要代价。

推荐项应当是当前证据下的专业默认答案。不能为了满足“2–3 个互斥选项”的输出形式强行制造没有业务意义的问题，也不能把可调查事实伪装成负责人决定。

采访必须理解用户通过 Composer 发送的完整自然语言，而不是切换到只能识别选项的表单模式。`1`、`按推荐`、自定义回答、纠正、附加事实、否定问题前提和追问都必须接回同一段对话；一句话同时回答问题并补充范围时，两部分都要保留。

## D004 多平台来源与京东边界

状态：已确认（2026-08-19）

标准商品抓取需要多来源数据。对冰箱等家电，京东是必须覆盖的核心平台来源，因为其分类、筛选、品牌/店铺和商品资料整合较完整；淘宝是京东之后需要增加的多平台来源。

因此采访不默认询问“是否纳入京东”。平台范围由系统根据商品和市场事实主动规划、解释并写入草稿；负责人仍可明确提出排除要求。平台必须覆盖不等于已获准访问，真实抓取必须分别通过许可、登录、验证码、风控、频控、熔断、恢复和 Crawl Plan 确认门。

## D005 事实、建议与决定分离

状态：已确认（2026-08-18，2026-08-19 澄清）

- 标准、监管、品牌、型号、参数、部件、来源和平台结构等可调查内容由系统调查；
- Agent 的问题和推荐只是 proposal；
- Workbench 先保存负责人通过 Composer 发送的原文；Agent 结合当前问题、历史消息、调查结果和草稿理解整条输入，只在语义明确时提交规范化的决定解释，Workbench 校验后保存 confirmed Interview Decision；
- 用户补充或纠正的相关事实、Agent 查回的事实和草稿版本共同组成持续演进的采访工作资料，是最终草稿的依据；追问或歧义输入只继续对话，不能被误记为选择；
- 消息文案、模型建议和搜索结果不能直接成为任务事实；
- 没有负责人未决项后才能形成 Capture Task Draft。

## D006 抓取任务与版本

状态：已确认（2026-08-18）

对话产出版本化 Capture Task Draft。用户整体确认后创建 Capture Task，但不自动抓取。确认后仍可回到同一对话修改范围；再次确认保持 Capture Task ID 不变并推进 revision，旧确认版本不可变。

## D007 本地执行与停止门

状态：已确认（持续有效）

Workbench、Codex 采访、来源访问和原始数据保存都在本机执行。Cookie、Profile、密码、认证 Header 和验证码材料不得进入 Git、日志、Codex 输入或导出。登录、验证码、风控、拒绝访问、许可不明或频控熔断时停止，不自动绕过。

1A 的专业问答质量仍需真实 PC 人工验收。用户于 2026-08-19 在理解规划流程后明确授权实现 1B 的最小规划纵切片，因此旧的“1A 未验收不得实现 Crawl Plan”门对本次实现失效；它仍与 Crawl Plan 确认、Provider、许可和频控门共同阻止任何真实来源抓取。测试、fixture、POC 和历史样本不能代替真实页面与真实来源验收。

## D008 Crawl Planning 与正式抓取分离

状态：已确认（2026-08-19）

Capture Task 确认后由负责人显式启动 Crawl Planning。Codex 在 Workbench 可见时间线中搜索并核实具体网站，形成可修订、可确认的版本化 Crawl Plan；计划直接决定来源、每个来源捕获的内容和数量。Planning Run 不做批量抓取，Confirmed Crawl Plan 也不自动创建 Source Run。

本轮采用前台可见、连接关闭即中止的最小运行语义；不为单次短规划引入后台队列或持久工作流。正式抓取运行中不允许 Codex 无边界边搜边抓；发现新来源时必须回到新的 Planning Run 和计划确认门。
