# Agent 知识生产平台阶段开发路线图

状态：执行基线
版本：V0.2
更新日期：2026-08-14

## 1. 使用规则

本文件只定义阶段顺序、产物和停止门。当前完成度只记录在 `PROGRESS.md`，不得在本文件维护第二套进度勾选。

任何阶段都必须遵守：先调研成熟开源方案，再完成最小原型，再冻结决策，再进入正式实现。

## 2. 总体顺序

```text
阶段 0 工程基线与验收范围
  → 阶段 1 四项可行性验证
  → 阶段 2 项目与流水线骨架
  → 阶段 3 官方来源－冰箱数据搜集板块
  → 阶段 4 商品知识加工厂 MVP
  → 阶段 5 知识包与 Runtime
  → 阶段 6 联调、评测与交付
```

阶段 1 的四个验证全部通过前，不得大规模重构旧业务代码、建设完整 UI 或冻结通用插件框架。

## 3. 阶段 0：工程基线与验收范围

### 目标

建立可比较的工程基线，把产品目标转换为已确认范围，并准备跨上下文持续开发所需的文档事实源。

### 工作内容

- 建立 `AGENTS.md`、领域词汇、架构基线、调研登记和进度协议；
- 核对 Git、Node/npm、依赖、环境变量和数据目录；
- 安装锁定依赖，运行现有 test/typecheck/build，记录历史失败与当前失败的区别；
- 形成产品对象到旧代码对象的保留、重构、淘汰、新增映射；
- 根据数据化品类知识定义、主流型号总体、组合覆盖与统计目标生成版本化验收范围，不预设无依据的数量或百分比；
- 冻结规格、功能、机制、适用条件、取舍、决策维度和能力问题的评测规则；
- 准备第二商品品类迁移样本，验证新增品类只提交定义数据与评测数据；
- 验证 Codex CLI 本地执行边界，并继续澄清可发布证据范围。

### 阶段产物

- 当前工程验证基线；
- 已确认研究范围和验收集；
- 旧代码处置矩阵；
- 第一批技术调研条目和验证计划；
- 可由新上下文直接继续的 `PROGRESS.md`。

### 通过门

- 当前依赖、测试、类型检查和构建状态有可复现记录；
- 产品范围、Codex CLI 执行边界和证据发布边界已获得人工确认；
- 下一阶段每项原型都有输入、输出、成功条件和失败停止条件。

## 4. 阶段 1：四项可行性验证

这一阶段只做独立小规模纵向原型，不建设完整平台。

### 验证 A：官方来源、平台研究采集与原始资料

调研并验证品牌官网/说明书、监管数据和京东网页的候选发现、详情、多规格、图片资料、时点状态、异常状态与敏感数据隔离。京东采用隔离的 Crawlee＋Patchright POC；淘宝登记为京东闭环后的下一来源，不并行展开。

阶段产物是代表性页面的不可变原始资料、受限快照的可加工白名单投影、状态分类、证据定位和失败记录，不是正式 Provider 插件系统。

通过门：样本规模由 R-010 的来源/页面因素和组合覆盖方法产生；代表性官方资料完成原始保存，失败和人工接管状态可见，不能出现空内容标记成功。

### 验证 B：混乱资料加工

从验证 A 的真实资料中完成候选属性发现、结构化抽取、单位和表达标准化、型号/规格识别、冲突发现、低置信度审核和证据返回。

通过门：核心知识层质量达到 R-010/R-011 随原型冻结的统计门槛，并能区分页面、规则、Codex 和审核错误来源。

### 验证 C：知识包与离线查询

把验证 B 的结果制作成候选知识包，在无模型、无网络环境下完成精确查询、条件筛选、全文搜索、关联和证据查看。

通过门：知识包可复制到另一台机器加载；Runtime 不依赖 Workbench 数据库、向量数据库或查询 embedding。

### 验证 D：第二商品品类迁移门

使用电视或微波炉小样本复用同一商品知识模型、同来源 Provider contract、加工流程、包结构和 Runtime。

通过门：生产 Schema、数据库结构、通用模块 interface、Runtime API 和同来源 Provider 实现零修改；只增加版本化品类知识定义、来源范围和评测数据。

### 阶段 1 原型 contract

| 验证 | 冻结输入 | 最小代表样本 | 必须输出 | 通过门 | 立即停止条件 |
| --- | --- | --- | --- | --- | --- |
| 1A 官方来源与原始资料 | `MarketUniverseVersion`、品类知识定义、来源策略、已核验来源清单、组合覆盖场景 | 品牌官网/说明书、监管数据、京东正常/登录/风险/下架、多规格和图片资料 | 来源身份与策略、来源对象、不可变快照、可加工白名单投影、资源清单、哈希、证据定位、明确失败分类 | 所有尝试均为完整成功或可解释失败；没有骨架屏成功；认证与个性化信息不进入加工/发布 | 需要自研反检测或验证码；凭据/个人信息泄漏；原始资料无法不可变保存；页面长期无稳定字段 |
| 1B 混乱资料加工 | 1A 快照、共享属性字典、品类知识定义、Codex 输出 Schema、R-011 质量 contract | 来源直出事实、确定性转换、图片/文本、型号歧义、冲突、缺证据和 `unknown` | 候选知识、知识状态、处理版本、证据引用、冲突、例外审核事项、可重放评测记录 | 正式候选 100% 绑定证据；模型不能直达发布；同输入可重放；错误能归因到页面/规则/Codex/审核 | 只能靠提示词保存专业知识；需要品类专用生产代码；必须自研 CLI/模型协议；无证据内容被补成事实 |
| 1C 知识包与离线查询 | 1B 已审核样本、版本化查询/能力问题集、R-011 硬门、SQLite FTS5 与 DuckDB/Orama 候选 | 精确型号/别名、数值筛选、中文全文、关系/证据、冲突/未知、新旧版本切换 | 可校验候选包、只读 Runtime adapter、查询结果、包大小/构建时间/查询资源报告、版本回滚记录 | 跨目录或机器复制后无网络/模型/embedding 可查询；能力顺序完整；新包校验后原子切换；旧包可回滚 | 启动必须联网下载扩展；包不能只读；证据联查丢失；需要自写全文/向量/质量基础设施 |
| 1D 第二品类迁移 | 电视或微波炉官方小样本、与 1A～1C 相同的生产 contract 和实现 | 身份、规格、功能/机制、适用条件/取舍、比较维度和官方来源各至少一例 | 新品类定义数据、来源范围、评测数据、零代码迁移 diff、能力缺口报告 | 生产 Schema、数据库结构、通用 interface、Runtime API、通用流程和同来源 Provider 实现零修改 | 出现品类类/表列/Runtime 方法/流程分支；为通过测试把第二品类语义塞入共享核心 |

原型可以使用隔离脚本和临时数据，但不能把自写脚本直接升级为生产基础设施。任何候选组件只有在对应原型真实通过、许可证与退出成本复核后才能进入依赖决策。

### 阶段停止门

任一验证失败，暂停平台化开发，先调整范围或候选技术；不得以“后面再解决”跳过。

## 5. 阶段 2：项目与流水线骨架

### 目标

把已经通过的原型收敛为可管理、可恢复、可观察的连续任务。

### 工作内容

- Product Knowledge Project、Category Knowledge Definition Version 和 Confirmed Scope；
- Collection Board Version；
- Pipeline Run、Stage Execution、Task Attempt 和 Intervention；
- 暂停、恢复、取消、阶段重试和人工事项处理；
- 输入版本冻结、幂等和恢复验证；
- Workbench 基础页面与 typed contract。

### 调研门

流水线编排器、迁移方案和事件/状态持久化必须完成对应 `RESEARCH.md` 条目并通过崩溃恢复与人工信号原型。

### 通过门

人为终止一次运行后能够恢复；已经提交的原始资料不会被覆盖或破坏性重复执行。

## 6. 阶段 3：官方来源－冰箱数据搜集板块

### 目标

将阶段 1A 原型收敛为满足 Provider 产品规范的品牌官网/说明书、监管数据和已获权限平台 API 能力与冰箱板块。

### 工作内容

- Provider 来源授权、能力声明和 contract 测试；
- 主流品牌/型号总体、官方来源和品类知识定义驱动的候选发现；
- API 授权或获准网页会话检查，失效时暂停；
- 页面状态、多规格、促销、缺货/下架和异常处理；
- 原始资料不可变保存、覆盖统计、增量采集和维护状态；
- Provider 版本和旧资料重放。

### 通过门

计划内当时可访问的官方资料达到 R-010/R-011 冻结的保存门槛；所有失败项可解释、可重试或明确等待人工处理。

## 7. 阶段 4：商品知识加工厂 MVP

### 目标

将真实、混乱的获准官方资料稳定加工为可审核、可追溯的知识结论。

### 工作内容

- 稳定商品知识模型、共享属性字典、品类知识定义和处理 recipe 版本；
- 确定性解析、规则处理和必要的模型 adapter；
- 单位、枚举、别名、型号、规格和 Offer 识别；
- 对象合并、冲突检测、低置信度和异常审核；
- 原始值、标准值、推断状态、证据和处理版本；
- 功能、机制、适用条件、取舍、需求映射和比较维度的专业知识结论；
- 使用旧原始资料重放加工并生成新版本。

### 调研门

模型接入、结构化输出、OCR/图片理解和对象合并候选必须完成调研与真实样本验证，不得先自研通用框架。

### 通过门

- 已发布候选知识来源可追溯率 100%；
- 核心知识层人工抽检达到 R-010/R-011 冻结的统计质量门槛；
- 模型结果未经校验不能进入确认知识；
- 冲突和无法判断项不会被静默填充。

## 8. 阶段 5：知识包与 Runtime

### 目标

把审核后的知识变成独立于生产环境的 Agent 交付物。

### 工作内容

- 包身份、兼容、领域描述、知识、证据、查询能力、质量和资源分层；
- 只读构建、校验和、发布、激活、切换和回滚；
- 精确查询、结构化筛选、全文搜索、关系导航和证据查看；
- 本地直接加载、本地服务和远程轻量服务共用查询语义；
- Node/TypeScript Agent 接入演示。

### 调研门

包内结构化存储、全文检索、压缩、校验和和 Node Runtime 必须通过跨机器、离线和资源上限原型。

### 通过门

知识包复制到另一台机器后仍可加载和查询；旧版本可安全回滚；通用 Runtime 中不存在商品专用固定 interface。

## 9. 阶段 6：联调、评测与交付

### 工作内容

- 使用完整验收集从头运行流水线；
- 模拟中断、授权过期、页面/API 异常和模型失败；
- 运行购物引导 Agent 问题集；
- 检查覆盖率、准确率、证据、性能、包完整性和资源使用；
- 验证另一台机器的安装、加载、切换和回滚；
- 整理操作手册、已知缺口和后续维护事项。

### 最终通过门

- PRD 第 10 节全部通过；
- 能力问题和下游任务集达到 R-011 冻结的通过门；
- 不存在按版本化发布策略定义的未解决阻断项；
- 用户可独立完成授权恢复、任务恢复、冲突审核、建包和版本切换；
- 已知缺口和未覆盖范围明确记录。
