# Agent 知识生产平台总体技术方案

版本：V1.1
文档性质：产品约束下的总体方案，不是详细设计

## 1. 本文档解决什么问题

本文档把 PRD 转换为系统边界和模块关系，确保工程团队不会把产品做成：

- 一个只会抓京东的脚本；
- 一个写死冰箱或其他品类字段的数据库；
- 一个必须依赖向量库和查询模型的重型 RAG 服务；
- 一个把登录态和原始资料上传服务器的高风险平台。

本文档不规定函数、表结构、目录结构、消息协议和类设计。这些由工程师在可行性验证后形成详细设计和 ADR。

## 2. 已锁定的总体约束

| 约束 | 对总体方案的影响 |
| --- | --- |
| 冰箱是首个完整 MVP | 首先验证完整纵向链路，同时用第二品类小样本验证迁移成本 |
| 多个搜集板块汇入一个加工厂 | 来源变化与知识加工必须解耦 |
| 商品知识资产可供多个消费者复用 | Workbench 可以拥有稳定商品语义，但不得出现冰箱专用 Schema；Runtime 不绑定具体 Agent |
| 品类差异必须数据化 | 新品类只增加版本化定义、来源范围和评测数据，不增加品类类、表列或 Runtime API |
| 只采官方权威来源 | 普通第三方和小型商家不进入首轮事实层；覆盖按主流型号而非卖家数计算 |
| 采集和加工只在本地运行 | 本地是唯一生产环境，服务器只承担轻量部分 |
| 原始数据可能非常混乱 | 加工厂必须包含规则、模型、校验和人工审核 |
| 查询应当轻量 | 重处理放在建包阶段，Runtime 默认不调用模型 |
| 不自研底层数据库和搜索引擎 | 优先组合成熟开源组件，项目只开发业务编排和适配层 |
| 用户技术栈为 Node/TypeScript | 首版优先选择有稳定 Node/TS 接入的组件 |

## 3. 总体结构

```text
本地 Workbench
  ├─ 项目与任务流水线
  ├─ 数据搜集板块
  │    └─ Source Provider
  ├─ 原始资料区
  ├─ 商品知识加工厂
  │    ├─ 稳定商品知识模型与共享属性字典
  │    ├─ 版本化品类知识定义
  │    ├─ 抽取与标准化
  │    ├─ 对象合并与冲突处理
  │    ├─ 人工审核
  │    └─ 构建与评测
  └─ 本地知识包与 Runtime

可选线上部分（MVP 后）
  ├─ 项目和板块维护信息
  ├─ 知识包管理
  ├─ 轻量 Runtime
  └─ 权限、审计与备份
```

数据只沿一个方向进入正式知识：

```text
来源 → 原始资料 → 候选知识 → 审核知识 → 知识包 → Runtime
```

任何阶段都不能反向修改原始证据。新处理结果通过新版本表达。

## 4. 为什么必须分成三个核心层

### 4.1 数据搜集层

解决“到哪里找、是否有权访问、怎样访问、怎样保存原始资料”。它必须理解来源授权、API/页面能力和来源状态，但不负责决定什么是正确的商品知识。同一个来源 Provider 必须服务冰箱和第二品类小样本，普通第三方卖家由来源策略排除而不是另写流程。

### 4.2 商品知识加工厂

解决“从混乱资料中得到专业商品知识”。它解释稳定商品知识模型、共享属性字典和数据化品类定义，但不应包含京东页面选择器、登录逻辑、冰箱类或某个 Agent 的对话状态。

### 4.3 知识包与 Runtime

解决“怎样把加工结果交付给 Agent”。它不携带爬虫、模型任务或加工 Worker，只提供稳定、轻量的知识使用能力。

这一分层使同一个获准 Provider 可以服务不同商品品类，也使同一份品类知识资产可以交付给多个不同 Agent/Skill。

### 4.4 商品模型与品类定义

生产系统只有一套商品、型号/变体、销售要约、属性结论、专业知识结论和证据语义。品类知识定义是数据，选择共享属性、单位、别名、来源策略、决策维度和能力问题。Schema.org 的扩展属性、Akeneo 的共享属性/Family 组合和 Pimcore Classification Store 的动态品类属性共同证明该方向有成熟行业先例；本项目不因此直接引入整套 PIM。

## 5. 任务流水线

产品层保留八个可见阶段：

1. 创建项目；
2. 规划并确认研究范围；
3. 配置数据搜集板块；
4. 搜集并保存原始资料；
5. 抽取、标准化和对象合并；
6. 人工审核；
7. 构建并评测知识包；
8. 发布和使用。

总体技术方案只要求每一阶段具备输入、结果、状态、错误和恢复点。内部是否继续拆成子任务、队列或状态机，由工程设计决定。

## 6. 开源组件基线

以下是 MVP 候选，不是 PRD 强制指定；工程师必须先做可行性验证，再冻结版本和使用方式。

### 6.1 采集候选

- Crawlee 作为网页采集任务、请求队列、成熟滚动器和运行统计候选。其 JavaScript 版本提供 PlaywrightCrawler、动态请求队列、Session Pool 和统计能力，符合“慢速、可恢复任务”的方向。[Crawlee 官方文档](https://crawlee.dev/js/api/3.13/playwright-crawler/class/PlaywrightCrawler)
- Patchright 作为京东教育研究采集的反检测浏览器候选。它是 Apache-2.0 的 Playwright 替代实现，官方推荐本机 Chrome、持久 Profile、有头模式和原生指纹；项目关闭 Crawlee 默认指纹注入，不再自研或叠加指纹实现：https://github.com/Kaliiiiiiiiii-Vinyzu/patchright-nodejs
- 原版 Playwright 只保留离线差分与普通来源兼容验证。认证状态可能包含敏感 Cookie 和 Header，因此登录资料必须留在本地并排除出版本库、Codex 输入和上传链路。[Playwright 认证文档](https://playwright.dev/docs/auth)
- 对无需浏览器渲染的稳定页面，可由工程师评估更轻的 HTTP/HTML 解析路径，但不能牺牲证据和页面状态识别。

这些组件只能证明技术能力可用，不能保证每个页面长期稳定。MVP 第一阶段按 ADR-0004 验证京东官方店铺白名单、登录接管、字段覆盖、懒加载、异常分类、敏感数据隔离和证据保真；淘宝在京东闭环后复用相同 Provider contract 另做调研。

### 6.2 知识包存储候选

- DuckDB 适合作为结构化知识包候选，因为它是进程内数据库，支持文件持久化并提供 Node.js 客户端；工程实现应评估当前 Node Neo 客户端，而不是已弃用的旧 Node 包。[DuckDB Node Neo 文档](https://duckdb.org/docs/lts/clients/node_neo/overview)
- Orama 适合作为 TypeScript 侧全文检索候选。它支持全文、过滤和可选向量能力；本项目基线只使用全文能力，不因此引入 embedding。[Orama 官方文档](https://docs.orama.com/docs/orama-js)

产品锁定的是“可携带的结构化数据＋全文检索＋证据”，不是锁定某个文件名、表结构或索引格式。工程验证失败时可以替换组件，但不能破坏知识包产品能力。

### 6.3 AutoPKG 的定位

AutoPKG 官方仓库明确说明其公开代码是从内部实验代码抽取的最小可复现版本；当前实现依赖 LLM、FAISS、NetworkX、ODPS 和多 GPU 处理。[AutoPKG 官方仓库](https://github.com/Product-Understanding-Lazada-Alibaba/AutoPKG)

因此：

- 在商品知识加工中参考其属性发现、关系抽取、动态更新和评测方法；
- 不把该仓库当作本平台可直接运行的基础框架；
- 不把它的电商图谱结构扩散为通用知识包结构；
- 不继承其 GPU、ODPS、FAISS 或查询 embedding 依赖。

## 7. Codex 在系统中的位置

Codex CLI 只在本地建包流程中用于难以稳定编码的任务，例如：

- 从品类、市场和用途说明生成研究范围草案；
- 发现候选属性、别名和表达映射；
- 解析非结构化文本或图片；
- 辅助对象合并、冲突解释和异常修复。

确定性解析优先；Codex 输出必须经过结构校验、保留来源并允许人工否决。运行时查询默认不调用 Codex。

MVP 的知识加工执行器固定为用户本机已登录的 Codex 能力。Workbench 使用 OpenAI 官方 `@openai/codex-sdk` 驱动其封装的 Codex CLI，通过 SDK structured events 跟踪过程，并使用 JSON Schema 约束最终结构化结果；应用不直接保存 OpenAI API Key，也不先建设 OpenAI-compatible、Qwen、豆包或本地模型 Provider，更不自研 CLI 进程与 JSONL 协议层。

Codex SDK/CLI 是本地执行入口，不等于模型在本机离线推理。它复用用户已有的 ChatGPT/Codex 登录和账户配置；项目只负责产品任务 contract、工作目录、权限、输入、结构化输出、超时、取消和审计，CLI 启动、事件解析和线程机制由官方 SDK 负责。Cookie、认证 Header 与浏览器 Profile 永远不作为 Codex 任务输入。以后若要增加直接模型 API 或本地开源模型，必须重新进入产品确认和开源调研门。

## 8. 本地与线上部署边界

### 8.1 永久留在本地

- 浏览器及认证状态；
- Provider 执行；
- 原始资料；
- Codex 任务编排、输入准备、输出校验、结果落库与人工审核；
- 知识包构建和评测。

### 8.2 后续可以部署

- 非敏感的项目、任务和板块维护信息；
- 知识包上传、下载、激活和回滚；
- 轻量 Runtime；
- 权限、审计和备份。

本地工作站离线后，线上只能继续查询已有知识包，不能生成新知识。

## 9. 总体质量要求

- 可恢复：进程退出、人工验证或单任务失败不导致整条流水线报废。
- 可追溯：正式知识可以回到来源、采集时间和处理版本。
- 可复现：同一原始资料和同一处理配置可以重新生成结果。
- 可替换：Provider、模型服务、存储和索引组件可以演进。
- 可携带：知识包不依赖生产工作目录和本地数据库服务。
- 可审计：规则、模型推断和人工决定可以区分。
- 轻量运行：未来 2 核 4G 服务器只加载已构建知识包并处理查询。

## 10. 决策层级

| 已锁定 | 候选方案，需验证 | 由工程详细设计决定 |
| --- | --- | --- |
| 本地生产、轻量运行 | Crawlee＋Playwright | Provider 函数接口 |
| 多板块汇入加工厂 | DuckDB Node Neo | 数据表与字段 |
| 通用知识包 | Orama 全文检索 | 文件目录与序列化格式 |
| 无强制向量/embedding | 规则＋可替换模型 | 队列、并发和重试算法 |
| 原始资料不可丢失 | AutoPKG 思想参考 | API、类和模块划分 |

## 11. 工程设计开始前的验证门

工程团队必须先提交四项小规模验证结果：

1. 品牌官网/说明书、监管数据和京东网页采集的发现、详情、多规格、图片资料、异常状态与敏感数据隔离验证；
2. 使用少量原始资料完成规则＋模型＋人工审核的加工闭环；
3. 生成候选知识包，并在无模型、无网络条件下完成结构化查询、全文搜索和证据返回。
4. 用第二商品品类小样本证明只新增品类定义、来源范围和评测数据，不修改生产 Schema、数据库结构、通用 interface、Runtime API 或同来源 Provider 实现。

四项验证通过后，才能冻结详细接口、数据格式和正式技术栈。
