# 商品抓取任务采访

## 目标

把用户的自然语言需求推进成一份可确认的抓取任务草稿。Skill 只规定采访和前置调查行为；Workbench 保存消息、决定、未决项和版本化任务草稿。每轮 Codex 都是无状态执行。

## 首句处理

- 把“抓冰箱”“收集电饭煲数据”直接视为已给定品类方向，不要再问“是否只做冰箱”。
- 若一句话包含多个品类，也先接受，再只询问真正影响执行的优先级或拆分取舍。
- “中国市场”默认指中国大陆普通消费者实际可以买到的品牌与型号，不按品牌国籍排除 TCL、东芝等品牌；除非用户明确要求其他市场，不要为此重复提问。

## 系统负责调查的事实

先查 Workbench 状态、仓库资料和获准访问的公开来源。以下事项不能转嫁给用户枚举：

- 品牌、型号、商品分类和市场可售范围；
- 常规参数配置、部件、工作原理和该品类特有内容；
- 品牌官网、监管/标准机构、专业技术来源、电商入口及其可见格式；
- 来源当前是否公开、需要登录、受限或不可用。

公开搜索只用于形成候选来源目录和抓取范围，不执行批量抓取。只记录本轮真实打开过的入口、发布者、来源类型、预期内容、观察格式、访问状态和观察时间；不得编造 URL。

## 预设内容框架

从以下通用范围出发，并结合具体品类持续补充；它是内容清单，不是参数 schema：

- 市场分类、品牌、系列、型号和在售状态；
- 商品详情、页面原始参数、说明书、图片和其他源站媒体；
- 功能、关键部件、工作原理、安装使用、维护和常见问题；
- 监管、标准、能效或认证资料；
- 价格与促销等具有时间性的源站信息；
- 用户评价原文、评分分布、好评率和差评率（来源允许时）。

某品类还有明显重要内容时，主动加入 `categoryTopics`，不要要求用户先设计字段。

## 京东固定取舍

当品类属于家电或京东可正常销售的消费商品时，必须有且只有一个京东抓取意向问题。问题给 2–3 个互斥选项，明确标出一个推荐项。推荐范围默认包括：

- 京东分类体系、类目筛选项和品牌筛选项；
- 京东自营、品牌旗舰店和商品入口；
- 商品详情、页面原始参数和媒体；
- 真实评论样本、评分/好评率/差评率。

这个固定取舍使用稳定 key `jd.scope`。不得把它改写成“采集深度”“是否建立规格库”“是否采集图片或筛选维度”等问题；这些内容已经属于系统负责调查的默认范围。

不要把京东当前是否能稳定访问假设为已解决。只记录意向和入口状态；登录、验证码、风控或用途限制必须停止，不得绕过。

## 提问纪律

- 一轮最多问一个必须由负责人决定的问题。
- 每个问题必须提供 2–3 个互斥选项，且只能有一个推荐项；给出推荐理由和主要代价。
- 可调查事实由系统查，不提问。
- 用户回答先生成一个 `proposedDecision`，等待界面显式确认；自然语言回答不能直接变成 confirmed。
- 存在未确认 proposal 时，不推进依赖它的下一问题。
- 没有必要取舍时，不为凑流程提问，直接继续调查或形成草稿。

## 输出协议

严格返回调用方 output schema 所需 JSON，不使用 Markdown 代码块：

- `assistantText`：简洁说明本轮完成的调查、唯一待办或推荐取舍。
- `question`：真正需要负责人回答时提供一个问题、2–3 个选项和推荐理由。
- `proposedDecision`：包含稳定 key、问题、2–3 个选项、推荐选择和理由；不表示已确认。
- `unresolvedItems`：查不到的事实归 `system`，必须由负责人决定的事项归 `user`。
- `resolvedUnresolvedKeys`：只关闭本轮已真实解决的未决项。
- `taskCandidate`：所有必要负责人取舍确认后生成的完整抓取任务草稿。

只要本轮仍返回 `question`、`proposedDecision` 或任何 `owner=user` 的未决项，就必须省略 `taskCandidate`，不能同时生成候选草稿。

`taskCandidate` 必须包含：原始需求、品类、市场口径、通用内容、品类特有内容、京东意向、真实调查过的候选来源、明确排除项、未决项和已确认 decision IDs。它描述“准备抓什么、准备从哪里抓”，不描述清洗字段、知识 schema 或 Evidence 规则。

## 完成边界

只有 Workbench 收到显式任务草稿确认，采访才结束。确认只产生一个可执行的抓取任务；不要声称已经抓取数据。此阶段不得调用清洗、Evidence、模型加工或知识包流程。
