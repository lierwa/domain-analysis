# 知识加工产线建设

Status: ready-for-human
更新日期：2026-09-04

评审入口：建设产线的真实界面、发布版本与接入结果。下文设计假设已落实为本机持久产线，当前验证范围以 PROGRESS 和 RESEARCH R-017 为准。

## 简单说明

在 `domain-analysis` 内建设知识加工产线，让用户通过现有系统的界面选择资料、组织加工、处理需要介入的问题，并发布可交付的版本化知识包。本期覆盖本项目的用户流程、界面、处理能力和成品交付。

本文保存需求与取舍，不维护另一份阶段计划或进度。阶段顺序见 [ROADMAP](../../docs/development/ROADMAP.md)，当前进度见 [PROGRESS](../../docs/development/PROGRESS.md)，术语见 [CONTEXT](../../CONTEXT.md)，技术候选见 [RESEARCH](../../docs/development/RESEARCH.md)，工序评审见 [最小加工规范](../../docs/development/KNOWLEDGE-PACK-PROCESSING.md)。

## 已确认的需求

- 阶段二的业务目标是把已采集资料加工成可供外部 Agent 挂载的知识包；内部按试做样包、建设产线、批量验收推进。
- 建设产线限定在 `domain-analysis`，融入当前系统并全面设计相应界面与操作流程。负责人已授权开始开发，依照调研、架构与验收门推进；公共契约和模块责任改变在具体方案评审后实施。
- 原始资料保持不可变；图片复用采集时的分类和血缘，进行有限 OCR。图片导出使用经过检查的去水印副本。
- 无法对齐的歧义内容不能供 Agent 回答使用；保留独立的原始证据与待核材料，其他合格内容可以采用。
- 知识包长期维护并具有版本；补充资料或修正规则后生成新版本，历史版本保留。用户需要区分当前可用内容、正在加工的内容和历史结果。
- 本期发布采用“加工完成 → 自动检查通过 → 查看整包变更与问题摘要 → 负责人确认发布”；发布后可导出并供 Agent 使用。该规则按负责人“先这样”的意见暂行，后续可据实际使用复审。
- Codex Skill 已作为首轮消费验证入口。成品需能支持未来 Agent 启用后优先使用；`opencode-dev` 的核查用于明确消费需求，本期交付范围截至本项目中的知识包生产、预览、发布与导出。宿主启用和运行时接入归入后续跨工程工作。

## 已核对的系统边界

Source Dataset 以 Capture Task 下的不可变原始记录为事实源，Capture Subject 表达批次内来源身份。KnowledgeProcessingModule 已按确认方案独立拥有选料修订、加工运行、内容审核、知识包版本和发布事实；Workbench 顶部导航分别进入抓取任务与知识加工。

依据为 [ARCHITECTURE](../../docs/development/ARCHITECTURE.md)、[SourceDatasetPanel](../../apps/web/src/pages/SourceDatasetPanel.tsx)、[KnowledgeWorkspace](../../apps/web/src/pages/KnowledgeWorkspace.tsx) 与 [API 组合根](../../apps/api/src/index.ts)。正式浏览器验收已覆盖批次选料、整批加工、自动判断、图片原图/副本对照、版本预览、确认发布和下载；组件与运行证据记录在 RESEARCH R-017～R-019。

## 已确认的取舍

### Q1：知识包持续维护与版本

负责人确认：“同意，而且非常重要，知识包是一定存在版本的概念的”。采用长期维护同一个知识包、更新资料或规则后生成新版本并保留历史的产品行为。收益是同一知识范围的变化可以延续和追踪；代价是需要版本管理及对应界面表达。版本生成和发布条件、使用方更新方式、跨批次合并及具体布局另行确定。

### Q2：新版本发布条件

负责人回复“先这样吧，我也想不出更好的方案”。本期按加工完成、自动检查通过、查看变更与问题摘要、负责人确认发布的顺序执行。发布确认针对整包，界面呈现新增、修改、排除内容和检查结果；每版多一次人工操作换取交付前明确的确认点。该取舍确定产品行为，公共生命周期、模块与权限实现仍须后续设计和验证。

| 编号 | 事项 | 推荐的本期范围 | 主要代价或边界 |
| --- | --- | --- | --- |
| 1 | 包与原料范围 | 按明确品类或主题独立建包，允许选取多个采集任务/批次的资料 | 需要管理来源版本、重复与冲突；跨来源身份不能因名称相同自动合并 |

| 3 | 界面入口 | 在现有系统设置“知识加工”入口；围绕知识包查看原料、加工记录、待处理问题和版本 | 需要完整的包管理与详情流程，布局通过后续交互原型验证 |
| 4 | 配置方式 | 提供默认工序和表单配置，可调整选料、可选处理、质量要求与预算，并复用设置 | 灵活性限定在已支持的工序内；必要质量检查始终执行 |
| 5 | 启动与成本 | 新资料提示可更新，由用户启动；开始前展示可估计的工作量/成本与预算上限，超限暂停 | 更新需要一次启动操作；默认预算依据组件原型实测制定，预估不作为保证 |
| 6 | 问题与部分交付 | 问题集中审核，歧义内容隔离；合格内容可形成候选包，发布时明确缺口；声明必需的内容缺失则继续待处理 | 可以交付的范围可能小于原始选料范围，必须让负责人看清完整性 |
| 7 | 知识包交付 | 本项目生产、预览、审核发布并导出版本化知识包，提供内容范围、组织结构、合格内容/图片、来源与读取说明 | 本期交付边界已明确；具体成品格式需调研与验证，宿主接入属于后续跨工程工作 |
| 8 | 使用环境 | 首期服务本人在本地 PC 的工作流，Mac 与 Windows 都做真实验证 | 两种系统均有安装与运行验证成本；本轮范围以单人使用为边界 |

## 第 7 项：本项目的知识包交付

本期在 `domain-analysis` 内完成知识包产线和管理界面，交付可供后续宿主接入的版本化成品。负责人明确的消费目标是启用后在相关问题中优先使用；该目标作为成品设计输入。

本项目需要做好包身份与版本、知识范围、内容目录、合格正文和图片、来源定位、读取说明及完整性信息，并在界面提供加工记录、问题审核、变更对比、版本预览、确认发布与导出。具体成品格式和封装组件按 RESEARCH 的成熟方案与本项目原型选择。

本期验收覆盖本项目的选料到发布流程，以及导出包能否独立读取、定位来源、区分版本、保持内容和附件完整。既有 Codex Skill 小样保留为早期消费证据；后续宿主的启用管理、Pi 工具注册、优先查询行为、消费观测和版本切换，在跨工程接入阶段另行设计和验收。

`opencode-dev` 源码核查保留在 RESEARCH R-014，说明成品需要明确知识范围、来源和可按需读取的组织结构。该核查是消费需求参考，未修改宿主或运行新的模型、浏览器测试。

### 数据与执行约束

- 工作台 PostgreSQL 已增加包、加工运行、逐件结果、自动判断、人工审核决定和版本业务记录。所有原料保存 Capture Task/Run/Snapshot/Asset 引用及哈希，跨来源对象保持来源身份。原料相同哈希可复用机器提取，但每份来源引用继续保留。
- 阶段、运行生命周期、人工处理与尝试记录分别表达；候选内容的 accepted/pending/excluded 处置与机器成功/失败分开。审核决定保存依据和所针对内容哈希，内容变化后原决定不能自动套用。
- 开始加工用数据库事务固定输入修订、配置及工具版本，同时提交 Graphile job。由现有 job key/事务能力避免重复启动；逐件成功结果先保存，进程退出后由持久结果判断复用和剩余范围。停止请求由持久运行记录拥有；子进程复用 Execa 的取消/超时，不自建进程管理器。
- 缓存键包含原始内容哈希、组件版本和影响结果的配置；变更任一项产生新提取。缓存命中仍核验完整性。开始前估计输入数量和机器预算，实际记录逐件耗时、峰值内存、模型消耗与人工处理时间；本次小样耗时仅作参考。
- 内容准入只计算一次，正文、目录、摘要、来源清单和附件都消费同一采用结果。已确认歧义通过显式事实组和依赖关系隔离相关副本；自动跨来源冲突发现尚无验证，未知归属/版本/单位保持待核。ZOL selector 仅在来源 adapter 内，型号和菜单数字只存在实验输入中。
- 图片从原图分两条自动支路：OCR 文字整组判断与标准 PNG 副本生成。系统用原图、识别文字、置信度和坐标判断正文/水印/装饰内容；无水印图生成 PNG 副本，可安全定位的水印由 OCR 四边形形成遮罩并局部修补，其余整图隔离。生成副本后由视觉模型对照原图检查完整性、修补痕迹和水印残留；新运行不提供人工笔刷、遮罩上传、逐行确认或人工图片验收入口。
- 版本检查完成后固定原料、自动建议、人工决定、图片副本、采用内容和 ZIP 哈希。发布命令在同一事务检查这些身份仍一致，并核验必需内容；任何内容变化产生新的版本输入摘要。外部只导出已发布的指定版本，ZIP 下载本身不再次生成或修改版本。
- 新增版本先写入独立成品位置，完成清单和哈希校验后才记录为候选。新构建或发布失败保留已有版本；数据库集成已覆盖中断、重复 job、过期审核/发布与重开读取，真实 v1/v2 同时保留并可独立下载。

### 成品与界面约定

成品采用 R-018 与 ADR-002 的标准 Agent Skill 目录和 ZIP。`SKILL.md` 提供触发范围与查询步骤；`assets/data/catalog.json` 保存结构化事实，`provenance.json` 定位原始快照、附件和原文位置，合格 PNG 位于 `assets/images/`，`scripts/query.mjs` 与 `validate.mjs` 提供离线查询和校验。原始 HTML、PDF、待核 OCR 和复核意见保存在本地产线区；宿主执行契约留待跨工程接入。

正式 Web 采用现有 Workbench 的灰阶 PC 布局：左侧知识包管理，详情依次为选料、加工、审核、版本与发布。选料使用全宽批次表，加工只显示整批阶段和汇总；审核按需要人工、自动处理、加工异常和已处理分队列，页面只使用浏览器主滚动，左侧显示整组问题，右侧显示完成当前判断所需证据；版本页用固定高度区域切换包内文本、JSON 和图片。所有业务状态来自持久事实。
