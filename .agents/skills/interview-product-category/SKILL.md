# 标准商品门类采访

## 目标

把用户的自然语言采集目标推进成一份可确认的门类级 Markdown 范围草案。草案确认后由 Workbench 独立转换为 Capture Task。

采访对象是标准商品门类，例如冰箱或电视；品牌和型号属于门类内待规划的覆盖对象，不是独立采访任务。

## 事实归属

采访只确认以下业务事实：

- 商品门类与市场范围；
- 需要采集的内容和排除内容；
- 品牌覆盖策略及其品牌数量上限；
- 品牌批次大小、每品牌每轮型号量和每品牌任务级型号上限；
- 用户明确提出的来源范围约束；
- 其他会改变最终纳入商品集合的负责人取舍。

以下事实由后续 Planning Run 调查并写入 Crawl Plan Draft：

- 指定来源中的品牌排行榜和入选品牌目录；
- 排行榜是否可验证、榜单行及按已确认策略得到的执行品牌集合；
- 请求预算、节奏、恢复和停止条件；
- Provider 配置和执行入口。

当前系统默认策略必须在草案中显式写出，并由负责人随草案一起确认：

- 选择来源品牌排行榜中综合评分大于 `0` 的品牌，按榜单顺序最多选择 `20` 个；
- 每批 `3` 个品牌；
- 每品牌每轮推进 `10` 个不同型号；
- 每品牌最多纳入 `20` 个不同型号。

负责人可以在采访中修改这些数值或策略。品牌数量上限和每品牌型号上限会改变最终商品集合；品牌批次与每轮型号量只控制同一份计划内的推进节奏。Planning Run 必须调查实际榜单并验证入选品牌目录，不能要求负责人先枚举品牌。

## 调查边界

- 首次调查一个门类，或用户切换到另一门类时，先完成至少一次公开网页搜索。
- 调查只需支撑门类边界、市场口径、内容范围和负责人取舍，不在采访阶段穷举品牌、型号或来源入口。
- 品牌、型号、商品分类、常见参数、部件、原理和公开候选来源属于系统可调查事实，不要求用户枚举。
- 搜索结果只作为采访依据或候选入口；只有实际打开的页面才能声明已观察到格式或访问状态。
- 采访不执行批量翻页、型号枚举、附件下载或 Source Run。

## 提问纪律

- 一轮最多提出一个必须由负责人决定的问题。
- 问题提供 2–3 个互斥选项，只标记一个推荐项，并解释推荐理由和主要代价。
- 用户已经明确的内容直接记录，不重复确认。
- 可调查事实由系统调查，不转成负责人问题。
- 用户可以回答、补充、纠正、否定问题前提或提出新约束；必须理解整条原文。
- 用户明确回答当前问题后，同一轮继续推进下一个必要取舍或形成草案。
- 没有必要取舍时直接形成草案，不为流程完整制造问题。

默认策略没有被用户修改时，不为四个默认值分别制造问题；把完整默认策略写入草案，由负责人一次确认。用户提出不同的覆盖目标但没有给出关键数值时，只询问一个会改变结果的取舍，并解释推荐值和主要代价。

## 采访记录

Workbench 提供的消息、Interview Decision、未决项、草案版本和调查活动是唯一持续事实源。Codex 每轮使用新的 ephemeral thread，只返回本轮增量。

- 保留用户明确提出的范围、排除项、数值约束和纠正。
- 后一句推翻前一句时形成新的当前结论，不并存冲突范围。
- 每轮只说明新增理解、决定和调查结果。
- 新输入到达后，上一版草案不再是可确认结果；最新完整草案通过校验后才能确认。
- 失败或中断重试只重新处理最近一条失败或中断的用户原文。

## Markdown 草案

草案面向负责人审阅，使用普通 Markdown，包含：

- 原始业务目标；
- 门类和市场范围；
- 内容范围与排除项；
- 品牌筛选依据、评分阈值和品牌数量上限；
- 品牌批次大小、每品牌每轮型号量和每品牌型号上限；
- 用户明确提出的来源范围约束；
- 影响范围的已确认决定；
- 支撑门类边界和取舍的关键调查 URL。

草案可以说明准备调查的来源角色和已确认的数量策略，但不生成品牌清单、来源对象、排行榜结果、Provider 配置或 Crawl Plan 字段。草案不是 JSON，也不是 Capture Task schema。

## 完成边界

负责人取舍和系统调查未决项全部解决后，生成最新 Markdown 草案。只有用户显式确认该版本，采访才结束。

确认后由 Workbench 发起独立的纯转换步骤生成 Capture Task。该步骤忠实转换已确认草案，不继续搜索、提问或补充事实。Capture Task 生成后停在任务页，等待 Planning Run。
