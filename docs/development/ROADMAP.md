# 数据抓取与清洗平台路线图

状态：1B 完整执行清单已由真实冰箱 v6 验收；1D 京东真实匿名目录切片通过、详情与评价受限；1E 已有真实多来源批次运行

## 1. 简单说明

项目只有两个阶段：先按一份完整清单把真实原始数据抓回来，再讨论怎么清洗。1B 已能把采访得到的电商、品牌官网、说明书、国家标准、监管附件和底层原理来源统一列成可确认清单。京东 v2 已从真实电视类目保存 30 个 SKU 和 60 条图片 URL，图片文件没有下载；首个详情请求只得到客户端骨架后立即停止，因此详情、店铺和评价尚未完成，不能把目录结果冒充京东闭环。

## 2. 阶段 1：数据抓取

### 1A 对话生成抓取任务

产物：标准商品的版本化 Markdown 采访范围草案，以及用户确认后单独结构化生成的正式抓取任务。

通过门：

- 首句门类直接生效；
- 系统先判断标准商品边界，主动调查标准、品牌、型号、参数和来源，不让用户枚举可查事实；
- 固定服务专业导购 Agent：任务必须覆盖多品牌多型号市场数据、品牌官方配置/说明书、标准/监管和技术原理；四类具体来源未齐或系统调查未决项仍开放时不得形成可确认任务；
- 每个负责人问题都是真实取舍，在普通消息中给出专业推荐、依据和主要代价；不得为了凑选项制造问题，Composer 同时接受建议之外的回答；
- 家电必须包含京东平台来源并解释原因，不询问“是否纳入京东”；淘宝作为后续多平台来源；
- 草稿用可读 Markdown 明确标准商品边界、抓什么、平台/官方来源事实、排除项和系统待核实项；采访回合不输出正式 Capture Task schema；
- 用户确认 Markdown 后才做一次不搜索、不加事实的正式 Capture Task 结构化；
- 确认不触发真实抓取。

### 1B 真实来源 Crawl Plan

用户已于 2026-08-19 授权按 `CRAWL-PLANNING-DESIGN.md` 开发。针对一个已确认 Capture Task revision，先用可见 Planning Run 形成版本化计划草稿；计划必须回答：

- 来源角色、真实入口和访问状态；
- 捕获 HTML、JSON、PDF、CSV/XLSX、图片或其他哪种源站单元；
- 抓取对象、覆盖分母、数量、分页/遍历终止；
- 唯一键、遍历方式和停止条件；
- 已注册 Provider 的 typed 配置、访问频率、请求预算、原始输出和强制停止条件；
- Capture Task 每个来源候选恰好一次、每个原文 topic 至少一次；说明书、PDF 和附件表格必须有正文 target，不能只列入口页。
- Planning 开始前先检查 Capture Task 是否具备核心零售/市场平台、品牌官方资料、标准或监管、权威技术原理四类来源，不能用“当前候选全部使用”掩盖上游候选本身不完整。
- Capture Task 已确认纳入京东时，计划必须包含 `jd.catalog-product@2.0.0` 的目录、店铺、详情、评价汇总和评价样本五类动态 target；一个 `search.jd.com` 通用网页快照不能作为京东商品覆盖通过门。

1B 保持计划生成、审查、修订和确认；计划确认不创建 Source Run。2026-08-20 真实家用冰箱 v6 已确认：7 个采访候选各一次，另加 1 个 NIST 技术来源，共 8 个来源、12 个 target、13 个 topic 全覆盖，海尔说明书 H5、GB 编制说明 PDF 和 CNIS 附件均为独立正文项。

用户确认计划前不得发真实批量请求。

### 1C 单一真实来源闭环

从一个真实来源抓取一批未清洗数据，写入正式本地数据区；重启 API/Web 后仍可查看；JSONL/CSV 或原文件可以导出；数据库计数、导出记录和来源标识一致。

Start/Resume 已改为 PostgreSQL 持久后台派发：HTTP 202 后页面关闭、刷新或离开不影响服务端 Batch，Workbench 只读取持久进度。未领取 job 的 runner 重启恢复和断连完成已通过真实本地 PostgreSQL/随机端口门；执行中进程强杀的整批 exactly-once 仍未通过，不得与页面断连修复混写为完成。

历史 `jd.catalog-product@1.0.0` 的目录＋首商品页面方案只读保留且不能再次启动。当前 `jd.catalog-product@2.0.0` 只接受显式 HTTP 五类 target；Prepare 固定零请求，未配置部署的真实能力开关失败关闭，项目本地开发配置在负责人明确要求真实抓取后显式开启。能力装配不出网；开始执行后每个 redirect hop 必须先写入持久准入账本，访问受限形成 truthful stopped/failed run，不能冒充完整通过。

### 1D 京东闭环

请求级工程门已经覆盖 PostgreSQL Capture Work Item、逐请求 attempt、跨进程冷却/预算/熔断和显式恢复关联；Crawlee 只负责本机持久派发，图片服务器请求必须为零。旧夹具用源站不存在的 `data-jd-*` 属性制造详情图片、店铺和评价完成状态，已撤回。当前真实通过的是匿名目录商品卡：30 个 SKU、60 条图片 URL；详情、店铺与评价仍是未通过项。

真实匿名最小探针已经按每分钟最多 1 个显式 HTTP hop 执行：目录成功，第 61 秒首个详情返回客户端骨架后停止，其余 29 个商品未继续请求。下一门是获准会话下的详情访问与稳定窗口；在负责人决定登录前，不自动登录、不复制签名、不换身份、不扩批，也不宣称京东闭环完成。

### 1E 淘宝、多来源和更新

完整清单现可用公共原始资源 Provider 表达淘宝精确入口、品牌官网、说明书、监管/标准和技术来源，但它不是专站 crawler：只允许精确 URL 或一次同源唯一链接，不做分页、模糊发现、登录或动态站点自动化。2026-08-21 电视任务已从真实 Workbench 点击 Start，307ms 显示后台提交回执后立即离开计划页；新 Batch 仍在服务端运行，并已保存京东目录 1 个 Snapshot、30 个商品工作项和 60 条图片 URL，证明页面不再拥有任务生命周期。此前同计划的完整前台批次为 7/10 来源完成、3 个来源真实失败；下一门仍是详情访问条件和执行中进程强杀恢复，不能用后台派发替代来源能力验收。

## 3. 阶段 2：数据清洗

阶段 1 全部通过后另行访谈和设计。输入只能是阶段 1 的不可变原始数据；清洗结果必须与原始数据物理或逻辑分离。当前不建设 Evidence、知识候选、Review、知识包或 Runtime。

## 4. 停止规则

- 1A 的产品负责人质量验收仍独立保留；当前 1B 完整清单及 1C/1D 有界能力已有明确授权，任何新的真实多来源 Start、专站 crawler 或阶段 2 仍需单独授权；
- 非标准商品不进入当前采访和抓取流程；
- Crawl Plan 未确认，不访问真实来源；
- 京东匿名目录与首错停止已真实验证；登录后访问窗口仍未验证，未经负责人明确决定不进入登录；
- 不新建 POC package、隔离数据库或平行应用；
- 测试绿灯不能代替 Workbench 真实路径验收。
