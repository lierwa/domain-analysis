# Agent 知识生产平台 PRD

版本：V1.1
MVP：官方来源－冰箱完整闭环＋第二商品品类迁移验证
文档性质：产品需求基线

## 1. 文档边界

本文档只回答：为谁解决什么问题、产品如何工作、MVP 做什么、怎样验收。

本文档不规定代码接口、数据库表、文件目录、爬虫选择器或最终技术栈。相关内容由工程师在《总体技术方案》约束下另行设计。

## 2. 产品要解决的问题

Agent 要可靠地完成专业商品导购，不能只依靠通用模型记忆，也不能简单把网页切块后做向量检索。

真正的问题是：

- 来源分散且持续变化；
- 原始页面结构不同，内容可能缺失、冲突或藏在图片中；
- 同一对象存在别名、不同规格和多种表达；
- Agent 需要结构化筛选、比较和证据，而不仅是相似文本；
- 知识生产过程较重，但 Agent 查询应当轻量、稳定、可离线使用。

因此产品必须同时解决“搜集原始资料”和“加工专业商品知识”两件事，并把两者分开管理。

用户不用 ChatGPT、DeepSeek 直接问商品的理由，不是本产品能聊天，而是本产品持续维护一批通用模型通常缺失或无法保证时效、口径和证据的专业商品数据：主流型号、规范参数、功能、技术机制、适用条件、取舍、比较维度、冲突和来源。下游 Agent 只是这些知识资产的消费者。

## 3. 产品定义

本产品是一个面向多个 Agent、Skill 和应用的商品知识生产系统：

```text
一个或多个数据搜集板块
        ↓
可追溯的原始资料
        ↓
商品知识加工厂
        ↓
版本化知识包
        ↓
本地或远程 Runtime
        ↓
一个或多个下游知识消费者
```

首个完整场景是中国市场冰箱商品知识，京东官方自营/品牌官方旗舰店是首批销售资料来源。系统必须以极低成本切换到电视、微波炉等商品品类；知识加工厂不能写死冰箱，Runtime 不能写死商品或某个 Agent。

## 4. 用户与使用场景

### 4.1 知识项目负责人

确认品类、市场、知识能力和资料范围，启动流水线、处理异常并决定是否发布知识包。MVP 中由用户本人承担。

### 4.2 数据维护者

维护来源登录状态、采集范围、失败任务和来源变化。MVP 中可与项目负责人是同一人。

### 4.3 Agent 开发者

下载或连接知识包，通过 Runtime 让 Agent、Skill 或应用查询、筛选、比较并取得来源证据。同一知识包可以支撑多个不同交互流程。

## 5. 核心产品对象

| 对象 | 产品含义 |
| --- | --- |
| 商品知识项目 | 围绕一个商品品类和目标市场长期维护、可被多个消费者复用的知识资产工作空间 |
| 数据搜集板块 | 针对一个已确认来源策略和资料范围的可独立运行单元，例如“京东－冰箱” |
| Provider | 某个来源的接入能力，例如品牌官网页面或京东网页采集；可被多个搜集板块复用 |
| 商品知识模型 | 所有商品品类共用的稳定身份、属性、结论、关系和证据语义 |
| 共享属性字典 | 跨品类复用的属性代码、含义、值类型、单位、别名与标准映射 |
| 品类知识定义 | 以版本化数据选择属性、决策维度、能力问题和官方来源策略；不是品类专用 Schema |
| 任务流水线 | 管理一次从范围确认到知识包发布的完整运行 |
| 商品知识加工厂 | 把不同板块的原始资料加工为可验证专业商品知识的通用能力 |
| 知识包 | 可下载、版本化、可被 Runtime 加载的知识交付物 |
| Runtime | 向 Agent 提供知识查询和包版本管理的轻量运行环境 |

Provider 不等于数据搜集板块。“京东网页 Provider”是来源能力；“京东－冰箱”是绑定教育研究范围、官方店铺白名单和本地登录策略后的业务搜集板块。

## 6. MVP 场景

### 6.1 目标

用户创建一个中国市场冰箱商品知识项目。系统基于调查过的品类知识定义和权威来源范围，覆盖大多数主流品牌与型号，经加工、审核和评测后生成一个可被多个专业导购 Agent/Skill 使用的冰箱知识包。

### 6.2 研究范围规划

系统根据品类、市场和希望支持的使用场景生成候选研究范围，包括：

- 冰箱品牌清单；
- 产品类型与使用场景；
- 用户选购时应关注的参数与能力；
- 型号、规格、价格与在售状态等资料范围；
- 专业知识必须回答的能力问题。

用户可以调整市场、用途和优先级，但不负责从零设计品类字段或样本数。未经确认的范围不能直接进入正式采集。

采集计划必须由“有证据的主流品牌/型号总体 × 产品类型/变体 × 官方来源 × 关注知识层”驱动，而不是随机抓取搜索结果或堆叠卖家。已确认口径为：监管备案形成合规身份台账，品牌官网/说明书、官方自营和核实后的官方旗舰店在同一快照窗口的并集形成官方在售总体；只有取得许可清晰的市场数据后才报告销量加权覆盖。具体来源枚举、更新窗口与数值门槛由 R-010 原型后冻结。

### 6.3 首批资料对象

MVP 知识资产重点覆盖：

- 品牌、系列、型号、SKU/规格；
- 标题、卖点、规格参数和详情说明；
- 价格、促销、库存或上下架状态及其采集时间；
- 主图、详情图及图片中需要识别的关键信息；
- 商品页 URL、采集时间和字段证据位置；
- 功能及其官方定义；
- 技术机制、适用条件和不能从证据推出的边界；
- 用户需求到筛选/比较维度的专业映射；
- 参数与功能之间可解释的关系和使用取舍。

价格和状态属于时点信息，不能被包装成永久事实。

## 7. 用户主流程

| 阶段 | 用户看到和完成的事情 | 阶段结果 |
| --- | --- | --- |
| 1. 创建项目 | 说明品类、市场、官方来源许可和希望支持的使用场景 | 用途说明 |
| 2. 规划范围 | 系统基于调查生成主流品牌/型号总体、品类定义和能力问题，用户确认业务取舍 | 已确认研究范围 |
| 3. 配置搜集板块 | 选择获准官方来源、范围和更新方式，并检查授权状态 | 官方来源－冰箱板块 |
| 4. 执行采集 | 查看发现量、成功量、失败原因；授权或来源状态异常时暂停 | 原始资料集合 |
| 5. 知识加工 | 系统完成抽取、标准化、对象合并和冲突发现 | 候选知识 |
| 6. 人工审核 | 用户处理低置信度、冲突、异常和无法判断的内容 | 审核后的知识 |
| 7. 构建与评测 | 系统生成知识包，并用 Agent 问题集评测 | 候选知识包与报告 |
| 8. 发布与使用 | 用户激活版本；Agent 本地加载或连接 Runtime | 已发布知识版本 |

上述过程必须作为一次可暂停、可恢复、可重试的任务流水线运行，而不是一组互不关联的脚本。

MVP 日常操作以本地 Workbench Web 为主：Codex 负责引导式澄清、解释和候选配置，结构化页面负责回顾、例外审核、恢复、版本差异和发布。CLI 只用于开发、诊断和自动化，不作为用户维护知识资产的必经入口。

## 8. 产品需求

### 8.1 项目与流水线

- 能创建、复制、暂停和归档知识项目。
- 每次流水线必须冻结当次范围、来源、处理规则、模型和知识包版本信息。
- 每个阶段显示进度、结果、失败原因和待人工处理事项。
- 中断后能够继续，不要求从头重跑。
- 允许基于旧原始资料重新加工，不必重新访问京东。
- 增量更新必须生成新版本，不覆盖历史结果。
- 更新策略按来源和知识变化速度配置；稳定规格/机制与价格/库存等时点信息不强制同频，具体频率由试采变化和业务风险派生。

### 8.2 数据搜集板块

- 冰箱完整 MVP 首批提供京东官方自营和经核实品牌官方旗舰店板块，并允许接入品牌官网、官方说明书和监管资料；普通第三方/小型商家排除。
- 用户能够维护采集范围、优先级、更新频率和启停状态。
- 支持用户本人在本地完成京东登录和验证。
- 遇到登录过期、验证码、限流或页面异常时暂停并明确提示，禁止静默跳过。
- 原始页面、必要的页面数据和采集上下文应被保存到本地受限区，供后续重放和举证；只有白名单投影的商品字段和证据定位能进入知识加工，整页原文不进 Codex。
- 系统显示候选资料数量、已采集数量、失败数量、重复数量和覆盖情况。
- 覆盖率必须相对于 R-010 给出的可审计主流品牌/型号总体计算，不能只统计已加入队列的 URL、店铺或搜索结果。
- 采集可以慢，MVP 优先保证可恢复、可核查，不追求高并发。

### 8.3 商品知识加工厂

- 不假设抓回来的数据已经干净或结构统一。
- 同时使用确定性解析、领域规则、必要的模型判断和人工审核。
- 能发现候选字段和表达差异，并由用户确认关键知识范围。
- 保留原始值、标准值、推断状态和来源证据。
- 处理单位、枚举、别名、重复对象、多规格和冲突来源。
- 把规格、功能、机制、适用条件、取舍、需求映射和比较维度作为可追溯知识，而不是只抽取参数表。
- 模型结果不能直接成为已发布事实；必须通过校验并绑定证据。
- 对模型推断、来源冲突、证据不足、异常值、模糊身份和品类定义变更使用例外审核队列，不得编造补齐；低风险、可重放的确定性事实不要求逐条人工确认。
- 官方直出事实和可重放的确定性转换可以自动进入发布候选，但新知识包发布仍需用户明确批准。
- 加工逻辑应能替换模型服务，不绑定单一模型厂商。

### 8.4 知识包与 Runtime

- 知识包必须独立于采集和加工环境，可下载、复制和离线保存。
- 每个知识包有明确身份、版本、适用领域、来源范围和质量状态。
- Agent 至少能够进行精确查询、条件筛选、全文搜索、对象关联查询和证据查看。
- 默认查询顺序为型号/别名精确匹配、结构化筛选排序、全文关键词、对象关系、证据与质量状态。
- 查询默认不要求调用模型、生成 embedding 或连接向量数据库。
- 语义或向量检索只可在真实验收集证明上述能力存在缺口后作为可选增强，不能替代结构化查询或成为包的兼容前提。
- Runtime 支持加载、激活、切换和回滚知识包版本。
- 已发布知识包不可原地修改；Runtime 通过稳定版本指针原子切换到已校验版本，并保留回滚能力。
- Runtime 的通用能力不出现冰箱或具体 Agent 专用命名；购物比较能力由知识包中的结构化知识声明。
- Agent 可选择直接在本地加载，也可连接一个已加载该包的轻量服务。

### 8.5 本地与线上边界

- 采集、解析、Codex 加工、清洗、人工审核、评测和建包只在本地 Workbench 发起和控制。
- MVP 直接调用用户本机已经安装并登录的 Codex CLI 完成需要智能推理的加工任务，不要求用户另备本地模型、模型 API Key 或通用模型 Provider。
- 登录状态、Cookie、浏览器资料和受限采集快照只保存在本地。
- Cookie、认证 Header 和浏览器 Profile 不得进入 Codex 加工任务；原始资料由本地 Workbench 按任务边界提供给 Codex CLI，并保留输入、输出和证据审计。
- 后续线上部分只管理项目维护信息、板块健康状态、知识包、Runtime、权限和审计。
- 线上服务器不得提供执行采集或知识加工的入口。
- 2 核 4G 服务器只作为未来轻量管理与 Runtime 的目标约束，不承担浏览器和模型处理。

## 9. MVP 范围

### 9.1 必须交付

- 本地项目与流水线管理。
- 基于调查生成并确认冰箱主流品牌/型号总体、共享属性引用、决策维度和能力问题。
- 品牌官网/说明书、监管来源与京东网页数据搜集板块；京东使用 Crawlee＋Patchright、本机 Chrome 和专用 Profile，先通过阶段 1A 有界验证再进入生产实现。
- 原始资料保存、任务恢复和人工登录/验证接管。
- 规则、模型与人工协同的知识加工流程。
- 冲突和低置信度审核。
- 通用知识包生成与本地版本管理。
- 轻量 Runtime 和一个 Agent 接入演示。
- 评测报告和来源证据查看。
- 一个第二商品品类的数据化小样本迁移验证；不建设第二品类完整生产知识库。

### 9.2 不在 MVP 内

- 淘宝、天猫和 Amazon 的正式采集；淘宝只登记为京东闭环后的下一来源。
- 自研浏览器指纹、验证码破解、账号切换规避、订单/购物车/账户资料采集或普通第三方商家采集。
- 多来源商品对齐。
- 服务器端采集、清洗或建包。
- 完整线上管理平台。
- 向量数据库和必须依赖 embedding 的查询链路。
- 面向消费者的最终聊天产品。
- 第二个商品品类的完整生产建设。
- 面向任意非商品领域的通用化承诺。

## 10. MVP 验收

### 10.1 验收数据集

使用有证据的冰箱主流品牌/型号总体建立版本化验收集，并覆盖多规格、官方渠道差异、缺货/下架、图片参数和页面异常。品牌数、型号数、知识完整度和抽样规模由 R-010/R-011 根据市场总体、品类定义、组合覆盖和统计目标给出依据，当前不得写死数量或百分比。

该验收集用于验证系统能力，不代表“已经覆盖京东全部冰箱”。系统必须如实显示范围和未覆盖部分。

### 10.2 通过条件

- 用户能够从创建项目开始，完整跑通一次流水线并得到可加载知识包。
- 计划内且当时可访问的官方资料达到随验收集冻结、可解释的保存成功门槛；失败项均有明确状态。
- 已发布知识结论的来源可追溯率为 100%。
- 人工抽检的核心知识层质量必须满足随验收集冻结的统计门槛；置信度、允许误差、分层方式和样本量仍待 R-010/R-011 给出依据，当前不预设无来源的固定准确率。
- 流水线中断后可以从最近完成阶段继续。
- 同一批原始资料可在不重新采集的情况下重新加工并生成新版本。
- 版本化能力问题与下游任务集达到 R-011 冻结的通过门，且结果能够返回证据和适用条件。
- Runtime 查询不依赖模型、网络或 embedding 服务。
- 知识包可以在另一台机器加载，并完成版本切换和回滚。
- 电视或微波炉小样本使用同一生产 Schema、数据库结构、Provider contract、Runtime API 和通用流水线完成验证，只新增版本化品类定义、来源范围和评测数据。

## 11. 后续路线

MVP 验收后，优先完整建设第二个商品品类，验证低成本品类复制；随后再评估新增来源、线上知识包管理和 Runtime 部署。是否扩展到非商品领域必须另立产品与架构调查，不作为本轮通用性目标。
