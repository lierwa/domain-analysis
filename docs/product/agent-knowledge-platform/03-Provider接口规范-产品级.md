# Provider 接口规范（产品级）

版本：V1.0
MVP Provider：京东
文档性质：来源接入的产品责任与验收边界

## 1. 为什么产品需要 Provider

“写一个通用爬虫”无法解决本项目的问题。不同网站在以下方面存在长期差异：

- 资料发现方式；
- 登录和验证流程；
- 页面类型与动态加载方式；
- 型号、规格和价格的展示方式；
- 下架、缺货、跳转、风控和错误页面；
- 页面变化后的维护方式。

如果把这些差异直接写进任务流水线或知识库加工厂，平台最终会变成“京东商品系统”，无法再接淘宝、资料站或昆虫数据源。

Provider 的产品价值是：把“某个来源怎样访问和保真保存”封装成独立能力，让上层只面对一致的任务、状态和原始资料。

## 2. Provider 不是什么

Provider 不是：

- 一个知识库；
- 一个领域清洗器；
- 一个商品 Schema；
- 一个独立的业务搜集任务；
- 一个保证绕过平台风控的工具。

Provider 只理解来源，不决定最终知识。

## 3. Provider 与数据搜集板块的关系

```text
京东 Provider
  ├─ 京东－冰箱板块
  ├─ 京东－洗衣机板块
  └─ 京东－空调板块
```

Provider 是可复用的来源能力；数据搜集板块是 Provider 与具体主题、范围、更新计划的组合。

MVP 只交付“京东 Provider 支撑京东－冰箱板块”所需能力，不宣称首版已经覆盖京东全部频道和页面类型。

## 4. 产品级输入与输出

### 4.1 Provider 接收

- 已确认的数据搜集范围；
- 搜索词、分类入口或种子页面；
- 采集优先级和更新规则；
- 本地登录状态；
- 本次流水线的任务上下文。

### 4.2 Provider 交付

- 发现的来源对象及稳定来源标识；
- 原始页面与完成举证所需的页面数据；
- 来源 URL、采集时间和页面状态；
- 成功、重复、跳过、失败和待人工处理状态；
- 能支持后续字段证据定位的来源上下文。

Provider 输出的是原始资料，不是“已经清洗好的冰箱商品”。对象合并、单位统一、属性判断和知识结论由知识库加工厂完成。

## 5. Provider 必须具备的产品能力

### 5.1 能力与范围声明

- 明确 Provider 版本和当前支持的来源范围。
- 明确支持和不支持的页面类型、登录方式及资料类型。
- 当能力不完整时如实声明，不用空字段伪装成功。
- 数据搜集板块创建前，能够判断其配置是否在支持范围内。

### 5.2 资料发现

- 根据已确认范围发现候选资料。
- 按品牌、类型和型号矩阵执行发现，不以随机搜索结果代替范围覆盖。
- 区分列表入口、详情对象、规格对象和无效链接。
- 对候选资料去重，并保留发现来源。
- 显示发现量和范围覆盖情况，不把“抓到一些”描述为“已经完整”。

### 5.3 页面访问与状态识别

- 识别正常、需要登录、需要人工验证、限流、缺货、下架、跳转和错误页面。
- 动态内容未完成加载时不能标记成功。
- 多规格页面必须知道当前保存的是哪个规格状态。
- 页面结构变化导致关键内容缺失时，应进入异常状态而不是返回空数据。

### 5.4 人工登录和恢复

- 登录与验证由用户在本地浏览器完成。
- 登录状态过期时暂停相关任务并提示用户接管。
- 用户完成登录或验证后可以继续原任务。
- 不要求用户复制 Cookie，不把认证信息上传服务器。

### 5.5 原始资料保真

- 保存足以重现当时页面内容和完成证据定位的原始资料。
- 每次采集保留时间、来源、板块和 Provider 版本。
- 新采集不得覆盖旧采集。
- 后续解析规则变化时，可以优先重放旧资料而不是重新访问来源。
- 认证信息、个人信息和与目标无关的敏感响应不能进入可发布知识包。

### 5.6 任务运行与维护

- 支持慢速、可暂停、可恢复和可重试的运行方式。
- 显示板块级和任务级成功率、失败原因和待处理数量。
- 支持按变化或过期规则进行增量采集。
- Provider 更新后保留版本信息，旧资料仍能说明由哪个版本采集。
- 页面变化被发现后，能够把板块标记为“需维护”，停止错误数据继续进入加工厂。

## 6. MVP：京东 Provider 的产品范围

### 6.1 必须支持

- 用户在本地完成京东登录并复用登录状态。
- 根据确认后的品牌、分类入口、搜索词或种子页面发现冰箱候选商品。
- 访问冰箱商品详情页并保存标题、卖点、规格参数、详情内容和相关图片的原始来源。
- 识别并保存当前选择的 SKU/规格信息。
- 保存采集时可见的价格、促销、库存或上下架状态，并明确时间属性。
- 识别登录、验证、限流、下架和页面结构异常。
- 对失败任务重试或转交人工，不静默丢弃。

### 6.2 MVP 不保证

- 京东全部频道和商品门类通用。
- 永久在线、永不变化的页面解析。
- 绕过验证码、风控或访问限制。
- 通过未公开接口大规模高速抓取。
- 全量商品评论、问答、直播或推荐流采集。
- 对商品事实做标准化和真实性判断。

## 7. 用户可见状态

数据搜集板块至少应让用户区分：

- 尚未配置；
- 登录可用或登录失效；
- 等待执行；
- 正在发现资料；
- 正在采集；
- 等待人工处理；
- 部分完成；
- 完成；
- 失败；
- 因页面变化需要维护。

“部分完成”必须列出缺失范围，不能直接进入正式发布而不提示。

## 8. MVP 验收

使用 PRD 中确定的冰箱验收集验证：

- 覆盖不少于 5 个品牌和 50 个有效商品型号；
- 包含普通详情、多规格、促销、缺货/下架、图片参数和异常页面；
- 当时可访问的计划页面原始资料保存成功率不低于 90%；
- 所有失败、跳过和人工接管任务均有明确原因；
- 任意抽取字段能够回到对应来源页面和采集时间；
- 人为中断运行后可以继续，已完成任务不重复破坏性执行；
- 模拟关键页面结构变化时，系统不能静默生成空记录；
- 原始资料可以在不重新访问京东的情况下被重新加工。

## 9. 后续 Provider 的接入原则

淘宝 Provider 接入时，产品流程、知识库加工厂和知识包使用方式不得改变。新增来源只应增加：

- 来源能力；
- 对应数据搜集板块配置；
- 必要的来源维护和跨来源知识规则。

如果新增淘宝必须修改通用项目流程，说明 Provider 边界设计失败。

本文档不提前决定：

- 函数名称和参数；
- 页面选择器与网络响应策略；
- 浏览器 Profile 的具体保存方式；
- 任务队列、并发、退避和重试算法；
- 原始资料目录和序列化格式；
- Provider 插件的加载机制；
- 单元测试和契约测试框架。

工程团队应在京东可行性验证后提交上述详细设计，并证明其满足本规范的产品能力和验收标准。
