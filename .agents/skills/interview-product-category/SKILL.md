# 商品抓取任务采访

## 目标

把用户的标准商品调研需求推进成一份可确认的 Markdown 采访范围草案。电视机、冰箱等有稳定型号、规格和标准体系的商品适用；手工孤品、定制品等非标商品不适用。Skill 只规定理解、调查、提问、记录和文字草案综合行为，不在采访阶段设计正式业务结构。

## 首句处理

- 把“抓冰箱”“收集电饭煲数据”直接视为已给定品类方向，不要再问“是否只做冰箱”。
- 若一句话包含多个品类，也先接受，再只询问真正影响执行的优先级或拆分取舍。
- “中国市场”默认指中国大陆普通消费者实际可以买到的品牌与型号，不按品牌国籍排除 TCL、东芝等品牌；除非用户明确要求其他市场，不要为此重复提问。

## 系统负责调查的事实

以调用方提供的采访工作资料为既有事实，再调查获准访问的公开来源。不要读取仓库或本机资料。以下事项不能转嫁给用户枚举或选择：

- 品牌、型号、商品分类和市场可售范围；
- 常规参数配置、部件、工作原理和该品类特有内容；
- 品牌官网、监管/标准机构、专业技术来源、电商入口及其可见格式；
- 来源当前是否公开、需要登录、受限或不可用。

首次调查一个品类，或用户把当前需求改成另一品类时，必须先真正完成至少一次公开网页搜索，再提负责人问题或形成草稿；只发起但未完成的搜索不算调查。其他轮次只在新事实确有需要时搜索，不为展示过程重复搜索。

公开搜索只用于形成采访事实和抓取范围，不执行批量抓取。搜索结果可以作为待核验候选入口；只有实际打开后才能声称已观察到格式或访问状态。不得编造 URL，也不得把候选入口说成已抓取数据。采访草案只需用自然语言或 Markdown 链接保留这些事实，不生成来源对象、观察时间或 Crawl Plan 字段。

## 预设内容框架

从以下通用范围出发，并结合具体品类持续补充；它是内容清单，不是要求用户设计的字段定义：

- 市场分类、品牌、系列、型号和在售状态；
- 商品详情、页面原始参数、说明书、图片和其他源站媒体；
- 功能、关键部件、工作原理、安装使用、维护和常见问题；
- 监管、标准、能效或认证资料；
- 价格与促销等具有时间性的源站信息；
- 用户评价原文、评分分布、好评率和差评率（来源允许时）。

某品类还有明显重要内容时，主动加入品类特有内容，不要要求用户先设计字段。

这些内容最终服务于同一门类下多品牌、多型号的专业导购比较和解释。采访阶段只需调查到足以确认品类边界、市场口径、内容方向和真实负责人取舍；把关键搜索证据 URL 写进草案。品牌版图、逐品牌官网、参数/说明书、标准/监管和技术原理的执行入口由后续抓取计划阶段负责，不在采访中提前凑齐或要求用户枚举；该阶段当前正在重新设计，采访不得预设其实现。

## 平台来源策略

平台、网站、入口及其优先级都属于系统调查和来源规划事实；只有会真实改变业务边界或抓取量且无法由公开事实判断的取舍，才交给负责人。跨品牌市场目录、品牌官网、标准监管和技术原理来源分别按实际内容职责进入后续计划。入口只有在公开、可审计并符合届时已验证的访问能力时才进入执行范围；采访草案不预先承诺平台覆盖。

## 范围依据纪律

生成草案前，逐项检查所有会改变纳入商品集合、市场范围或观察时间范围的边界。某项边界只有具备以下任一依据时，才能直接写入草案：

1. 用户当前或历史原文已经明确；
2. 已由负责人回答并形成 confirmed Interview Decision；
3. 属于本 Skill 已明确批准的系统默认；
4. 是调查得到、且不包含负责人选择的客观事实。

调查结论和专业推荐不能自行扩大“系统默认”。凡是会改变结果、却没有上述依据的边界，选择影响最大的一个形成 `proposedDecision`，并在该轮省略 `draftMarkdown`。推荐答案只是 proposal，不等于用户确认。

这不是最低问题数要求。用户原文已经完整覆盖必要边界时，可以在调查完成后零问题生成草案；不得为品类、关键词或固定问题建立条件表。

## 提问纪律

- 一轮最多问一个必须由负责人决定的问题。
- 每个问题必须提供 2–3 个互斥选项，且只能有一个推荐项；给出推荐理由和主要代价。
- 可调查事实由系统查，不提问。
- 当前问题只是理解用户下一句话的上下文，不是限制输入的表单。用户可能回答序号、说“按推荐”、给出自定义方案、纠正前文、补充来源或事实、否定问题前提，也可能反问原因；必须理解整条原文并逐项承接。
- 只有用户意思明确时，才把当前问题解释为一个已明确取舍。不能因为一句话含有选项回答，就丢掉同一句里的其他事实或修改要求。
- 若答案有歧义或用户正在追问，不要猜测并确认；先回答或只追问一个真正必要的澄清，原问题继续保持未决。
- 若用户明确否定当前问题的前提，先判断其纠正是否成立；成立时撤回这个问题并记录原因，不得强行映射成某个选项、自定义答案或继续保留为负责人未决项。
- 明确回答被理解后，同一轮继续推进：仍有下一个真实负责人取舍就提出它；没有则继续必要调查或形成新草稿。不要只回复“已记录”后要求用户再输入“继续”。
- 存在尚未确认的当前问题时，不推进依赖它的下一问题。
- 没有必要取舍时，不为凑流程提问，直接继续调查或形成草稿。
- 示例：是否纳入已停售型号、首期覆盖哪个市场或明确的历史时间窗，可以是负责人取舍；品牌、参数、标准、来源平台及来源入口不是。

## 采访记录纪律

把调用方提供的消息、已确认决定、未决项、当前草稿和来源调查记录视为持续演进的工作资料，作用相当于设计采访中同步维护的 glossary 与 ADR：

- 用户明确给出的范围、排除项、纠正和偏好必须保留；后一句推翻前一句时说明变化，不悄悄并存两个冲突结论。
- 调查得到的标准、品类内容和来源事实必须说明依据强度；搜索发现、页面实际观察和访问限制不能混写成同一可信等级。
- 每轮只说明本轮新理解、解决或修改的内容；不要重报全部历史。
- 已有草稿时，根据新事实或纠正形成新的完整草稿候选；历史版本必须保留，不能覆盖。
- 用户只是要求解释、且没有改变任何抓取范围时，明确说明当前范围未变，不虚构决定、未决项或草稿修订。
- 一旦收到新输入，不再把上一版草稿当作当前可确认结果；完成本轮理解后，只有最新范围完整、没有负责人未决项的草稿才可提示确认。
- 失败或中断后的重试只能重新处理最近一条失败或中断的用户原文；不得选择更早的历史消息伪装成本轮输入。
- 只有必要负责人取舍已明确后才形成完整草稿。草稿必须综合原始需求、对话事实、已确认决定和来源调查，说明准备抓什么、准备从哪里抓；来源级内容、数量和停止口径仍由后续 Crawl Plan 冻结。

## 草案格式

- 草案必须是人能直接审阅和修改的普通 Markdown，可以使用标题、段落和清单。
- 草案应说明原始目标、已确认范围、纳入项、排除项、用户回答和搜索得到的事实；没有内容时不要为了凑标题制造信息。
- 草案不是正式 Capture Task，不得输出 JSON，也不得设计或填充 `taskCandidate`、`sourceCandidates`、`observedAt`、`decisionIds` 等业务字段。
- 若调用方要求调查凭证，只提交草案中用于判断品类边界、市场口径或取舍背景的关键 URL。每个 URL 必须来自已完成的公开搜索并原样出现在 Markdown；这是采访范围行为校验，不是品牌清单、正式来源对象、数量清单或 Crawl Plan。
- 草案确认前，所有修改仍是采访记录和新 Markdown 版本；不得偷偷提前结构化。

## 完成边界

只有负责人取舍和影响范围的系统调查未决项都已解决，并且最新 Markdown 草案清楚表达品类、市场、内容与排除边界后，才可提示用户确认。品牌、官网、标准和技术来源不在采访阶段穷举。只有用户显式确认本轮完成后的最新 Markdown 草案，采访才结束。确认之后由 Workbench 发起一个独立的纯转换步骤，把已确认文字生成正式 Capture Task；该步骤不得继续搜索、提问或补充新事实。Capture Task 生成后停在任务页，当前不会自动进入计划或抓取。此阶段不得调用清洗、Evidence、模型加工或知识包流程。
