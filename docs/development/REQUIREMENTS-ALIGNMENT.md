# 当前产品决定与需求对齐记录

状态：当前有效
更新日期：2026-08-24

本文件只记录用户已经明确确认、会约束后续设计和验收的产品决定。2026-08-18 以前围绕 Evidence、Knowledge Factory、知识包和 Runtime 的 18 项访谈问题树已被“两阶段：数据抓取、数据清洗”的产品收口取代，原文保留在 Git 历史中，不得继续驱动当前实现。

## D001 两阶段产品范围

状态：已确认（2026-08-18）

项目只包含两个阶段：先抓取并保存真实原始数据，再讨论数据清洗。当前只实施阶段 1。Evidence、知识加工、知识包和 Runtime 不在当前生产组合根。

## D002 当前只服务标准商品

状态：已确认（2026-08-19）

采访 Skill 面向能够通过品牌、型号、规格、分类、国家/行业标准或其他稳定身份进行枚举和比较的标准商品，例如冰箱、电视机。手工制品、孤品、定制品等非标准商品不属于当前范围。

系统必须主动调查是否存在国标、监管备案、能效/认证和稳定市场分类；不能要求负责人预先提供完整品牌、型号、参数或来源清单。

## D003 专业引导式采访

状态：已确认（2026-08-19）

采访 Skill 参考 `grill-with-docs` 的推进方式，但服务于专业数据抓取。用户不是专业抓取工程师，Agent 必须用调查和专业判断引导用户理解过程，每次只推进一个真实取舍，并提供有依据的推荐答案和主要代价。

推荐项应当是当前证据下的专业默认答案。不能为了满足“2–3 个互斥选项”的输出形式强行制造没有业务意义的问题，也不能把可调查事实伪装成负责人决定。

采访必须理解用户通过 Composer 发送的完整自然语言，而不是切换到只能识别选项的表单模式。`1`、`按推荐`、自定义回答、纠正、附加事实、否定问题前提和追问都必须接回同一段对话；一句话同时回答问题并补充范围时，两部分都要保留。

## D004 多平台来源与京东边界

状态：已被 D014 替代（2026-08-24）

标准商品抓取需要多来源数据。对冰箱等家电，京东是必须覆盖的核心市场目录来源，用于观察公开分类、筛选、品牌、分页、商品卡、展示价格/评价数量和卡片媒体 URL；淘宝是京东之后需要增加的多平台来源。京东当前不承担商品详情、官方型号参数、说明书或评价正文的完整来源职责。

因此采访不默认询问“是否纳入京东”。平台范围由系统根据商品和市场事实主动规划、解释并写入草稿；负责人仍可明确提出排除要求。平台必须覆盖不等于已获准访问，真实抓取必须分别通过许可、登录、验证码、风控、频控、熔断、恢复和 Crawl Plan 确认门。

该决定的“京东必须覆盖”部分已被真实访问证据和负责人新决定替代；保留本节只用于解释历史任务中的 `jd` 字段。

## D014 规划阶段 AI 深度调查品牌与官方来源

状态：已确认（2026-08-24）

当前正式规划先不执行京东。Planning Agent 必须通过多轮网页搜索尽可能完整地调查一个品类的品牌集合，并逐品牌核实官网、型号/参数/说明书入口；国家标准、监管、能效认证、关键部件、技术路线和底层原理也在同一规划阶段深度调查。用户不负责预先枚举品牌、官网或知识来源。

“尽可能全”不是绝对市场全集承诺，而是可审核的研究与采集过程：至少四路独立非 JD 品牌发现证据、逐品牌官网或 unresolved 对账、四类调查记录、全部任务 topic 到实际来源的映射和明确停止理由。AI 只生成 version 4 Crawl Plan Draft；Workbench 再把官网种子确定性组装成有界 `site` route，把明确正文/附件组装成 `exact` route。只有内容验收为 accepted 的原始页面才增加有效完成数；负责人确认前不创建 Source Run、不批量抓取。历史京东 Plan/Run/Snapshot 只读保留，不进入新执行清单。

## D005 事实、建议与决定分离

状态：已确认（2026-08-18，2026-08-19 澄清）

- 标准、监管、品牌、型号、参数、部件、来源和平台结构等可调查内容由系统调查；
- Agent 的问题和推荐只是 proposal；
- Workbench 先保存负责人通过 Composer 发送的原文；Agent 结合当前问题、历史消息、调查结果和草稿理解整条输入，只在语义明确时提交规范化的决定解释，Workbench 校验后保存 confirmed Interview Decision；
- 用户补充或纠正的相关事实、Agent 查回的事实和草稿版本共同组成持续演进的采访工作资料，是最终草稿的依据；追问或歧义输入只继续对话，不能被误记为选择；
- 消息文案、模型建议和搜索结果不能直接成为任务事实；
- 没有负责人未决项后才能形成可确认的 Markdown Capture Task Draft；采访回合不生成正式任务结构。

## D006 抓取任务与版本

状态：已确认（2026-08-18，2026-08-20 澄清）

对话产出版本化 Markdown Capture Task Draft。用户整体确认后，Workbench 才通过独立纯转换步骤创建结构化 Capture Task；转换不得继续搜索、提问或补充新事实，也不自动抓取。确认后仍可回到同一对话修改范围；再次确认保持 Capture Task ID 不变并推进 revision，旧确认草案不可变。

## D007 本地执行与停止门

状态：已确认（持续有效）

Workbench、Codex 采访、来源访问和原始数据保存都在本机执行。Cookie、Profile、密码、认证 Header 和验证码材料不得进入 Git、日志、Codex 输入或导出。登录、验证码、风控、拒绝访问、许可不明或频控熔断时停止，不自动绕过。

1A 的专业问答质量仍需真实 PC 人工验收。用户于 2026-08-19 在理解规划流程后明确授权实现 1B 的最小规划纵切片，因此旧的“1A 未验收不得实现 Crawl Plan”门对本次实现失效；它仍与 Crawl Plan 确认、Provider、许可和频控门共同阻止任何真实来源抓取。测试、fixture、POC 和历史样本不能代替真实页面与真实来源验收。

## D008 Crawl Planning 与正式抓取分离

状态：已确认（2026-08-19）

Capture Task 确认后由负责人显式启动 Crawl Planning。Codex 在 Workbench 可见时间线中搜索并核实具体网站，形成可修订、可确认的版本化 Crawl Plan；计划直接决定来源、每个来源捕获的内容和数量。Planning Run 不做批量抓取，Confirmed Crawl Plan 也不自动创建 Source Run。

本轮采用前台可见、连接关闭即中止的最小运行语义；不为单次短规划引入后台队列或持久工作流。正式抓取运行中不允许 Codex 无边界边搜边抓；发现新来源时必须回到新的 Planning Run 和计划确认门。

## D009 采访、范围确认、结构化计划与执行分段

状态：已被 D014 的当前规划策略取代（2026-08-24）

从 Agent 发出第一句话到开始真实抓取，共有四段：第一段采访与必要搜索，只保留消息、用户回答、调查活动和文字事实；第二段生成并由用户确认可读 Markdown 范围草案；第三段先把已确认范围转换成正式 Capture Task，再制定并确认严格结构化 Crawl Plan；第四段必须由用户显式启动，才执行已确认计划。前三段的任何确认都不自动开始抓取。

采访协议只允许承载推进对话所需的最小 typed 状态，例如当前问题的 proposal/resolution 和 `draftMarkdown`；不得在每轮输出完整 `taskCandidate/sourceCandidates/observedAt`。正式 Capture Task 和来源、内容、数量、停止口径只在各自通过门之后结构化。

## D010 可执行计划与显式真实运行

状态：已确认（2026-08-20）

该历史实验只保留为 JD 路线否决证据；当前不得据此启动新的 JD canary。Crawl Plan 仍必须绑定已实现 Provider；确认计划只冻结版本，另一次显式“开始抓取”才创建 Batch/Source Run。

## D011 专业导购 Agent 的数据目标

状态：目标保留，来源策略已由 D014 修订（2026-08-24）

抓取数据最终用于同一商品门类下的多品牌、多型号专业导购比较。当前由 Planning Agent 深搜品类品牌版图，品牌官方站点负责可核实型号、配置参数、规格页和说明书；任务还必须包含国家标准/监管/能效/认证、关键部件与底层工作原理，使后续 Agent 能解释参数差异而不是只复述商品页。

因此完整标准商品任务至少同时具备核心零售/市场平台、品牌官方资料、标准或监管、权威技术原理四类具体候选入口。该组合属于系统调查与产品完成门，不是负责人逐项选择题；缺失时不得生成可执行 Crawl Plan。阶段 1 仍只保存不可变原始数据，导购 Agent、清洗、标准化和知识加工属于后续阶段。

## D012 京东图片当前只保存 URL

状态：历史 JD 专项决定；当前正式计划排除 JD（2026-08-24）

当前京东阶段不下载商品卡图、变体图或其他图片字节。系统只从已经取得的公开目录 HTML 或源站 JSON 中保存商品卡/变体图片原始 URL、资源类型、用途、区块、顺序、所属商品关系和来源快照关系；不得请求详情页来补图片，不得向图片 CDN 增加请求，不生成京东图片 `SourceAsset`，也不记录未经取得的内容哈希、尺寸或本地内容地址。

这是以请求最小化、尽量不触发京东限制为第一优先级的产品决定。通用 `SourceAsset` 与本地内容寻址存储继续用于 Crawl Plan 明确要求下载的 PDF、XLSX 等来源，不因本决定删除。

## D013 市场目录发现、品牌官网补齐与完整性

状态：已被 D014 取代（2026-08-24）

用户仍创建一个逻辑抓取任务。系统内部先用京东公开目录观察品类中的品牌和商品卡，再把真实发现的品牌/型号候选交回新的 Crawl Planning Run，确认品牌官网、产品目录、规格页和说明书来源后继续抓取；剩余问题通过后续计划版本修复。Source Run 不得边抓边搜、自动扩大来源范围。

完整性必须按已冻结的市场、观察时间、生命周期和入口口径对账：京东品牌/分页/商品卡分母、品牌官网映射、型号匹配、官方产品页与说明书覆盖都要有原始证据。任一未知、缺失、歧义、受限或分母不一致都必须显式记为 gap 并使整体状态保持 `partial`，不得用“抓到一些记录”冒充完整。原始事实仍只属于 Source Dataset；覆盖与缺口是可从不可变快照重建的控制投影，不是阶段 2 知识库。
