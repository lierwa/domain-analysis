# 知识包格式规范（产品级）

版本：V1.1
文档性质：知识交付物的产品结构与能力要求

## 1. 为什么要抽象“知识包”

如果 Agent 查询时仍然需要连接采集数据库、运行清洗脚本或调用建库模型，那么知识生产和知识使用就没有真正分开。

知识包要解决的是：

- 本地重加工一次，Agent 可以重复使用；
- 采集与清洗环境可以关闭，查询仍然可用；
- 数据能够下载、复制、部署、切换和回滚；
- Agent 知道包里有什么、能怎样查询、结论来自哪里；
- 不同商品品类使用同一种加载和管理方式，而不共享一套写死的品类字段。

因此知识包是本项目的核心产品交付物，不是某个数据库文件的别名。

## 2. 知识包的产品定义

知识包是一份：

- 只读；
- 有版本；
- 可验证；
- 可携带；
- 可被 Runtime 理解；
- 能说明自身领域和能力；
- 能把知识结论追溯到来源证据；

的 Agent 知识发布单元。

“知识包”是逻辑概念，最终可以表现为下载包、本地目录或由包管理服务托管的版本。本文档不提前规定它必须只有一个文件，也不规定内部数据库表。

## 3. 为什么需要分层

知识包同时承载知识、查询、证据、版本和专业能力。如果全部混成一张冰箱表，会产生三个问题：

1. 无法低成本支持电视、微波炉或其他商品品类；
2. 无法区分事实、证据、推断和查询索引；
3. 一次搜索引擎或存储技术变化会迫使整个包重做。

因此必须在产品语义上分层，但具体文件和表由工程设计决定。

## 4. 知识包的产品层次

| 层次 | 解决的问题 | 必须表达的内容 |
| --- | --- | --- |
| 身份与兼容层 | 这是什么包，能否加载 | 包 ID、版本、领域、发布时间、兼容范围、状态 |
| 商品模型层 | 包里有哪些稳定概念 | 商品、型号/变体、Offer、属性、关系、术语、单位和共享字典版本 |
| 品类定义层 | 当前品类如何使用公共模型 | 属性选择、别名、值域、决策维度、能力问题和官方来源策略 |
| 知识数据层 | 消费者可以查询什么 | 对象、规格、功能、机制、适用条件、取舍、关系、限定条件和时点信息 |
| 证据与来源层 | 为什么相信这条知识 | 来源、采集时间、证据位置、处理过程和推断标记 |
| 查询能力层 | 怎样高效找到知识 | 精确、筛选、排序、全文搜索和关联导航所需能力 |
| 消费能力层 | 这个包为下游提供什么业务能力 | 可用操作、决策维度、参数含义、返回内容和使用说明 |
| 质量与评测层 | 这个版本是否适合发布 | 覆盖情况、已知缺口、准确率、评测结果和风险 |
| 附属资源层 | 知识是否依赖图片等资源 | 经允许发布的图片、缩略图或辅助材料及其来源 |

这些层次是产品责任，不等于八个固定目录。

## 5. 稳定商品模型与品类数据

### 5.1 稳定商品模型必须理解

- 商品、型号、变体和销售要约；
- 对象的别名、类型和身份边界；
- 对象之间的关系；
- 带来源和限定条件的知识结论；
- 版本、质量、证据和查询能力。

### 5.2 稳定商品模型不能假设

- 所有商品都是冰箱；
- 所有品类共享同一组专业属性；
- 所有知识都来自销售页面或都带价格；
- 所有查询都需要向量相似度。

### 5.3 品类知识定义负责

冰箱、电视等品类知识定义以版本化数据选择共享属性、值类型、单位、别名、决策维度、能力问题和官方来源策略。切换品类不得修改生产 Schema、数据库结构或 Runtime API。

## 6. MVP 冰箱知识包应表达什么

### 6.1 领域对象

- 冰箱品牌、系列、型号和规格；
- 商品页面与时点 Offer；
- 参数、功能、技术机制、适用条件、使用取舍、决策维度和对象关系；
- 原始表达、标准表达和别名。

### 6.2 结论状态

每条重要知识需要区分：

- 来源直接给出的值；
- 经过确定性转换的值；
- 模型推断的候选值；
- 人工确认的值；
- 存在冲突或暂未确认的值；
- 带采集时间的动态值。

Agent 不应把冲突、推断或过期价格当成无条件事实。

### 6.3 下游使用能力

任意冰箱导购 Agent 或 Skill 至少能够：

- 按品牌、类型、尺寸、容量、功能和价格条件筛选；
- 查找某个型号及其规格；
- 比较多个型号并说明差异；
- 找到同一型号的不同规格或 Offer；
- 查询某项结论的来源和采集时间；
- 在知识不足或冲突时得到明确提示。
- 解释关键功能背后的机制、适用条件以及证据不支持的部分；
- 把用户需求映射为可解释的筛选和比较维度，而不是只返回参数表。

同一包可以被多个消费者加载。消费者自己的主动提问、状态机和界面不进入知识包事实层，也不能反向定义包 Schema。

## 7. 检索原则

MVP 默认采用以下产品顺序：

1. 标识、型号和别名精确匹配；
2. 结构化条件筛选、排序和聚合；
3. 全文关键词搜索；
4. 对象和关系导航；
5. 返回证据和质量状态。

向量或语义检索可以在未来作为可选增强，但不能成为：

- 知识包的必需组成；
- Agent 每次查询前必须执行的步骤；
- Runtime 启动的外部模型依赖；
- 结构化筛选和证据查询的替代品。

## 8. Agent 的三种使用方式

### 8.1 本地直接加载

Agent 应用下载知识包，在本机通过 SDK 或 Runtime 读取。适合离线、个人和桌面应用。

### 8.2 本地 Runtime 服务

本机运行一个轻量服务，多个本地 Agent 共用当前激活知识包。

### 8.3 远程 Runtime 服务

服务器加载已发布知识包，Agent 通过网络查询。服务器只使用现成知识包，不运行采集、模型或清洗。

三种方式使用相同的包身份、查询语义和证据规则。具体 SDK、HTTP 或 MCP 协议由工程设计确定。

## 9. 版本生命周期

```text
构建 → 评测 → 候选 → 发布 → 激活 → 被新版本替换 → 归档
```

- 构建完成不等于可以发布。
- 评测不达标或存在未处理严重冲突时不能激活。
- 已发布版本不可被原地修改，只能发布新版本。
- 新版本加载成功后才能替换旧版本。
- 用户可以查看版本差异、已知缺口并回滚。
- 包被归档后仍应保留必要的版本和审计信息。

## 10. 可携带与安全要求

- 包不依赖采集工作目录、浏览器 Profile 或本地任务数据库。
- 包不包含 Cookie、登录凭证、完整认证响应或用户隐私信息。
- 包能够验证是否完整、是否被意外修改以及是否与 Runtime 兼容。
- 包应声明使用的来源范围和允许发布的证据类型。
- 外部资源不可用时，核心结构化知识与来源说明仍应可读。
- 包的资源消耗应允许未来在 2 核 4G 服务器上加载和查询；具体大小与性能上限在 MVP 实测后冻结。

## 11. MVP 验收

- 知识包可以离开生产工作目录复制到另一台机器。
- Runtime 能识别包身份、领域、版本、质量状态和可用能力。
- Runtime 不需要模型、向量数据库、PostgreSQL 或网络即可完成基础查询。
- 精确查询、条件筛选、全文搜索、对象关联和证据查看均能工作。
- 已发布知识结论 100% 能返回来源；推断和时点信息有明确标记。
- 新旧两个版本能够安全切换和回滚。
- 商品专用能力不出现在 Runtime 通用能力中。
- 知识包中不存在认证状态和未允许发布的原始敏感资料。
- 第二商品品类小样本可以用完全相同的包结构与 Runtime 加载，只有品类定义和知识数据不同。

## 12. 留给工程设计的内容

工程团队在原型验证后决定：

- 物理文件组织；
- 数据库、索引和资源格式；
- 稳定商品对象、结论、关系和证据的精确 Schema；
- 版本兼容与迁移机制；
- 校验和、签名和压缩方式；
- SDK、HTTP、MCP 的实际协议；
- 查询性能、缓存和并发策略。

工程设计可以改变实现，但不能取消本文档定义的分层责任、可携带性、证据、版本、品类数据化和消费者解耦要求。
