# Agent 知识生产平台 MVP 实施计划

版本：V1.0
实施目标：京东－冰箱端到端闭环

## 1. 实施原则

MVP 不是先搭一个“万能平台”，再等待真实数据接入；而是先用京东－冰箱跑通一条完整纵向链路，同时守住未来扩展边界。

实施顺序必须是：

```text
真实页面可行性
  → 最小原始资料闭环
  → 最小知识加工闭环
  → 最小知识包与 Agent 查询
  → 再补任务管理和完整验收
```

如果真实京东页面、混乱数据加工或轻量知识包中任一环节不可行，不应继续投入平台 UI 和通用插件框架。

## 2. 交付假设

- 首版由一名主工程师负责 Node/TypeScript 主体，可借助 AI 编程工具，但关键设计和验收由人确认。
- 用户担任产品负责人和知识范围审核者。
- 模型 API 或本地模型资源单独准备；Codex/ChatGPT 订阅不作为应用 API 预算。
- 采集、清洗、评测和建包均在本地电脑执行。
- MVP 只做京东－冰箱，不并行开发淘宝。
- 完整线上部署不属于本轮 MVP。

## 3. 预计工作量

在单人全职开发前提下，当前预计为 8～11 人周。该数字不是固定工期；必须在第一阶段完成京东真实页面验证后重新估算。

| 阶段 | 预计工作量 | 是否为停止门 |
| --- | ---: | --- |
| 0. 验收范围冻结 | 2～3 天 | 否 |
| 1. 三项可行性验证 | 1～2 周 | 是 |
| 2. 项目与流水线骨架 | 1～1.5 周 | 否 |
| 3. 京东－冰箱搜集板块 | 1.5～2 周 | 是 |
| 4. 知识库加工厂 MVP | 2～3 周 | 是 |
| 5. 知识包与 Runtime | 1～1.5 周 | 是 |
| 6. 联调、评测与交付 | 1～1.5 周 | 是 |

## 4. 阶段 0：冻结验收范围

### 目标

把“冰箱调研”变成可执行、可验收的范围，避免开发过程中不断改变字段和样本。

### 主要工作

- 生成冰箱品牌候选清单；
- 生成产品类型、用户场景和参数矩阵；
- 生成购物引导 Agent 的典型问题集；
- 确定不少于 5 个品牌、50 个有效商品型号的验收集；
- 特意加入多规格、促销、缺货/下架、图片参数和异常页面样本；
- 冻结核心字段抽检规则和评测问题。

### 阶段产物

- 已确认研究范围；
- MVP 验收集；
- 核心字段与 Agent 问题集；
- 明确不采集的内容清单。

## 5. 阶段 1：三项可行性验证

这一阶段只做小规模纵向原型，不建设完整平台。

### 验证 A：京东真实页面

验证用户本地登录、候选发现、详情页、多规格、图片资料、价格状态、验证码/限流和下架页面是否能被可靠识别和保存。

通过条件：至少 20 个有代表性的页面完成原始资料保存；失败和人工接管状态可见；不能出现“空内容但标记成功”。

### 验证 B：混乱资料加工

从验证 A 的真实资料中选择样本，完成：

- 候选属性发现；
- 结构化抽取；
- 单位和表达标准化；
- 型号/规格对象识别；
- 冲突与低置信度审核；
- 来源证据返回。

通过条件：核心字段人工抽检准确率达到 90% 以上，并能说明错误来自页面、规则还是模型。

### 验证 C：知识包与查询

把验证 B 的结果制作成候选知识包，在无模型、无网络环境下完成精确查询、条件筛选、全文搜索和证据查看。

通过条件：知识包可复制到另一台机器加载；Runtime 不依赖向量数据库或查询 embedding。

### 停止规则

三项验证有一项不通过，暂停平台化开发，先调整范围或候选技术。不得用“后面再解决”跳过核心风险。

## 6. 阶段 2：项目与流水线骨架

### 目标

把验证原型变成可管理的连续任务，而不是散落脚本。

### 主要能力

- 创建知识项目；
- 保存目标 Agent 和已确认范围；
- 创建并运行一次任务流水线；
- 显示阶段、任务、进度、错误和待人工事项；
- 支持暂停、恢复、重试和版本记录；
- 区分原始资料、加工结果、审核结果和知识包版本。

### 通过条件

人为终止一次运行后能够继续；已完成的原始资料不会被覆盖或无意义重复抓取。

## 7. 阶段 3：京东－冰箱数据搜集板块

### 目标

达到 Provider 产品规范和 PRD 验收集要求。

### 主要能力

- 管理“京东－冰箱”板块范围和启停状态；
- 本地登录检查和人工接管；
- 候选资料发现、去重和覆盖统计；
- 原始资料保存及来源上下文；
- 正常、多规格、促销、缺货/下架和异常页面处理；
- 失败重试、部分完成提示和页面变化预警；
- 基于上次运行进行增量采集。

### 通过条件

PRD 验收集中，当时可访问页面的原始资料保存成功率达到 90%；所有未成功项均可解释和重试。

## 8. 阶段 4：知识库加工厂 MVP

### 目标

将真实、混乱的京东原始资料稳定加工为可审核知识。

### 主要能力

- 根据 Agent 目标生成并维护领域知识范围；
- 确定性解析与规则处理；
- 必要的模型抽取、图片理解和候选判断；
- 属性、单位、枚举和别名标准化；
- 品牌、型号、规格和 Offer 对象识别；
- 重复对象合并和冲突检测；
- 低置信度与异常审核；
- 原始值、标准值、推断状态和证据保留；
- 使用旧原始资料重新加工并生成新版本。

### 通过条件

- 已发布候选知识的来源可追溯率达到 100%；
- 核心字段人工抽检准确率达到 95%；
- 模型结果未经校验不能进入已确认知识；
- 冲突和无法判断项不会被静默填充。

## 9. 阶段 5：知识包与 Runtime

### 目标

把加工结果变成独立于生产环境的 Agent 交付物。

### 主要能力

- 构建只读、版本化知识包；
- 表达领域、来源范围、能力和质量状态；
- 支持精确查询、筛选、全文搜索、对象关联和证据查看；
- 在本地加载、激活、切换和回滚；
- 提供一个 Node/TypeScript Agent 接入演示；
- Runtime 查询不调用模型和 embedding。

### 通过条件

知识包复制到另一台机器后仍可加载和查询；旧版本可以安全回滚；通用 Runtime 中不存在商品专用固定接口。

## 10. 阶段 6：联调、评测与交付

### 主要工作

- 使用完整验收集从头运行流水线；
- 模拟中断、登录过期、验证码、页面异常和模型失败；
- 运行购物引导 Agent 问题集；
- 检查覆盖率、准确率、证据、性能和资源使用；
- 整理已知缺口、操作手册和后续维护事项；
- 冻结 MVP 版本。

### 最终通过条件

- PRD 第 10 节全部通过；
- Agent 任务集通过率不低于 90%；
- 严重缺陷为 0；
- 用户可以独立完成登录接管、任务恢复、冲突审核、建包和版本切换；
- 已知缺口和未覆盖范围明确记录。

## 11. 风险与处理

| 风险 | 处理方式 | 触发停止条件 |
| --- | --- | --- |
| 京东风控或页面变化 | 低速运行、人工接管、真实页面验证、维护状态 | 无法稳定保存代表性详情资料 |
| 资料字段分散在图片或动态区域 | 保存证据，必要时模型/OCR，保留人工审核 | 核心字段准确率持续低于门槛 |
| “全部型号”无法证明 | 以用户确认范围和覆盖报告验收，不声称绝对完整 | 无法解释遗漏来源 |
| 模型输出不稳定 | Schema 校验、证据、置信度和人工否决 | 推断值无法与事实区分 |
| AutoPKG 无法直接使用 | 只借鉴思想，小样本复现关键处理 | 因其 GPU/ODPS 前提阻塞本地 MVP |
| 知识包设计过早固化 | 先做两轮原型再冻结详细格式 | 格式写死商品概念 |
| 平台化投入过早 | 先完成三项可行性验证 | 纵向闭环未通过却开始大规模 UI |

## 12. 人员责任

| 角色 | 主要责任 |
| --- | --- |
| 产品负责人 | 确认范围、优先级、验收集、人工审核和发布决定 |
| 主工程师 | 可行性验证、总体实现、测试和详细设计 |
| 领域审核者 | 检查冰箱属性、对象合并和 Agent 问题答案；MVP 可由产品负责人承担 |
| Agent 接入者 | 验证知识包和 Runtime 是否真正可被 Agent 使用；MVP 可由主工程师承担 |

## 13. 工程团队必须补充的文档

开始正式编码后，由工程团队维护：

- 详细架构和 ADR；
- Provider 技术接口与契约测试；
- 原始资料格式；
- 知识 Schema 与迁移规则；
- Runtime API；
- 安全与隐私方案；
- 测试计划和运维手册。

这些工程文档可以细化实现，但不得反向修改 PRD 的产品目标和边界；如需改变，必须先形成产品变更决定。

## 14. MVP 之后

1. 增加淘宝 Provider 与“淘宝－冰箱”板块；
2. 验证京东和淘宝两个板块汇入同一冰箱知识项目；
3. 建设线上知识包管理、轻量 Runtime 和板块维护信息；
4. 再选择一个非商品领域验证通用性；
5. 根据真实查询缺口决定是否增加可选语义检索，而不是预先引入向量基础设施。
