# Agent 知识生产平台 MVP 实施计划

版本：V1.4
实施目标：官方来源冰箱端到端闭环＋第二商品品类迁移门

## 1. 实施原则

MVP 不是先搭一个“万能平台”，也不是给冰箱定制一套系统；而是用冰箱跑通完整纵向链路，并用第二商品品类小样本证明切换只改数据定义。

实施顺序必须是：

```text
品类启动采访与任务书确认
  → 知识需求与来源授权
  → 目的驱动访问与最小证据闭环
  → 最小知识加工闭环
  → 最小知识包与 Agent 查询
  → 第二品类零 Schema 迁移验证
  → 再补任务管理和完整验收
```

如果获准官方来源、混乱数据加工或轻量知识包中任一环节不可行，不应继续投入平台 UI 和通用插件框架。

## 2. 交付假设

- 首版由一名主工程师负责 Node/TypeScript 主体，可借助 AI 编程工具，但关键设计和验收由人确认。
- 用户担任产品负责人和知识范围审核者。
- 用户本机已经安装并登录 Codex CLI；MVP 复用该登录，不要求另备模型 API Key 或本地推理服务。
- 采集、清洗、评测和建包均在本地电脑执行。
- Codex CLI 任务必须限定工作目录、权限和输入；Cookie、认证 Header 与浏览器 Profile 不进入任务上下文。
- MVP 完整建设冰箱；第二品类只做结构迁移小样本，不并行建设完整知识资产。
- 冰箱事实来源只纳入品牌官网/说明书、获得访问授权的平台官方渠道和监管/标准资料，普通第三方商家排除；普通用户账号登录和公开可见不构成自动采集授权。
- 完整线上部署不属于本轮 MVP。
- 用户只在批次级确认知识范围、证据政策、例外和发布；不逐字段排网页。人工频次由真实样本中 `unknown/conflict/insufficient` 比例实测，未测前不得承诺固定次数。
- 品类启动从 Workbench Chat Timeline 开始；专用品类采访 Skill 一次一问，现有完整表单只负责回顾和修改结果。
- 交互式采访已接受 `assistant-ui` ExternalStoreRuntime＋官方稳定 `codex exec --ephemeral`；Workbench 拥有全部继续上下文。批次候选加工同样通过窄用途 ephemeral CLI adapter 执行，不使用 App Server/SDK thread。首版不引入 Pi Agent，技术接受状态以 R-028/R-029 为准。

## 4. 阶段 0I：品类启动采访与调研任务书

### 目标

让用户从一句“开启冰箱品类”开始，通过可恢复的一次一问采访得到可执行、可审核的品类调研任务书，而不是从零填写品牌、属性、部件、原理或来源清单。

### 主要工作

- 在当前 React/Vite/Tailwind Web 中验证 `assistant-ui` primitives 和 ExternalStoreRuntime，不接 Assistant Cloud；
- 在本地后端以 `codex exec --ephemeral --json --output-schema` 验证无状态单轮、typed 事件、取消、错误、显式 Skill、搜索完成门和全局 Session 零新增；
- 创建仓库专用 `interview-product-category` Skill，规定一次一问、主动调查、推荐理由、完成判断和任务书输出；
- 建立采访会话、标准化消息、Interview Decision、未决事项和 Category Research Brief 的 typed contract 与单一事实源；
- 将任务书确认结果投影为 Product Project 草稿；现有大表单只负责检查和修改；
- 用真实“开启冰箱品类”完成桌面和移动宽度验收，并证明中断后可以继续。

### 通过条件

- 用户无需填写品牌、型号、参数、部件、原理和来源列表，Agent 能调查后生成任务书；
- 模型建议不能直接成为决定，只有用户确认生成追加式 Interview Decision 和 confirmed brief；
- Browser、Workbench、Codex 执行、Skill 和表单没有重复事实源；
- 不引入 Pi、模型 registry、跨 Provider fallback、自写 JSONL/进程管理或 Assistant Cloud；
- UI 或 ephemeral CLI adapter 若不能满足本地、React 18、恢复、typed stream、取消、Session 隔离和退出成本，必须重新打开 R-028/R-029 调研，不在失败原型上叠 wrapper。
- 旧 App Server/SDK thread 路径已因全局 Session 污染和成熟度边界拒绝；除非官方能力或产品约束变化，不得重启该路径。

### 阶段产物

- 可恢复的品类采访会话；
- 已确认 Category Research Brief；
- 可由下一阶段读取的项目草稿和验收输入；
- R-028/R-029 的压缩证据记录与接受/拒绝结论；生产实现和测试是当前验收事实。

## 5. 阶段 0：冻结验收范围

### 目标

把“冰箱调研”变成可执行、可验收的范围，避免开发过程中不断改变字段和样本。

### 主要工作

- 根据 R-010 生成可审计的主流品牌/型号总体；
- 生成产品类型、用户场景和参数矩阵；
- 生成专业商品知识的能力问题集；
- 根据 R-008 的数据化品类知识定义和 R-010/R-011 的覆盖与统计目标生成版本化验收集，不预设无依据的数量或百分比；
- 特意加入多规格、促销、缺货/下架、图片参数和异常页面样本；
- 冻结规格、功能、机制、适用条件、取舍和决策维度的抽检规则与能力问题；
- 选定一个第二品类迁移样本，只验证结构迁移成本，不假装完成该品类知识研究。

### 阶段产物

- 已确认研究范围；
- MVP 验收集；
- 核心知识层与能力问题集；
- 明确不采集的内容清单。

## 6. 阶段 1：四项可行性验证

这一阶段只做小规模纵向原型，不建设完整平台。

### 验证 A：目的驱动来源访问与最小证据

用已确认知识需求生成 EvidenceRequest，验证品牌官网/说明书、监管数据和京东网页的候选发现、最小证据、时点状态、异常状态和敏感数据隔离。至少覆盖三个品类、每类两个布局不同的官方站点，以及 HTML、PDF、XLSX 和图片；不允许增加站点/品牌/品类 DOM 分支。京东只复用成熟 Patchright＋Crawlee 的访问与状态能力；淘宝只登记为下一来源。

通过条件：代表性请求均产生可复核的 EvidenceItem 或明确 `insufficient/unknown/failed/waiting`；整页内容只在临时区存在并完成清理；同页多图关系不明时拒绝自动入证据；不能出现“访问成功/空内容但标记证据充分”。

### 验证 B：混乱资料加工

从验证 A 的真实最小证据中选择样本，完成：

- 候选属性发现；
- 结构化抽取；
- 单位和表达标准化；
- 型号/规格对象识别；
- 冲突与低置信度审核；
- 来源证据返回。
- 统计需要人工的请求/候选比例、原因和批次处理量，证明不会按字段逐条打断整个运行。

通过条件：核心知识层质量达到随原型冻结的统计门槛，并能说明错误来自页面、规则还是 Codex；具体置信度、允许误差和样本量由 R-010/R-011 给出依据。

### 验证 C：知识包与查询

把验证 B 的结果制作成候选知识包，在无模型、无网络环境下完成精确查询、条件筛选、全文搜索和证据查看。

通过条件：知识包可复制到另一台机器加载；Runtime 不依赖向量数据库或查询 embedding。

### 验证 D：第二品类迁移门

选择电视或微波炉的小型官方资料样本，复用同一商品知识模型、Provider contract、加工流程、包结构和 Runtime。只新增版本化品类知识定义、来源范围和评测数据。

通过条件：生产 Schema、数据库结构、通用模块 interface、Runtime API 和同来源 Provider 实现零修改；如需新增品类类或通用流程分支，立即停止并返回架构设计。

### 停止规则

四项验证有一项不通过，暂停平台化开发，先调整范围或候选技术。不得用“后面再解决”跳过核心风险。

## 7. 阶段 2：项目与流水线骨架

### 目标

把通过纠偏门的验证原型变成可管理的连续任务，而不是散落脚本。既有 Product/Pipeline 骨架可复用，但不得把旧 Raw Material/Snapshot contract 当成阶段通过证据。

### 主要能力

- 创建知识项目；
- 保存品类、市场、用途说明、品类知识定义版本和已确认范围；
- 创建并运行一次任务流水线；
- 显示阶段、任务、进度、错误和待人工事项；
- 支持暂停、恢复、重试和版本记录；
- 区分 EvidenceRequest、SourceObservation、EvidenceItem、加工结果、审核结果和知识包版本。

### 通过条件

人为终止一次运行后能够继续；已提交的最小证据不会被覆盖或无意义重复采集，临时完整内容不会残留。

## 8. 阶段 3：官方来源－冰箱数据搜集板块

状态：原“已通过”结论于 2026-08-15 撤销。旧实现证明了来源访问、状态识别、内容寻址和任务恢复等局部能力，但整页快照/DOM projector 违背新的目的驱动最小证据基线，且生产组合根不可达。必须先重新通过阶段 1A/1B，才能按新 contract 重做本阶段。

### 目标

达到 Provider 产品规范和 PRD 验收集要求。

### 主要能力

- 管理品牌官网/说明书、监管数据和已确认教育研究平台网页板块的范围、来源依据和启停状态；
- 检查公开入口或本地专用网页会话，登录失效或需要验证时暂停并由用户接管；
- EvidenceRequest 生成、候选来源发现、去重和覆盖统计；
- SourceObservation 与最小 EvidenceItem 保存；
- 正常、多规格、促销、缺货/下架和异常页面处理；
- 失败重试、部分完成提示和页面变化预警；
- 基于上次运行进行增量采集。

### 通过条件

PRD 验收集中，计划证据请求达到 R-010/R-011 冻结的充分性门槛；所有不足、未知、失败和待人工项均可解释和重试。生产入口必须真实可达，不得只由测试注入 handler。

## 9. 阶段 4：商品知识加工厂 MVP

### 目标

将真实、混乱的获准最小证据稳定加工为可审核知识。

状态：旧的参数纵切片、DOM projector 和测试接线不构成本阶段通过；在新的 EvidenceItem contract、共享商品模型/属性字典和生产入口完成前保持未通过。

### 主要能力

- 根据品类、市场和用途说明生成并维护专业商品知识范围；
- 确定性解析与规则处理；
- 必要的模型抽取、图片理解和候选判断；
- 属性、单位、枚举和别名标准化；
- 品牌、型号、规格和 Offer 对象识别；
- 重复对象合并和冲突检测；
- 低置信度与异常审核；
- 证据原文/像素、标准值、推断状态和证据保留；
- 功能、机制、适用条件、取舍、需求映射和比较维度进入结构化知识层；
- 使用旧最小证据重新加工其已支持的问题并生成新版本。

### 通过条件

- 已发布候选知识的来源可追溯率达到 100%；
- 核心知识层人工抽检达到 R-010/R-011 冻结的统计质量门槛；
- 模型结果未经校验不能进入已确认知识；
- 冲突和无法判断项不会被静默填充。

## 10. 阶段 5：知识包与 Runtime

### 目标

把加工结果变成独立于生产环境的 Agent 交付物。

### 主要能力

- 构建只读、版本化知识包；
- 表达领域、来源范围、能力和质量状态；
- 支持精确查询、筛选、全文搜索、对象关联和证据查看；
- 在本地加载、激活、切换和回滚；
- 提供一个 Node/TypeScript Agent 接入演示；
- Runtime 查询不调用模型和 embedding。

### 通过条件

知识包复制到另一台机器后仍可加载和查询；旧版本可以安全回滚；通用 Runtime 中不存在商品专用固定接口。

## 11. 阶段 6：联调、评测与交付

### 主要工作

- 使用完整验收集从头运行流水线；
- 模拟中断、授权过期、页面/API 异常和模型失败；
- 运行购物引导 Agent 问题集；
- 检查覆盖率、准确率、证据、性能和资源使用；
- 整理已知缺口、操作手册和后续维护事项；
- 冻结 MVP 版本。

### 最终通过条件

- PRD 第 10 节全部通过；
- 能力问题和下游任务集达到 R-011 冻结的通过门；
- 不存在按版本化发布策略定义的未解决阻断项；
- 用户可以独立完成授权恢复、任务恢复、冲突审核、建包和版本切换；
- 已知缺口和未覆盖范围明确记录。

## 12. 风险与处理

| 风险 | 处理方式 | 触发停止条件 |
| --- | --- | --- |
| Chat UI 或 Agent runtime 重复造轮子 | 先验证 assistant-ui 与 Codex App Server，Workbench 只保留产品 contract 和薄 adapter | 需要自写通用 Chat runtime、Agent loop、会话协议或同时维护 Pi/Codex 双状态 |
| 平台页面、登录或风控变化 | 固定官方店铺白名单、专用 Profile、并发 1、无默认重试；Patchright/Crawlee 版本化 | 需要自研反检测、自动解验证码、切换账号或采集账户/订单资料 |
| 证据藏在图片或动态区域 | 先证明图片与对象/知识点关系，再按最小区域保存；OCR/模型只生成候选 | 无法证明关系、错误关联或核心准确率持续低于门槛 |
| 未知 DOM 导致逐站解析器膨胀 | 用 EvidenceRequest 驱动候选寻找，跨站点真实样本禁止站点/品牌/品类 DOM 分支 | 必须为每个官网或品类维护字段 projector |
| “主流型号总体”无法证明 | 先完成 R-010，多来源估计仍不可靠时报告未知并停下确认 | 无法解释总体与遗漏来源 |
| 模型输出不稳定 | Schema 校验、证据、置信度和人工否决 | 推断值无法与事实区分 |
| AutoPKG 无法直接使用 | 只借鉴思想，小样本复现关键处理 | 因其 GPU/ODPS 前提阻塞本地 MVP |
| 知识包设计过早固化 | 先做两轮原型再冻结详细格式 | 格式写死冰箱或某个下游 Agent |
| 平台化投入过早 | 先完成四项可行性验证 | 纵向闭环或跨品类迁移门未通过却开始大规模 UI |

## 14. 工程团队必须补充的文档

开始正式编码后，由工程团队维护：

- 详细架构和 ADR；
- Provider 技术接口与契约测试；
- EvidenceRequest、SourceObservation、EvidenceItem 格式；
- 知识 Schema 与迁移规则；
- Runtime API；
- 安全与隐私方案；

这些工程文档可以细化实现，但不得反向修改 PRD 的产品目标和边界；如需改变，必须先形成产品变更决定。

## 15. MVP 之后

1. 完整建设通过迁移门的第二商品品类；
2. 根据覆盖缺口决定是否增加新的官方来源 Provider，而不是先增加普通卖家；
3. 建设线上知识包管理、轻量 Runtime 和板块维护信息；
4. 根据真实查询缺口决定是否增加可选语义检索，而不是预先引入向量基础设施；
5. 是否扩展到非商品领域另立产品调研，不从商品 MVP 自动推出。
