## 简单说明

这次证明了已交付的系统可以在负责人执行一次正式 Start 后自行运行并结束：没有在运行中改代码，也没有人工逐条 Resume。它没有证明这份新 Batch 的资料已经可以作为阶段 1 的完整合格输入，因为商品目录覆盖投影仍为缺口、13 个型号需要关注，且 6 个公开来源被既有安全 gate 如实阻止。

### 2. 原始数据质量：未通过完整门

- ZOL 有 11 个型号资源在一次复核后仍为 HTTP 404，另有 2 个型号因可信 DoH 查询 `DNS status 2` 进入需关注；相关 DNS 图片工作项另有 3 项失败。它们不能被重写为“来源无图”，也不能从 247 的计划型号分母中删除。
- 6 个公开来源在本次开始前已被对应 origin 的持久安全 gate 阻止，因此各自以 0 Snapshot 终态。这是失败关闭，不是系统跳过或绕过访问限制；其余 14 个公开来源仍完成并保存原始内容。

## 404 与失败审计

ZOL Run 共保存 3,475 个 Snapshot、2,708 个 Asset；3,731 个 Work Item 中 3,715 个完成、16 个失败。请求账本中：

- 86 个 exact URL 出现 `404 -> 200`：一次 ZOL HTML 有界复核恢复了这些可访问页面；旧实现会把它们过早记为失败。
- 11 个 exact URL 出现 `404 -> 404`：达到两次上限后保留最终 `not_found` Snapshot 和对应型号问题。
- 6 次 HTTP 403 与 15 次无 HTTP 状态的传输失败都保留在审计；最终没有打开的 ZOL access gate。

由此可以确认，先前的主要问题不是规划阶段没有给够来源，也不是把 URL 分片公式整体写错；关键是将 ZOL HTML 的偶发 404 当成第一次即终态，以及失败作用域曾被放大。P0 修复已经用真实 Batch 证明前者得到显著改善、后者没有阻断后续工作。剩下的持续 404 与 DNS 失败仍是具体来源事实或传输问题，不能由增加重试次数推断为成功。
