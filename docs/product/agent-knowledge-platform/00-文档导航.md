# Agent 知识生产平台文档导航

版本：V1.1

## 1. 文档组成

| 文档 | 负责决定什么 | 明确不决定什么 |
| --- | --- | --- |
| 《产品需求文档 PRD》 | 用户、问题、产品流程、功能范围、MVP 和验收 | 函数、表、目录和技术实现 |
| 《总体技术方案》 | 系统边界、模块关系、数据流、部署边界和候选开源基础 | 详细接口与数据结构 |
| 《Provider 接口规范（产品级）》 | Provider 为什么存在、来源授权、来源接入责任和验收 | 函数签名、选择器、队列实现 |
| 《知识包格式规范（产品级）》 | 知识包为什么存在、产品分层、Agent 使用方式和验收 | 文件目录、数据库表、索引格式 |
| 《MVP 实施计划》 | 实施顺序、阶段产物、停止门、工作量、风险和交付标准 | 具体代码任务和工程排期承诺 |

## 2. 文档权威顺序

发生冲突时按以下顺序处理：

1. PRD 的产品目标、范围和验收；
2. 总体技术方案的系统边界；
3. Provider 与知识包产品级规范；
4. MVP 实施计划；
5. 后续由工程团队编写的详细设计。

工程详细设计不能为了实现方便取消本地执行、证据追溯、跨品类低成本迁移、知识包可携带或无强制 embedding 等产品要求。

## 3. 当前统一结论

- 当前产品面向专业商品知识生产，知识资产可被多个 Agent、Skill 或应用复用，不围绕单一导购 Agent 建模。
- 所有商品品类共用稳定商品知识模型和共享属性字典；品类差异是版本化数据，不是冰箱/电视专用 Schema 或代码模板。
- 多个官方数据搜集板块向同一个商品知识加工厂提供原始资料。
- Provider 是来源接入能力；品牌官网、监管数据或京东网页采集 Provider 与冰箱范围组合后才是数据搜集板块。
- MVP 完整建设冰箱，并用第二商品品类小样本通过迁移门；普通第三方和小型商家不在首轮范围。
- 采集、清洗、Codex 加工、审核、评测和建包只在本地 Workbench 发起和控制；MVP 复用用户本机已登录的 Codex CLI，不要求另备模型 API 或本地推理服务。
- 后续线上只部署维护信息、知识包管理、轻量 Runtime、权限与审计。
- 原始资料可能混乱，知识加工采用规则、模型、校验和人工审核协作。
- 知识包可承载商品品类知识；Runtime 不绑定冰箱、具体品类或具体 Agent。
- Runtime 默认不需要模型、向量数据库或查询 embedding。
- AutoPKG 只作为购物领域知识加工的思想和实验参考，不作为平台底座。

## 4. 工程接手后的下一步

工程师应先执行《MVP 实施计划》的四项可行性验证，包括第二商品品类迁移门，再补充 Provider 技术接口、原始资料格式、稳定商品知识 Schema、Runtime API 和安全方案。验证前不冻结详细表结构和插件机制。
