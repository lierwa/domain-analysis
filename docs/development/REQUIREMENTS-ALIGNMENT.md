# MVP 需求逐项确认记录

## 访谈规则

- 用户已要求剩余问题每 8 个一组，以该要求覆盖技能默认的单题节奏。
- 能从代码、真实运行或官方资料查到的事实不反问用户。
- 每项推荐必须给出调查依据；不能让用户替系统发明品类字段、品牌数量、抽样数字或技术方案。
- 每个重要问题同时给出简单说明与专业设计；简单表达不降低设计深度。
- 领域术语确认后立即更新根目录 `CONTEXT.md`。
- 固定问题树共 18 个主问题；新矛盾只能拆分已有问题，不能暗中增加用户决策负担。

## 已确认结果

### Q001 MVP 成功终点

状态：已确认（2026-08-13）

确认结果：本地 Workbench 从已确认知识需求出发，目的驱动访问官方来源并保存最小证据，经可恢复加工、必要的 Codex 候选、人工审核与评测，产出证据可追溯、版本化、可复制并能被 Runtime/SDK 查询的商品知识包。冰箱是首个纵向验证品类，不是系统边界。

### Q002 核心用户

状态：已确认（2026-08-14）

确认结果：MVP 是单机单用户产品，用户本人承担知识项目负责人和数据维护者；不建设团队协作、多用户或权限系统。

### Q003 项目启动入口

状态：已确认（2026-08-15），技术实现待真实原型

简单说明：用户只需说“开启冰箱品类”。系统通过一个专用品类采访 Agent 一次问一个问题；能自行调查的品牌、型号、参数、部件、原理和来源不反问用户，最后给用户确认一份《品类调研任务书》。

确认结果：项目围绕可复用的商品知识资产创建，不围绕单一“目标 Agent”创建。正式入口必须是本地 Workbench 的 Chat Timeline，不是要求用户从零填写完整表单。专用品类采访 Skill 规定一次一问、推荐理由、主动调查、完成判断和任务书输出；Workbench 保存标准化消息、负责人决定、状态和任务书版本。结构化表单只负责回顾与修订采访结果。任务书确认后才进入品类范围调查、批量资料收集和后续加工。

用户进一步确认的实现方向：Chat Timeline 优先复用成熟开源 UI；本地后端接入 Codex CLI 的交互能力；首版不再叠加 Pi Agent。R-028/R-029 当前接受 `assistant-ui` ExternalStoreRuntime＋锁定版本的 App Server `stdio`，每轮使用 `thread/start(ephemeral:true)` 获取官方文字 delta；拒绝持久 App Server/SDK thread、resume 和第二套产品会话事实源。当前事实以生产实现、RESEARCH 与 PROGRESS 为准。

### Q004 跨品类知识模型

状态：已确认（2026-08-14）

简单说明：我们建设的是一台“商品知识生产机”，冰箱、电视、微波炉只是不同原料。换品类时换数据定义和来源清单，不换机器。

确认结果：采用一套稳定的商品知识模型与共享属性字典；品类差异以版本化 `Category Knowledge Definition` 数据表达。切换品类不得新增生产 Schema、数据库表/列、TypeScript 类、Runtime API、通用流程分支或同来源的新 Provider 实现。冰箱完整 MVP 冻结架构前，必须用第二品类小样本通过品类迁移门。

后续确认（2026-08-17）：商品知识资产必须同时包含“商品底层知识”和“商品品类知识”。底层知识解释原理、部件、作用链、条件、边界、取舍和失效，不依附品牌/型号；品类知识把适用底层知识组织为品类标准、技术路线、功能/指标、比较/需求知识，并包含目标市场的品牌、系列、型号和变体。品牌＋型号目录不是完整品类知识，更不是商品底层知识。

调查依据：Schema.org 支持通用产品属性；Akeneo Family 通过共享属性集合组织品类；Pimcore Classification Store 可在不改变产品类定义时承载动态品类属性。详细证据见 R-008 和 ADR-0002。

### Q007 首轮来源边界

状态：已确认（2026-08-14）

简单说明：不是把京东所有卖家都抓一遍，而是找到足以代表市面主流型号的官方资料。普通第三方、小店和重复卖家没有进入首轮的必要。

确认结果：事实层只接受品牌官网、官方产品资料/说明书、平台官方自营、经核实的品牌官方旗舰店以及监管或标准来源。普通第三方和小型商家排除。多个官方渠道用于补齐、验证或发现冲突，不以卖家数量作为覆盖指标。价格与库存仍按官方销售要约和采集时点单独记录。

后续决定（2026-08-14）：官方规则调研作为风险证据保留；用户明确选择教育研究用途的京东网页采集，不走京东官方 API。京东仍只采官方自营或经核实旗舰店，不扩到普通第三方店铺；技术上只组装成熟开源能力，不自研反检测、验证码或账号切换。ADR-0004 已取代 ADR-0003。淘宝在京东闭环后单独调研。

后续确认（2026-08-17）：京东来源不是预设少量字段的型号发现器。其首要产物包括京东冰箱分类/筛选体系、国内外品牌自营及经核实官方旗舰店目录、每款商品详情区的全部公开参数与图文、以及每款商品的评价汇总和前 50/100 条代表性评价。第一轮先保留来源原始结构，再从真实数据归纳类型、属性、比较维度、型号总体和用户痛点；最小证据是后续知识加工产物，不能反向删除来源数据集。详细方案见 `JD-COLLECTION-DESIGN.md`。用户已授权按方案开始开发；技术 interface、数据结构、依赖和测试策略由工程负责，R-031 已按 ADR-0014 冻结并通过冰箱＋电视本地纵切片，不再作为产品负责人确认题。真实京东访问仍受第 9.1 节完整频控硬门约束。

同日补充：京东、官网商品页和评价主要承担市场/型号事实、品牌声明和用户体验来源，不能单独证明压缩机、制冷、换热、控温或保鲜等通用原理。底层知识必须另由标准、监管/科研、权威技术、核心部件和经核验品牌技术资料补证；具体白名单、许可和质量门进入 R-030 调研，不能凭产品确认直接冻结实现。

## 第二批确认前的调研背景

### Q005 主流品牌/型号覆盖口径

用户已确认的目标：数据要支撑目标市场中某品类的大多数主流品牌和型号，不追求每个卖家或无法证明的全网全量。

确认前待解决：目标市场的边界、可作为品牌/型号总体的权威清单、在售/历史型号窗口、主流判定方式和可报告覆盖率。系统必须通过 R-010 找到可审计总体或给出多来源估计方法，不能让用户拍一个数量。

第一轮调查结论：将监管备案作为合规身份台账，将品牌官网/说明书、官方自营和核实后的官方旗舰店在同一快照窗口的并集作为“官方在售总体”；没有许可证清晰的市场份额数据时，只承诺并报告官方在售总体覆盖，不宣称销量加权覆盖。

### Q006 专业能力与质量验收

用户已确认的价值目标：知识资产必须覆盖配置参数、功能、技术机制、适用条件、使用取舍、需求映射、参数对比、来源证据和时效信息，使下游专业导购能够主动澄清需求、解释功能并比较型号。差异化来自清洗后的专业数据，而不是通用模型的聊天能力。

2026-08-17 进一步确认：质量报告必须分别检查来源数据、商品底层知识、商品品类知识、型号知识和发布知识。底层原理没有权威证据、品类只有品牌/型号目录、型号机制关系只有营销声明，均不得以型号数、参数数或 EvidenceItem 数量掩盖为完成。

确认前待解决：每层知识的完整度、准确率、冲突率、能力问题规模及统计抽检门槛。R-010/R-011 必须从真实官方资料、下游任务和成熟评测方法派生指标；不得恢复“5 个品牌、50 个型号”或无依据固定准确率。

第一轮调查结论：发布门分层而不是只给一个“准确率”。结构、证据、身份一致性、知识层完整性、时效/冲突是确定性硬门；检索能力和专业导购任务使用版本化用例集；模型评分只作补充。具体工具仍需隔离比较，不会先装依赖或升级 Node。

## 第二批已确认结果（Q005、Q006、Q008～Q013）

用户于 2026-08-14 一次确认 8 项全部选择 A。以下保留当时的 A/B 取舍作为决策审计；这只确认产品行为，不自动决定 Schema、数据库、浏览器库、评测库或统计实现。

### Q005 覆盖口径

状态：已确认（2026-08-14，选择 A）

- **A（推荐）**：监管备案做合规身份台账；品牌官网/说明书、官方自营和核实后的官方旗舰店在同一快照窗口的并集做官方在售总体。系统报告品牌发现覆盖、在售型号发现覆盖和知识完整覆盖；只有取得许可清晰的市场份额数据后才报告销量加权覆盖。
- **B**：必须以销量加权“大多数”为验收门；在获得合规市场份额数据前项目保持阻塞。

简单说明：A 能诚实回答“官方在售型号我们覆盖了多少”；B 能回答“销量覆盖了多少”，但需要目前尚未取得的市场数据。

### Q006 质量验收

状态：已确认（2026-08-14，选择 A）

- **A（推荐）**：结构、证据、身份一致性、知识层完整性、时效和冲突是发布硬门；检索与专业导购能力使用版本化问题/任务集；模型评分只作补充。
- **B**：以一个总准确率作为主要发布门。

简单说明：A 能指出具体坏在哪一层并阻止脏知识发布；B 看起来简单，但一个平均数会掩盖缺证据、过期和错误合并。

### Q008 登录态使用

状态：已确认（2026-08-14，选择 A）

- **A（推荐）**：使用项目专用的本地浏览器 Profile，由用户手动登录；Cookie、认证 Header 和 Profile 不交给 Codex、不进日志、临时来源区、证据区或知识包；登录失效时暂停并提示用户恢复。
- **B**：只采无需登录即可访问的官方页面，遇到登录内容直接记为不可访问。

简单说明：A 能覆盖登录后官方自营页面，同时把账号控制权留在本机；B 更简单但会降低可见范围。

后续约束（2026-08-15 最小证据纠偏后）：京东使用项目专用 Profile 和用户现有人工登录，不读取密码、Cookie 或认证 Header；失效或验证码时暂停等用户。登录态整页只可在本机临时读取，不能进入持久快照；只有与 EvidenceRequest 相关、通过隐私和最小化门的 EvidenceItem 能进入候选加工。Cookie、Header、Profile 和无关个性化内容永远不是证据。

### Q009 商品身份分层

状态：已确认（2026-08-14，选择 A）

- **A（推荐）**：稳定厂商型号、销售变体/SKU、官方销售 Offer、不可变最小证据分层记录；同款判断不确定时保持两个候选并进入人工合并，不让 Codex 猜。
- **B**：一个商品页面就是一个商品，后续再做去重。

简单说明：A 不会把同一冰箱的颜色、渠道价格或页面更新时间误算成多个型号；B 初期快，但知识库很快会重复和串价。

### Q010 发布门

状态：已确认（2026-08-14，选择 A）

- **A（推荐）**：官方资料直接给出的事实和可重放的确定性转换可以自动进入发布候选；Codex 推断、来源冲突、缺少证据、身份合并和高风险知识必须人工确认；发布新知识包版本仍需一次明确批准。
- **B**：所有字段逐条人工确认后才可发布。

简单说明：A 让人工只处理机器不能可靠决定的例外；B 最保守，但主流型号规模下维护成本过高。

### Q011 人工审核范围

状态：已确认（2026-08-14，选择 A）

- **A（推荐）**：采用例外审核队列，只呈现推断、冲突、证据不足、异常值、模糊身份和品类定义变更，并保留审核理由；低风险确定性事实不逐条打扰用户。
- **B**：每个型号按完整表格统一审核。

简单说明：A 把时间花在真正有争议的知识上；B 容易形成大量机械点击。2026-08-15 进一步确认：例外不暂停其他独立任务，队列按 typed request/reason/source/evidence/category version 确定性筛选和批量处理，不另用 LLM 判断“同类”。

### Q012 证据边界

状态：已确认（2026-08-14，选择 A）

- **A（推荐）**：每条发布知识都必须指回官方来源对象、不可变最小证据、具体定位和采集时间；Runtime 默认返回简洁答案与证据引用，需要时再展开获准摘录。无证据只能保持 `unknown` 或待审核。
- **B**：只在型号级保存来源链接，具体字段和知识结论不强制定位。

简单说明：A 能回答“这句话从哪里来、当时来源片段写了什么”；B 数据量小，但发生冲突时无法追查。2026-08-15 的纠偏确认取代旧“保存整页快照”解释：文本保存 exact/context，文档保存页/片段，表格保存表头/行列范围，图片保存已证明关系的资源/区域；URL-only 不算证据，新问题缺上下文时重新采集。

### Q013 知识包交付与版本

状态：已确认（2026-08-14，选择 A）

- **A（推荐）**：知识包是不可变版本；Workbench 构建并批准新版本，独立只读 Runtime/SDK 加载指定版本或 `stable` 指针，支持校验、原子切换和回滚；多个 Agent/Skill 复用同一包。
- **B**：Agent 直接查询 Workbench 当前数据库，总是读取最新数据。

简单说明：A 让一次发布可复现、可回滚，也不会把冰箱导购和未来其他 Agent 绑死在采集系统上；B 实现表面直接，但在途清洗数据会影响线上回答。

## 最后一批已确认结果（Q014～Q018）

用户于 2026-08-14 确认本批 5 项全部选择 A。技术组件、具体性能数字和更新频率仍由真实原型派生；以下保留 A/B 取舍作为决策审计。

### Q014 Runtime 查询顺序

状态：已确认（2026-08-14，选择 A）

- **A（推荐）**：默认按型号/别名精确匹配、结构化筛选排序、全文关键词、对象关系和证据查看的顺序查询；语义/向量检索只在真实验收集证明存在缺口后作为可选增强，不能成为知识包或 Runtime 的必需依赖。
- **B**：第一版所有查询都先做 embedding 和向量检索。

简单说明：A 像查一份可靠的商品数据库，型号、参数和证据都能精确找到；B 像先“猜相似意思”，对精确型号和数字未必更好，还会增加模型、网络和向量库成本。

推荐依据：SQLite FTS5、Orama 等成熟方案已经覆盖离线全文检索；R-003 将用真实中文型号、别名和比较问题决定最终存储，不需要先假设向量搜索不可缺少。

### Q015 更新策略

状态：已确认（2026-08-14，选择 A）

- **A（推荐）**：不同知识按变化速度分别设置更新策略；稳定规格/机制低频复核，价格/库存等时点信息高频采集，人工也可触发。先做变化检测和影响评测，再生成新知识包版本；旧版本不原地覆盖。
- **B**：所有数据使用同一固定频率整库重抓，并直接覆盖当前结果。

简单说明：A 不会为了一个价格变化重做整座知识库，也不会让旧规格被悄悄改掉；B 操作概念简单，但浪费采集成本且难以追查变化。

推荐依据：已确认的不可变快照、知识包版本和 `stable` 指针要求更新可审计、可回滚；具体天数不能凭空规定，将由来源变化试采和业务风险计算。

### Q016 日常操作方式
