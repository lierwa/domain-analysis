# 标准商品数据抓取与清洗平台 PRD

版本：V2.0
更新日期：2026-08-20
当前实施范围：阶段 1 数据抓取

## 1. 产品目标

产品帮助负责人把“抓冰箱”“抓电视机”等自然语言需求，转化为专业、可审核、可执行的数据抓取任务，并从多个真实来源保存可查看、可导出的原始数据。

这些原始数据最终服务于专业导购 Agent：在同一商品门类内进行多品牌、多型号比较，并能用国家标准、测量口径、关键部件、技术路线和底层原理解释参数差异，而不是只复述两三个品牌页面。阶段 1 负责把足够且可追溯的原件抓回来；导购回答、参数标准化和知识加工仍属于后续阶段，不在当前运行链中提前实现。

负责人不需要预先掌握爬虫、网站结构或完整商品资料。系统负责调查标品边界、标准/监管资料、品牌和型号结构、平台分类以及候选来源，只把会实质改变任务结果、且必须由负责人承担的取舍拿出来讨论。

项目只分两个阶段：

1. 数据抓取：确认抓什么、从哪里抓、怎样抓，并保存不可变原始数据；
2. 数据清洗：未来基于原始数据做解析、去噪、标准化、合并和质量判断。

当前不实现阶段 2。

## 2. 商品范围

### 2.1 当前纳入：标准商品

标准商品是能够通过品牌、型号、规格、分类、国家/行业标准或其他稳定身份进行枚举和比较的商品。首批典型品类包括：

- 冰箱、电视机等家电；
- 手机、电脑、显示器等消费电子；
- 其他具有相对稳定型号、规格和市场分类的商品。

存在国标、监管备案、能效/认证或稳定行业分类时，系统必须主动调查并把它们用于确定品类边界和候选来源。

### 2.2 当前排除：非标准商品

手工制品、孤品、定制品、独一件艺术品以及主要依赖个体创作、无法用稳定型号/规格形成市场总体的商品，不进入当前产品范围。服务、内容和非商品对象也不在本阶段讨论。

边界不清时，Agent 先调查是否存在稳定商品身份和行业分类；只有该事实无法可靠判断时才向负责人解释并确认是否停止。

## 3. 用户角色

### 3.1 抓取任务负责人

用户本人承担抓取任务负责人。他不是专业抓取工程师，但需要理解系统为什么这样划定范围、为什么选择这些来源、哪些取舍会影响覆盖和成本，并对关键决定和最终任务草稿负责。

### 3.2 专业抓取任务顾问

采访 Agent 承担专业引导：

- 先调查，再提问；
- 给出专业判断、推荐答案、依据和主要代价；
- 一次只推进一个真实决定；
- 不把可以调查的品牌、型号、参数、标准和来源清单转嫁给用户；
- 不为满足“2–3 个互斥选项”的形式强行制造问题；
- 推荐项应代表当前证据下的专业默认答案，而不是为了平衡措辞给出随意选项。

## 4. 核心产品对象

| 对象 | 产品含义 |
| --- | --- |
| 抓取任务对话 | 用户与专业抓取任务顾问围绕一个标准商品范围进行的可恢复对话 |
| 采访决定 | 必须由负责人确认、会实质改变抓取结果的取舍 |
| 抓取任务草稿 | 对话形成、供人直接审阅的版本化 Markdown 范围说明；不是正式任务 schema |
| 抓取任务 | 用户确认 Markdown 后单独结构化的当前抓取范围事实源；确认不等于计划或执行 |
| 候选来源 | 从已确认采访事实结构化的来源入口；候选不等于已授权或已接入 |
| 抓取计划 | 面向一个已确认任务的完整执行清单；逐项冻结来源入口、正文/附件目标、数量、Provider 与停止口径 |
| Provider | 执行某一外部来源访问协议的能力，不决定产品范围 |
| 来源运行 | 一次正式抓取执行及其状态、计数和停止原因 |
| 来源数据集 | 一个任务下所有来源对象、观察、不可变快照和原始附件的集合 |

## 5. 平台与来源范围

系统目标是取得能够互相补充的多来源原始数据，而不是只依赖单一网站。候选来源通常包括：

- 国家标准、监管、能效、认证等官方来源；
- 品牌官网、产品目录和说明书；
- 主要电商平台的分类、筛选、品牌/店铺、商品详情、媒体、价格状态和评价；
- 必要的行业或专业技术来源。

一个面向专业导购 Agent 的标准商品任务，至少必须同时具备四类经过调查的具体入口：核心零售/市场平台、品牌官方参数/目录/说明书、标准或监管、权威技术原理。任一类缺失时只能继续系统调查，不能把任务或 Crawl Plan 标为完整；京东已经判定适用时，还必须存在具体京东入口。

平台是否属于某品类的必要数据资源，由系统根据商品销售与分类事实主动判断，不把每个平台改造成一道“是否纳入”的负责人问题。

对冰箱等家电：

- 京东是必须覆盖的核心平台来源，因为其分类、筛选、品牌/店铺和商品资料整合较完整；
- 淘宝是后续多平台来源，用于扩大和对照平台覆盖；
- 是否以及何时真实访问，仍必须分别通过许可、登录、频控、验证码、风控和 Crawl Plan 确认门。

系统可以解释为什么某平台重要，也允许负责人明确提出排除要求；但不得为了凑出相悖选项，默认先问“是否纳入京东”。

## 6. 用户主流程

1. 用户输入“抓冰箱”等需求。
2. Agent 先调查标品边界、标准/监管体系、市场分类、品牌/型号结构和候选来源。
3. Agent 用普通对话解释已知事实、推荐范围和原因。
4. 只有出现必须由负责人决定且会影响结果的真实取舍时，Agent 才一次提出一个问题，并给出 2–3 个可执行方案、唯一推荐项、推荐依据和代价。
5. 用户通过 Composer 发送任意自然语言。系统先保存原文，再结合当前问题、既有事实和草稿理解其中的回答、纠正、补充或追问；语义明确的负责人回答由 Workbench 校验后保存为 confirmed Interview Decision，不能把追问或含糊文本强行当成选择。
6. 消息、调查活动、用户事实、决定、未决项和草稿版本持续作为采访工作资料；没有负责人未决项后，系统综合这些依据生成版本化 Markdown 范围草案，采访回合不输出正式 Capture Task schema。
7. 用户可以继续对话修改，也可以整体确认。确认后系统以独立、不搜索、不增加事实的步骤生成正式 Capture Task，但不自动启动 Crawl Planning 或抓取。
8. 用户在任务页显式启动 Crawl Planning；Codex 可见地核实具体来源、内容和数量，生成版本化 Crawl Plan Draft。
9. 用户修改或确认计划；确认不会自动开始抓取。
10. 正式抓取在停止条件内运行，原始数据持久化后可在 Workbench 查看和导出。
11. 阶段 1 全部验收后，另行设计数据清洗。

## 7. Markdown 抓取范围草案必须说明

- 用户原始需求和标准商品边界；
- 目标市场和观察时间范围；
- 准备抓取的通用内容与品类特有内容；
- 需要覆盖的来源类别和主要平台；
- 本轮真实调查得到的候选入口及其观察层级；
- 明确排除项；
- 系统尚未查清的事实；
- 用户已经确认的决定。

草稿必须能追溯到同一对话保存的用户原文、调查说明和 confirmed Decision；这些工作资料用于继续理解和修订，但只有用户整体确认后的 Capture Task 才是当前正式范围事实。

草稿只用普通 Markdown 说明“准备抓什么、准备从哪里抓”，不输出 JSON、`taskCandidate/sourceCandidates/observedAt`，也不描述具体选择器、分页、频控、重试、清洗字段、Evidence 或知识 Schema。

## 8. 阶段 1 产品要求

- 对话可创建、暂停、刷新恢复、继续和删除未关联正式任务的记录；
- 消息、工具时间线、采访决定、未决项和草稿版本分别保存；
- 模型建议不能自行成为 confirmed Decision；
- 老草稿不覆盖，新确认版本保持同一 Capture Task ID 并推进 revision；
- 候选来源必须区分“搜索发现”“页面/接口实际观察”和“正式抓取”，不得把 URL 字符串冒充页面已读取；
- Crawl Plan 必须完整对账 Capture Task 的全部来源候选和原文 topic，并说明每个入口、正文或附件 target 的覆盖分母、捕获单元、数量、唯一键、Provider typed 配置、遍历与停止口径；新计划不能用占位 Provider、blocker 或入口页中的链接文字冒充可执行项；
- 公共资源只能按精确 HTTPS URL 或前序 HTML 中一次同源唯一链接执行；说明书 H5 保存 HTML，PDF/表格/图片保存原文件，不自由发现、递归、分页、登录或绕过访问限制；
- 计划确认前不得执行真实批量访问；
- 登录、验证码、风控、拒绝访问、许可不明或频控熔断时停止，不自动绕过；
- 原始内容按来源真实格式保存，新观察追加新快照，不覆盖历史；
- 工作台能查看来源运行、对象、快照、附件和失败原因，并导出 JSONL、CSV 或原文件。

## 9. 当前 MVP 验收

当前验收 Roadmap 1A/1B，以及已明确授权的 1C/1D 首个京东有界纵切片：

- “抓冰箱”直接进入专业调查，不重复确认已给出的品类；
- Agent 能说明冰箱为什么属于标品、需要调查哪些标准和来源；
- Agent 不把“是否纳入京东”作为默认第一题；
- Agent 的问题是对负责人真正有意义的取舍，推荐项有证据和专业理由；
- 用户能从问答过程理解范围、覆盖、成本或时点等影响；
- Markdown 草稿准确表达抓取内容、来源事实、排除项和未决项，不提前展示正式任务字段；
- 草稿与正式 Capture Task 同时覆盖多品牌多型号市场数据、品牌官方配置/说明书、国家标准/监管和技术原理四类专业导购资料；系统调查未决项未解决时不得确认；
- 确认草稿只生成正式 Capture Task，不自动启动规划或真实抓取。
- 用户从已确认任务显式启动 Planning Run，能看到真实 commentary 与网页搜索活动；
- 计划逐个来源和 target 明确抓取内容、数量、覆盖分母和停止口径，7 个采访候选、品牌官网/说明书、国家标准、监管附件、底层原理和全部 task topic 能独立对账；
- Crawl Planning 开始前再次检查四类来源组合；不能因为“现有两个候选都用了”就把只有品牌官网的窄任务判为完整；
- 用户可补充要求生成新版本，旧版本保留；
- 确认计划不创建 Source Run，也不开始抓取。
- 已确认计划另行显式开始；服务端重读精确版本，Provider preflight 通过后才创建 Source Run；原始 HTML、H5、PDF、表格和图片按来源格式保存为不可变 Snapshot/Asset 并可查看、下载和导出。阶段 2 才从这些原件抽取参数、标准化和形成知识。

1A 专业问答质量仍待产品负责人独立审查；后续授权已经完成 1B 完整清单、两个有界 Provider 和显式 Start 主链。本轮只确认多来源计划，没有启动真实访问；专站 crawler、扩量抓取和阶段 2 仍不在当前验收内。

## 10. 当前明确不做

- 非标准商品调研；
- 数据清洗、Evidence、知识加工、知识包和 Runtime；
- 万能 Provider 插件系统或逐站点 DOM projector；
- 自动绕过验证码、风控、登录挑战或用途限制；
- 用测试、fixture、POC 或少量手工 URL 冒充完整抓取闭环。
