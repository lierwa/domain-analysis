# 标准商品数据抓取与清洗平台 MVP 实施计划

版本：V2.0
更新日期：2026-08-24
当前阶段：1D AI 品类深搜规划；下一步 1E 品牌官网真实抓取 POC

## 1. 实施原则

项目只按以下顺序推进：

```text
专业采访与抓取任务
  → 每个真实来源的 Crawl Plan
  → 单一真实来源原始数据闭环
  → AI 深搜品类品牌版图与官网来源
  → 品牌官网补齐与缺口修复
  → 淘宝及其他多市场来源
  → 阶段 2 数据清洗设计
```

后一项不能用测试、fixture、POC、历史样本或不可达代码替代前一项的用户验收。任何真实来源访问都必须晚于计划确认和访问停止门。

## 2. 1A：对话生成抓取任务

### 目标

让负责人从“抓冰箱”“抓电视机”等一句标准商品需求出发，在专业抓取任务顾问的引导下理解范围和来源取舍，得到可审核、可修改、可确认的版本化 Markdown 范围草案。

### 主要工作

- 判断需求是否属于标准商品范围；
- 主动调查标准/监管、市场分类、品牌/型号结构、内容范围和候选来源；
- 用普通对话持续解释调查过程和当前判断；
- 只询问必须由负责人决定、会实质改变结果的取舍；
- 每题给出专业推荐、依据和主要代价，不为凑选项制造问题；
- 形成版本化 Markdown Capture Task Draft，并只在用户整体确认后通过独立纯转换生成 Capture Task；
- 支持刷新恢复、中断、重试、继续修订和历史版本保留。

### 平台来源规则

- 平台覆盖属于系统主动调查和规划的数据资源，不是默认的“要不要”问卷；
- 品类品牌、官网、标准和技术来源由系统调查，不要求负责人先枚举；
- 当前正式规划排除需要登录或已触发访问限制的 JD；历史 JD 数据只用于审计，不作为当前覆盖分母；
- 型号、官方参数、规格页和说明书由品牌官网补齐；
- 淘宝作为后续多平台来源，在目录发现与官网补齐闭环后单独计划和验收；
- 平台必须覆盖不等于已获准访问，真实执行仍受许可、登录、验证码、风控和频控停止门约束。

### 通过条件

1. “抓冰箱”直接进入调查，不重复确认已明确的品类；
2. Agent 能解释冰箱的标品身份、相关标准体系、主要数据面和多来源理由；
3. 可调查事实不反问用户枚举；
4. 不把“是否纳入京东”作为默认首题或强凑题；
5. 每个真实问题都说明推荐答案、依据和主要代价，负责人能理解为什么这样选；
6. Composer 接受任何自然语言；原文必须先由 Agent 结合当前问题和采访工作资料理解，明确回答才落成 confirmed Decision，追问、纠正和附加事实都能继续并被保留；
7. Markdown 草稿明确标准商品边界、市场/时间范围、内容范围、关键调查依据、排除项和未决项；采访回合不要求穷举品牌/官网，也不输出正式任务 schema；
8. 用户确认后才结构化 Capture Task；该转换不搜索、不增加事实，也不启动规划或访问真实来源；
9. 用户在真实 PC Workbench 路径人工验收问答质量与草稿内容。

### 停止门

用户已明确授权实现 1B/1D AI 深搜规划，因此旧的“1A 未验收不得实现 1B”门对本次实现失效。1A 的专业问答质量仍待真实 PC 人工验收；规划可以网页搜索，但任何品牌官网或其他来源抓取仍晚于计划确认和显式 Start。

## 3. 1B：单一真实来源 Crawl Plan

在一个已确认 Capture Task 上显式启动可见 Planning Run，先生成版本化 Crawl Plan Draft，再由用户确认。计划必须回答：

- 来源角色、入口和访问状态；
- 抓取对象、覆盖分母、数量和唯一键；
- 覆盖分母的原始证据和漂移处置；
- 捕获 HTML、JSON、CSV、PDF、XLSX、图片或其他哪种源站单元；
- 遍历方式和停止条件；
- Provider、许可、登录、验证码、风控、频控、恢复或持久化尚未验证时的执行阻塞项。

必须先调研成熟组件并通过与真实来源一致的最小原型；用户确认计划前不得运行真实批量请求。

1B 首个纵切片只实现规划、修订和确认。Planning Run 连接关闭即中止，完成结果可刷新恢复；不引入后台队列。计划必须以 Capture Target 逐项明确来源、内容和数量，确认不创建 Source Run。

## 4. 1C：单一真实来源闭环

从 1B 已确认来源抓取一批未清洗原始数据，写入正式本地数据区。重启 API/Web 后仍可查看；JSONL、CSV 或原文件可导出；数据库计数、导出记录、来源身份和停止原因一致。

这一阶段只证明一个来源的真实闭环，不冒充跨来源或平台完成。

## 5. 1D：AI 品类版图与官网来源规划

在一个已确认 Capture Task 上，依次验收：

1. `brand_landscape` 覆盖权威目录、广覆盖目录、主流、长尾/细分、区域/进口、母品牌/子品牌/授权品牌和饱和核查七个镜头，至少使用四个独立非 JD 证据源，并保存每轮发现/新增品牌；
2. 每个发现品牌都有专门官网检索；无法确认时至少保留两条不同查询并明确记为 `unresolved`；
3. 每个已规划品牌都通过 `parameters_and_manuals` 专门核对产品目录、规格页或说明书入口；
4. `standards_and_principles` 找到标准/监管和技术原理权威来源；
5. 每个任务 topic 映射到实际 source/target；
6. 最后两个不同饱和查询连续无新增，覆盖分母等于逐品牌对账数；排名榜不能充当完整目录；
7. UI 显示搜索记录、证据 URL、每轮新增、品牌对账、完整度和停止口径，负责人确认前不创建 Source Run。

当前 version 4 计划只允许 `public.web-resource@2.0.0`，排除 `*.jd.com` 和 JD Provider。品牌官网首个 HTML 种子使用有界 `site` route，明确正文/附件使用 `exact` route；抓到响应与内容通过分别记账。搜索未发现不等于品牌不存在；证据不足必须保持 `partial`，不得伪造全量。

## 6. 1E：品牌官网补齐、缺口修复与其他多来源

AI 深搜形成品牌—官网清单后，负责人确认 plan version，再抓取官方产品目录、产品页、规格页和说明书。公共资源 Provider 复用 Crawlee 的 sitemap 解析与持久 RequestQueue，在计划冻结的同源、深度、页数、时长和请求预算内发现页面；精确正文/附件继续按 exact route 保存。运行中不得跨计划来源搜索，也不得越过路由边界。

多来源阶段验证：

- 相同标准商品身份如何跨来源关联，但不提前清洗合并；
- 每个 Research Audit 发现品牌都有官网映射状态；后续每个型号候选都有 exact/family/ambiguous/not-found 结论；
- 产品页、规格页和说明书分别 captured 或带原因 missing；任何 gap 使任务保持部分完成；
- 各来源原始结构分别保存，不压成共同参数表；
- 不同访问策略、更新时间和失败不互相串线；
- 新观察追加快照，不覆盖历史；
- 任务可以部分完成并明确报告未覆盖来源。

## 7. 阶段 2：数据清洗

只有阶段 1 全部通过后才开始需求访谈、开源调研和架构设计。输入只能是阶段 1 的不可变原始数据；清洗结果必须与原始数据物理或逻辑分离，不能反向改写来源快照。

当前不得恢复旧 Evidence、Knowledge Factory、知识包或 Runtime 路线，也不得把旧文档和历史 POC 当成阶段 2 已设计。

## 8. 全局停止规则

- 非标准商品不进入当前流程；
- 1A 未人工验收且没有负责人明确授权时，不进入新的后续实现；本次 1B 规划实现已有明确授权；
- Crawl Plan 未确认，不运行真实批量访问；
- 历史 JD 计划不得再运行，生产组合根不注册 JD Provider；
- 不自动绕过验证码、风控或访问限制；
- 不新建万能 Provider 系统、平行应用、POC package 或隔离数据库冒充生产；
- 自动化测试不能代替真实 Workbench 与真实来源验收。
