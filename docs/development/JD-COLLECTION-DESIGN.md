# 商品知识补救与京东冰箱数据采集开发方案（历史方案）

状态：已被 2026-08-24 的“京东目录发现＋品牌官网补齐”方向替代，仅保留历史证据
更新日期：2026-08-24

> 本文件中的京东登录、旗舰店、商品详情、详情媒体和评价采集不再是当前实现依据。真实账号异常已经否决该路径；当前开发范围、删除清单和验收门以 `JD-COLLECTION-ITERATION.md` 与 ADR 0017 为准。历史记录和原始数据保留，不得按本文件继续实施。

## 1. 简单说明

最终要生产的不是商品目录，而是能让 Agent 解释“商品为什么这样工作、不同技术有什么取舍、具体型号怎样实现和是否适合某种需求”的商品知识。知识资产必须同时包含商品底层知识和商品品类知识；冰箱品类知识再包含品牌、系列、型号、变体、规格、功能、评价和时点销售信息。

京东负责提供冰箱市场分类、官方渠道、完整商品内容和用户体验样本；品牌官网、说明书、监管/标准和其他权威技术来源负责补足产品结构、部件、压缩机与制冷循环、换热、控温、除霜、保鲜等原理及适用边界。任何单一来源都不能冒充完整知识库。所有结果必须逐条落盘、可查看、可导出、可断点恢复，再经证据绑定、加工和审核形成知识。

## 2. 本方案纠正的错误方向

- 不先写死“要抓哪些冰箱字段”，再把页面压缩成少量字段。
- 不把京东只当作品牌＋厂家型号的发现入口。
- 不去 `item.jd.com` 寻找冰箱技术官方文档；商品详情页本身就是待采的销售资料。
- 不把 `maxConcurrency: 1` 冒充频控，也不在未持久化结果前运行大批量循环。
- 不把一次 Node REPL 内存、几个样本或参数数量当作采集产物。
- 不把品牌＋型号目录冒充商品品类知识，更不能冒充压缩机、制冷、换热、控温或保鲜等商品底层知识。
- 不要求京东独自证明技术机制；详情中的技术文案先作为来源资料和补充线索，后续再由品牌说明书、标准或监管资料核验。

## 3. 商品底层知识与品类知识

### 3.1 商品底层知识

冰箱底层知识至少要能解释：

- 制冷循环怎样通过压缩、冷凝、节流和蒸发搬运热量，各环节的输入、输出和效率约束；
- 压缩机、冷凝器、蒸发器、节流部件、风机、传感器、控制器和保温结构分别承担什么职责；
- 直冷、风冷、混冷，定频、变频，多循环、独立控温、除霜等技术路线的工作链、适用条件和取舍；
- 温度、湿度、气体、微生物、密封、材料和气流如何影响保鲜，以及保鲜宣传能够和不能够推出什么；
- 能耗、噪声、容积、换热、安装散热、可靠性和维护之间的约束与常见失效机制。

底层知识不能从京东筛选词、商品卖点或评价直接推断。每条正式结论必须有可定位的权威技术证据，说明原理链、适用条件、边界和冲突；品牌技术文案只能证明该品牌作过什么声明，不能自动升级为通用科学事实。

### 3.2 商品品类知识

冰箱品类知识把适用的底层知识组织成用户和 Agent 可以使用的专业体系，至少包含：

- 品类边界、监管分类、标准、核心部件、技术路线、功能、指标和共享属性；
- 需求场景到规格、功能、机制、限制和取舍的关系；
- 目标市场中的品牌、系列、型号、变体、SKU、官方渠道和在售状态；
- 每个型号的完整规格、功能声明、结构与图文、说明书、Offer 和评价样本；
- 型号事实、品牌声明、底层原理和用户体验之间的显式关系与证据状态。

品牌、系列和型号是品类知识的市场实例层，只解决“市场上有什么、某个型号声明了什么”；只有把这些实例与底层原理、品类技术路线、适用条件和证据连接起来，才形成可供 Agent 使用的商品知识。

### 3.3 来源职责

| 来源类型 | 能直接证明什么 | 不能单独证明什么 |
| --- | --- | --- |
| 京东自营/核实官方旗舰店 | 市场分类、渠道、SKU、完整商品详情、品牌卖点、Offer、评价与时点状态 | 通用科学原理、品牌宣传的真实性、跨市场完整型号总体 |
| 品牌官网、说明书、服务/技术资料 | 品牌型号、规格、官方功能声明、产品结构、使用与维护边界；有明确技术材料时可证明品牌采用的技术方案 | 未明确披露的内部实现、跨品牌通用原理、市场总体 |
| 监管备案与标准 | 合规身份、适用分类、指标定义、试验方法、法定边界 | 当前在售、完整商品体验、品牌营销功能是否有效 |
| 权威技术资料与核心部件资料 | 制冷、压缩、换热、控温、保鲜等原理，部件作用、技术路线和边界 | 某具体型号确实采用了该方案；必须再由型号证据连接 |
| 用户评价 | 真实使用体验、故障/安装/噪声/保鲜等问题线索和频次候选 | 技术原理、因果关系、型号规格或质量定论 |

“权威技术资料与核心部件资料”的具体来源白名单、许可、时效、可携带边界和质量门必须先登记到 `RESEARCH.md` 并用真实样本验证；普通营销媒体、SEO 内容和无出处转载不进入正式知识。

## 4. 历史采集数据合格性审计

### 4.1 为什么不合格

旧采集的主要问题不是数量，而是目标、结构和持久化都只支持“目录 identity”：

1. `OfficialCatalogEntry` 只保存品牌、厂家型号、来源 ID、URL及少量身份/分类字段，无法保存完整详情、技术资料或知识关系；
2. 京东详情虽然曾读取参数，`entryFromDetail` 最终只取品牌和能效网规格型号，其余参数、文字、图片、Offer 和评价全部丢弃；
3. 多数来源使用 `MemoryStorage({ persistStorage:false })`，在内存聚合整批结果，进程退出后没有原始目录、详情或持久队列；
4. 九源 737 个 identity 和监管对账只存在于后来删除的隔离数据库，没有形成当前可查看、可导出、可重放的数据集；
5. URL 和数量没有对应的不可变内容、hash、locator、对象关系和证据充分性，不能证明“当时实际看到了什么”；
6. 没有采集说明书、技术页、标准条款、部件资料和原理证据，也没有“原理 → 品类技术 → 型号声明/实现 → 用户体验”的关系；
7. 当前开发库只有 `example.com` 测试观察和 EvidenceItem，不能冒充品牌、监管或京东真实资料。

### 4.2 哪些仍然合格、可以保留

| 现有资产 | 合格用途 | 明确不能冒充 |
| --- | --- | --- |
| allowed origin、typed 页面状态、首次受限即停止 | 来源访问安全边界和失败分类 | 已通过京东生产访问或频控 |
| 品牌＋厂家型号 identity、冷柜/酒柜/冰吧排除规则 | 目录去重和型号候选规则 | 完整商品资料或商品知识 |
| 九个官网 adapter 与 737 条历史运行统计 | 已覆盖来源的候选清单、adapter 可达性和历史枚举证据 | 当前持久化数据、当前在售总体或覆盖率 |
| 监管 381 matched、338 not_found、18 producer_conflict 的历史运行 | 监管 identity 对账流程和冲突分类证据 | 当前监管事实库、能耗/容积详情或底层原理库 |
| R-026 的 HTML/JSON、PDF 页、XLSX 行、图片字节原型 | 最小证据格式、locator、hash 和内容边界的原型证据 | 已完成的多来源商品知识数据集 |
| PostgreSQL/Drizzle、DBOS、`cacache`、Evidence Module | 逐条持久化、恢复、内容寻址和证据提交的已有基础 | 上层来源 contract、知识模型或真实数据已经完成 |
| 当前 `example.com` 数据 | 自动化测试夹具 | 任何真实商品、品牌、监管或知识结论 |

历史运行结果不得删除或篡改，但统一降级为 `historical_run_evidence` 或候选输入。凡是原始内容已经不存在的记录都必须重新访问来源，不能根据历史数量或 URL 补造内容。

## 5. 官网、监管与京东统一补救方案

### 5.1 统一运行边界

补救不是单独重跑九个官网、再另跑京东，而是在一次冻结的 `PipelineRun` 下建立相互隔离的数据搜集板块：

- **底层知识板块**：围绕制冷、压缩、换热、控温、除霜、保鲜、能耗、噪声和可靠性等 Knowledge Need，采标准、监管/科研资料、权威技术资料、核心部件资料和品牌技术资料；
- **品牌官网板块**：重采品牌目录、完整产品页、说明书/服务资料入口、技术页、规格图文和来源完整性；
- **监管板块**：重采身份、适用分类、标准与指标记录，并保留 matched/not_found/conflict 和原始证据；
- **京东板块**：按本文件后续方案采分类/筛选、核实店铺、SKU、完整详情和评价；
- **统一加工板块**：从上述来源数据生成底层知识候选、品类知识、Market Universe、型号事实、比较维度和用户问题候选，再经证据绑定和审核发布。

各板块共享项目、品类版本、来源/证据政策和最终验收报告，但拥有独立队列、频控、授权、失败和恢复点。京东触发 403/验证只熔断京东板块，不阻塞官网、监管和不依赖京东的底层知识采集；任何板块失败都不能丢失其他板块已提交记录。

### 5.2 官网与监管补救

每个历史官网来源必须重新执行并逐条持久化，至少取得：

1. 目录声明数、实际读取数、分页、品牌/系列/型号、排除项和 unknown；
2. 每个型号的完整参数分组、详情文字块、图像关系、说明书/服务资料链接和当时状态；
3. 品牌技术页或说明书中明确出现的部件、技术路线、功能机制、适用条件和限制；
4. 原始内容或最小证据的 URL、时间、hash、locator、对象关系和解析版本；
5. 监管记录的备案身份、适用标准、指标原文和冲突状态；
6. PC Workbench 查看、JSONL/CSV 导出、失败恢复和来源完成度。

官网没有说明某项底层原理时必须保持 `unknown`，转到底层知识板块补证；不得从产品名、营销标题、相邻图片或同品牌其他型号推断。旧 737 条只能作为待重新核验的 source-object 候选，不能直接写入新快照。

### 5.3 底层知识补救

先由品类能力问题生成底层 Knowledge Need，例如“蒸汽压缩制冷循环如何工作”“变频压缩机改变了什么”“风冷与直冷为何产生不同温湿度和结霜表现”“不同保鲜技术作用于哪些变量”。每项至少形成：

- 规范概念、部件和作用链；
- 输入、输出、关键指标、适用条件和边界；
- 可比较技术路线、收益、代价和常见失效；
- 一条或多条可定位的权威证据；
- 与冰箱品类功能/属性的关系；
- 与具体品牌/型号声明的连接状态：`confirmed / candidate / conflicting / unknown`。

底层结论不能因为某型号页面写了“全空间保鲜”“双系统”就自动成立。页面只创建品牌声明候选；只有通用原理证据和该型号采用该结构的证据都存在时，才允许建立“型号实现/利用该机制”的审核候选。

### 5.4 合格数据的统一判定

| 层级 | 合格完成门 |
| --- | --- |
| 来源数据 | 内容逐条持久化；可查看/导出/恢复；有 URL、时间、hash、typed 状态和对象关系；失败与 unknown 不被吞掉 |
| 商品底层知识 | 说明原理链、部件、条件、边界、取舍和失效；绑定权威证据；不依赖品牌营销文案独立成立 |
| 商品品类知识 | 同时覆盖品类标准/技术路线/比较维度和品牌/系列/型号/变体市场实例；能引用适用的底层知识 |
| 型号知识 | 完整规格、功能声明、详情图文、说明书、Offer 和评价可追溯；型号采用某机制的关系有单独证据 |
| 发布知识 | 来源直出、确定性转换、模型候选、人工确认、冲突和 unknown 状态分开；能力问题验收通过后才进入知识包 |

完成报告必须按这五层分别给出覆盖、缺口、失败和 unknown。只报告抓取页数、型号数、参数数或 EvidenceItem 数量一律不算完成。

## 6. 京东来源的四个核心产物

### 6.1 京东分类与筛选体系

从京东冰箱类目页、搜索/频道页和可见筛选面取得：

- 功能分类、热销系列、潮流新品等运营分类；
- 品牌、类型、门体结构、门个数、容量类型、嵌入方式、控温方式、制冷方式、能效、尺寸等当时公开的全部筛选维度；
- 每个维度的原始名称、全部原始选项、展示顺序、入口 URL 和采集时间；
- 分类/筛选选项与商品 SKU 的实际对应关系；
- 页面声明数量、实际读取数量、分页范围、空结果和异常状态。

这些数据首先保留京东原文，不提前冻结为跨品类属性或监管分类。后续加工才能判断哪些是市场分类、比较维度、营销标签、污染项或未知项。

### 6.2 自营与经核实官方旗舰店

- 从类目品牌面、京东店铺入口和商品店铺关系发现国内外品牌；
- 对每个候选店铺记录京东店铺 ID、名称、URL、自营/官方旗舰店类型、品牌关系、核实依据、核实状态和核实时间；
- 只有京东自营及核实后的品牌官方旗舰店进入首轮商品目录；普通第三方、小型商家和无法核实的店铺不进入；
- 按店铺冰箱分类枚举商品，记录声明数、读取数、唯一 SKU、分页、排除项和未知项；
- 同一品牌可有多个官方渠道，同一 SKU/型号也可被多个入口发现；来源关系保留，但不据此制造新型号。

### 6.3 商品目录与完整商品详情

每个 SKU 至少保留以下公开资料，字段以页面实际出现为准，而不是预设白名单：

- SKU、标题、品牌、店铺、商品 URL、类目路径、在售/缺货/下架状态、价格/促销及采集时间；
- 商品详情参数表的全部原始分组、参数名、参数值和展示顺序，允许同名参数重复出现；
- 京东商品编号、能效网规格型号/厂家型号、系列、颜色或规格选择及 SKU 间关系；
- 商品详情区全部可见文字块、表格、功能说明、卖点、技术描述、适用场景、售后说明及其区块顺序；
- 主图、详情图、参数图在详情 HTML/源站 JSON 中声明的原始 URL、用途、区块、顺序和与 SKU 的关系；本阶段不请求图片字节，不记录内容哈希、尺寸或本地内容地址；
- 页面访问状态、最终 URL、采集时间、内容哈希和解析版本。

完整商品内容区域可以在本机受控环境中保存；导航、广告、猜你喜欢、账号信息、地址、Cookie、Header、Profile、追踪脚本和无关个性化内容不得进入来源数据集。

### 6.4 用户评价汇总与样本

每个 SKU/商品记录：

- 平台公开展示的评价总量、好评率、差评率、各评分档计数和评价标签计数；
- 可配置的样本上限，首轮验收候选为每款 100 条；数据量或访问边界不足时可以降为 50 条，但必须记录实际取得数量；
- 不能只保存默认推荐好评。采样计划必须记录排序、评分筛选、分页和各档实际数量，使差评/中评能够进入样本；
- 每条样本保留公开评价 ID、评分/档位、正文、时间、购买规格、追评、图片/视频引用和有用数；
- 不保存用户头像、个人主页、完整账号标识或与商品体验无关的个人信息；展示昵称如无业务必要不保存。

评价是用户体验来源，不直接等于产品技术事实。后续可以形成噪声、空间、制冷、保鲜、安装、故障、售后等主题候选，但必须保留样本范围和时点。

## 7. 来源数据怎样保存

### 7.1 事实分层

```text
权威技术资料／官网／监管／京东页面
  → 来源对象与不可变来源快照
  → 商品底层知识候选＋商品品类知识候选
  → 市场总体／品牌系列型号／属性字典／比较维度／用户反馈候选
  → 最小证据与审核知识关系
  → 知识包
```

- **来源原始数据事实源**：Workbench PostgreSQL 保存批次、来源对象、结构化快照、资源引用、关系、状态和哈希；本地内容寻址存储只保存 Crawl Plan 明确要求取得的原文件，本阶段不保存京东图片字节。
- **执行事实源**：DBOS 保存队列、尝试、恢复、取消和运行生命周期；不得反向充当商品事实。
- **市场总体事实源**：确认后的 `MarketUniverseVersion` 由来源快照投影并人工确认；SKU、店铺或页面数量不等于型号数量。
- **证据与知识事实源**：EvidenceItem、候选、审核和知识包仍是下游，不覆盖来源快照。

### 7.2 最小数据结构

实施阶段优先复用现有 PostgreSQL、Drizzle、DBOS 和本地内容寻址存储，不新增数据库、队列或对象存储产品。公共 contract 必须先用 Zod 校验，不允许把无类型 `metadata` 传入加工模块。

| 记录 | 责任 |
| --- | --- |
| `SourceCollectionRun` | 冻结项目、来源、类目、店铺范围、评价样本上限、频控政策版本、开始/结束、统计和终止原因 |
| `SourceObject` | 稳定标识技术资料、标准/监管记录、官网产品/文档、京东类目/店铺/SKU/评价等外部对象 |
| `SourceSnapshot` | 对一个来源对象的不可变 typed 快照；具体 content kind 在共享 contract 原型后冻结，不能只覆盖京东五类对象 |
| `SourceResourceReference` | 快照中观察到但未下载的外部资源 URL、类型、用途、区块、顺序和所属来源对象/Snapshot 关系；不表示字节已取得 |
| `SourceAsset` | Crawl Plan 明确要求下载的原文件字节、来源 URL、内容哈希、媒体信息和本地内容地址；本阶段京东图片不进入此记录 |

当前已实现的共享 contract 仍是 ADR-0014 冻结的 `source_collection_runs / source_objects / source_snapshots / source_assets` 四张 Workbench 表。下一轮候选只新增通用 `SourceResourceReference` 表达未下载 URL；它尚未实现，需随 `JD-COLLECTION-ITERATION.md` 整体复核后再修改公共 contract。实现继续保护以下不变量：

1. 每取得一条有效记录立即事务提交，不等整批结束；
2. 同一对象的新观察追加新快照，不覆盖历史；
3. 原始参数使用有序数组保存，不能用 `Record<string,string>` 吞掉重复键和区块顺序；
4. 原始参数与规范化属性分离；后续改映射不需要重新访问京东；
5. 品牌、店铺、SKU、厂家型号、变体和 Offer 分开建模；
6. 每个派生结果可以定位回来源快照、URL 和时间；只有实际取得的 Snapshot/Asset 才要求对应内容哈希，资源引用不得伪造内容哈希；
7. 用户能在 PC Workbench 直接查看，且可按批次导出 JSONL；适合表格的数据另提供 CSV；
8. 当前批次即使失败，已提交记录仍可查看，恢复后只处理未完成对象。

### 7.3 面向用户的可见输出

Workbench 至少提供“来源数据”和“京东数据”两个关联视图，并展示/导出：

- 分类/筛选维度、选项数量、商品覆盖和异常；
- 品牌、已核实店铺、候选/拒绝原因和店内商品数量；
- 商品 SKU 列表、详情完成度、全部原始参数、详情图文和时点状态；
- 每款商品评价汇总、实际样本数量及好/中/差样本；
- 当前速率、已完成/待处理/失败、最近一次 403/验证和恢复点；
- 本批次 JSONL/CSV 导出入口。
- 底层知识问题、已取得权威证据、缺口和与品类/型号的连接状态；
- 官网/监管重采完成度，以及历史候选、已重采、失败和 unknown 的区别。

## 8. 统一采集与加工执行顺序

以下顺序不可颠倒：

1. **知识范围与输出面先通过**：冻结底层知识问题、品类知识范围和合格判定；实现逐条落盘、查看、导出、失败记录和断点恢复；没有可见产物时禁止真实批量抓取。
2. **本地队列与频控门**：用 fake 数据和本地 HTTP fixture 证明幂等、恢复、限速、冷却、熔断和取消后零残留；此时不访问京东。
3. **官网/监管补救小批次**：选择代表来源重采目录、完整详情、说明书/技术页和监管记录，验证统一来源数据 contract；不等待京东恢复。
4. **底层知识小批次**：围绕压缩机、制冷循环、控温/除霜和保鲜选择代表性权威资料，形成可审核的原理链和边界。
5. **京东分类小批次**：只有第 9.1 节频控门通过后，采冰箱分类、全部筛选维度和选项，验证动态展开、分页、污染项和快照差异。
6. **京东店铺与目录**：发现品牌候选，逐个核实自营/官方旗舰店，按已核实店铺枚举冰箱 SKU，去重但保留来源关系。
7. **京东商品详情与评价**：逐 SKU 保存完整参数、详情文字块、图片 URL 关系、时点 Offer、评价汇总及 50/100 条样本；图片 URL 从详情响应提取且不下载图片，单项失败不影响已落盘数据。
8. **联合派生加工**：从所有来源快照生成底层知识、品类技术路线、型号总体、属性/比较候选和用户反馈主题；不得改写原始快照。
9. **联合审核与报告**：逐项核对“原理 → 品类技术 → 型号声明/实现 → 用户体验”，按五层完成门报告覆盖和缺口。

## 9. 频控、风控与恢复

- `maxConcurrency: 1` 只表示单并发，不等于频控；必须另设单位时间请求上限、同域间隔、批次上限和批次冷却。
- 京东没有公开可直接采用的网页安全数字，因此生产值不能拍脑袋冻结。先用极小批次记录实际请求时间、页面状态和 403/验证结果，再确认保守运行区间。
- 频控配置作为 `SourceCollectionRun` 的版本化输入保存，包括每分钟上限、间隔、批次大小、冷却和评价样本上限。
- 第一次出现 403、`rate_limited`、验证码、登录挑战或异常跳转，立即停止京东来源；不立即重试、不轮换代理/账号/Cookie、不伪造指纹、不自动破解验证码。
- 用户人工恢复后，从持久队列中未完成对象继续；已经成功的分类、店铺、SKU、详情和评价不重复抓。
- 访问失败也要立即落一条 typed observation，保存失败类型、URL、时间和所在对象，但不得把验证码页正文或个人会话内容保存为商品数据。

### 9.1 开始真实抓取前的频控硬门

用户已明确要求：频控问题没有完全形成可验证工程闭环前，禁止开始京东数据抓取。这里的“解决”不能虚假承诺京东永远不改变限制，而必须同时证明系统不会无上限发请求、不会在受限后继续撞击、不会因暂停丢失结果：

0. 先通过来源许可门：当前 2026-01-20 生效的《京东用户服务协议》第九条第六款限制未经特别书面同意的复制、引用、链接和抓取。项目尚无书面许可或负责人确认的法定例外，因此生产 Planner 不注册京东可执行规则，真实 reader、探针与批量访问均暂停；频控通过不能替代许可。只有取得可审计的授权依据并冻结允许字段、保存、模型输入、发布和再分发边界，才进入后续 1～7 项；依据见 `RESEARCH.md` R-010/6.4。

1. 持久队列、逐条落盘和恢复先通过；进程退出后能重读未完成项和已完成项；
2. 显式配置并持久化 `maxRequestsPerMinute`、同域最小间隔、随机抖动、批次上限、批次冷却和最长运行窗口；`Infinity`、仅单并发或 250ms 页面等待一律失败；
3. 403、`rate_limited`、验证、登录挑战为全京东板块熔断信号；当次请求不重试，队列停止派发，恢复需要新的人工/冷却决定；
4. 用本地可控 HTTP fixture 记录真实请求时间戳，证明一分钟窗口、同域间隔、批次冷却、取消和恢复均符合政策，并证明失败时没有后台残留请求；
5. 本地门通过后，只允许执行“频控验收探针”，不进入数据集：每个观察窗口至多 1 个目录页＋3 个详情页，连续三个相互冷却的窗口均无 403/验证、实际间隔符合政策，才形成候选安全区间；
6. 任一验收探针出现 403/验证，候选区间作废，停止访问并回到原因分析；不得把前 16 次成功推成安全阈值；
7. 频控门通过后，正式抓取仍从首批 20 个 SKU 开始，先复核落盘、请求节奏和页面状态，再扩批；任何一次 403 仍立即熔断，而不是说明频控方案“已经失效后继续跑”。

当前本地门状态：历史 60 秒、逐条落盘和强杀测试属于已退出的旧 Source Collection workflow，不能证明当前 Playwright JD Provider。2026-08-21 本地显式会话 HTTP fixture 已证明每个 redirect hop 先占预算、最小间隔/批次冷却和首个 429 后零继续派发；浏览器 route 方案因漏计重定向而被删除。跨进程持久计数、全京东熔断、待抓工作项恢复和逐请求 observation 仍未接入当前 Source Execution，因此第 1～4 项整体未通过，第 5 项探针禁止执行。生产 JD Provider 的 Prepare、Preflight、Collect 统一失败关闭，不启动浏览器、不检查登录、不访问京东。

频控完成门必须在 `RESEARCH.md` 登记实测政策、时间戳证据、观察窗口和失败边界，在 `PROGRESS.md` 记录当前候选状态。没有这些证据时，本文件后续 B～E 阶段全部保持禁止执行。

## 10. 旧实现处置

### 保留

- allowed origin、安全状态识别和 typed failure；
- 京东自营/核实官方旗舰店范围；
- 品牌＋厂家型号的 identity 原则，以及显式排除冷柜/酒柜/冰吧；
- 九个品牌官网来源与京东失败隔离；
- 已验证的 DBOS durable queue、PostgreSQL 和本地内容寻址存储。

### 重写

- `JdPageObservation`：从目录卡＋`Record<string,string>` 改为分类、店铺、商品、评价的 typed observation；参数保留原始分组与顺序；
- `crawlCatalog`：从“一次运行结束后返回品牌＋型号”改为发现一个对象就立即提交快照，并从持久队列恢复；
- 京东输出：从单一 `OfficialCatalogSnapshot` 扩展为来源数据集，再由显式 projector 生成 Market Universe 输入；
- Workbench：增加京东分类、店铺、商品、评价、失败和导出视图。
- 九源官网输出：从 identity 目录扩展为可逐条持久化的目录、完整详情、文档/技术资料入口和 typed 来源快照；旧 identity 只作为下游投影。
- 知识加工输入：同时接受底层知识 Evidence 和品类/型号 Evidence，显式保存两者关系，不从型号页面反推通用原理。

### 删除或禁止继续使用

- 硬编码单一自营品牌页作为京东全部冰箱入口；
- 把 `maxConcurrency: 1` 描述为已经有频控；
- 只保存参数数量、品牌、型号而丢弃详情内容；
- 把结果留在 Node REPL 或一次运行的内存 Map/数组；
- 未完成小批次频控 POC 就对数百详情页连续运行；
- 用标题猜厂家型号，或把营销分类直接冻结为跨品类知识模型。
- 把历史 737 条 identity、监管对账统计或测试 EvidenceItem 当作当前商品知识库。

## 11. 实施阶段与通过门

### A. 统一来源数据 contract、合格判定与可见输出

当前状态：跨品类公共 seam、迁移、逐条持久化、恢复读取、附件关系、JSONL/CSV、API 与通用 PC“来源数据”页已通过；冰箱＋电视使用同一 interface。尚未用真实官网/监管/权威技术资料验证分层来源视图，也没有导入历史 737 候选，因此 A 仍是部分通过，不能进入京东真实访问。

- 用最小原型冻结跨官网/监管/权威技术资料/京东的来源对象、typed content kind、关系、哈希、导出格式和隐私字段；
- 新迁移、Workbench module、API、PC 查看页和 JSONL/CSV 导出通过；
- fake 数据证明逐条提交、中断恢复、幂等去重和历史不覆盖；通用 Asset 继续验证内容哈希去重，京东详情另验证 25+ 图片 URL 完整保存且图片服务器零请求。
- PC 能分别查看底层知识来源、品类/型号来源、历史候选与本轮真实快照。

### B. 官网、监管与底层知识补救小批次

- 代表性官网重新取得目录、完整商品详情、说明书/技术页和来源完成度，旧 identity 与新快照逐项对应；
- 监管记录保留原文、适用标准、指标和冲突，不只保留 matched/not_found 数量；
- 制冷循环、压缩机、控温/除霜、保鲜至少各有一条完整“原理链＋条件＋边界＋权威证据”纵切片；
- 官网缺失、技术来源不足和型号实现无法证明均保留 typed unknown。

### C. 京东分类、店铺与商品真实小批次

- 第 9.1 节频控硬门通过；
- 真实采到当前页面全部可见分类维度和选项；
- 至少核实多个国内外品牌的自营/官方旗舰店，并保留核实/拒绝依据；
- 多品牌、多门体/安装形态样本均保存完整参数行、详情文字块和图片 URL 关系，图片服务器没有收到请求；
- Workbench 与导出内容和真实页面逐项核对，不以自写测试单独证明；
- 强制中断后继续，不重复已完成 SKU。

### D. 京东评价与联合知识真实小批次

- 每款保存汇总指标和实际 50/100 条样本；
- 好/中/差覆盖、排序、页码和不足原因可复核；
- 不保存无关个人资料，评价图片仍可定位到商品和评价。
- 至少一条品类技术路线能回到权威底层原理证据，并连接到一个有独立型号证据的商品；用户评价只作为体验证据，不作为原理证明。

### E. 批量运行

只有 A～D、PC 可见输出和停止/恢复路径全部通过，才允许在同一冻结 PipelineRun 下扩展官网/监管/底层知识与已核实京东旗舰店目录。京东仍必须单独通过第 9.1 节频控硬门。批量结束后必须按来源数据、底层知识、品类知识、型号知识和发布知识五层报告覆盖、失败和 unknown，不能只报告“抓了多少页”或“有多少型号”。
