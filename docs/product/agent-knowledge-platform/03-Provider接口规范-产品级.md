# Provider 接口规范（产品级）

版本：V1.3
MVP Provider：品牌官网/说明书、监管来源与京东教育研究网页采集
文档性质：来源接入的产品责任与验收边界

## 1. 为什么产品需要 Provider

“写一个通用爬虫”无法解决本项目的问题。不同网站在以下方面存在长期差异：

- 资料发现方式；
- 来源策略、开放 API、教育研究范围和敏感数据边界；
- 登录和验证流程；
- 页面类型与动态加载方式；
- 型号、规格和价格的展示方式；
- 下架、缺货、跳转、风控和错误页面；
- 页面变化后的维护方式。

如果把这些差异直接写进任务流水线或商品知识加工厂，系统最终会变成“京东冰箱系统”，无法用同一能力服务电视、微波炉或其他官方来源。

Provider 的产品价值是：把“某个来源按什么策略访问、怎样识别状态和保真保存”封装成独立能力，让上层只面对一致的任务、状态和原始资料。

## 2. Provider 不是什么

Provider 不是：

- 一个知识库；
- 一个领域清洗器；
- 一个商品 Schema；
- 一个独立的业务搜集任务；
- 一个保证永远绕过平台风控的工具；
- 一个自研浏览器、指纹或验证码破解模块。

Provider 只理解来源，不决定最终知识。

## 3. Provider 与数据搜集板块的关系

```text
品牌官网 Provider
  ├─ 品牌官网－冰箱板块
  ├─ 品牌官网－电视板块
  └─ 品牌官网－微波炉板块
```

Provider 是可复用的来源能力；数据搜集板块是 Provider 与具体主题、范围、更新计划的组合。

MVP 完整交付品牌官网/说明书、监管来源和京东网页采集能力，并用第二商品品类小样本证明同一个 Provider contract 不含冰箱专用逻辑。京东按 ADR-0004 使用成熟 Patchright＋Crawlee 和本地专用 Profile；淘宝在京东闭环后沿同一 contract 单独调研。

## 4. 产品级输入与输出

### 4.1 Provider 接收

- 已确认的数据搜集范围；
- 可审计的来源策略、用途、访问方式和风险边界；
- 允许的权威来源类型和已核实官方店铺身份；
- 搜索词、分类入口或种子页面；
- 采集优先级和更新规则；
- API 凭证或网页所需的本地专用会话状态；
- 本次流水线的任务上下文。

### 4.2 Provider 交付

- 发现的来源对象及稳定来源标识；
- 原始页面与完成举证所需的页面数据；
- 来源 URL、采集时间和页面状态；
- 成功、重复、跳过、失败和待人工处理状态；
- 能支持后续字段证据定位的来源上下文。

Provider 输出的是原始资料，不是“已经清洗好的商品”。对象合并、单位统一、属性判断和知识结论由商品知识加工厂完成。

## 5. Provider 必须具备的产品能力

### 5.1 能力与范围声明

- 明确 Provider 版本和当前支持的来源范围。
- 明确来源策略、允许用途、访问方式、敏感数据边界和停止条件；缺失时拒绝运行。
- 明确支持和不支持的页面类型、登录方式及资料类型。
- 当能力不完整时如实声明，不用空字段伪装成功。
- 数据搜集板块创建前，能够判断其配置是否在支持范围内。

### 5.2 资料发现

- 根据已确认范围发现候选资料。
- 按有证据的主流品牌/型号总体和官方来源矩阵执行发现，不以随机搜索结果、店铺数量或普通第三方卖家代替范围覆盖。
- 区分列表入口、详情对象、规格对象和无效链接。
- 对候选资料去重，并保留发现来源。
- 显示发现量和范围覆盖情况，不把“抓到一些”描述为“已经完整”。

### 5.3 来源访问与状态识别

- API 与网页都必须在已确认来源策略和商品资料范围内运行；未公开接口只有另行调研、记录依据并通过隔离验证后才可成为候选。
- 识别正常、需要登录、需要人工验证、限流、缺货、下架、跳转和错误页面。
- 动态内容未完成加载时不能标记成功。
- 多规格页面必须知道当前保存的是哪个规格状态。
- 页面结构变化导致关键内容缺失时，应进入异常状态而不是返回空数据。

### 5.4 授权会话和恢复

- 登录与验证码由用户在本地专用浏览器完成，不读取密码、不自动解验证码。
- 登录状态过期时暂停相关任务并提示用户接管。
- 用户完成登录或验证后可以继续原任务。
- 不要求用户复制 Cookie，不把认证信息上传服务器。

### 5.5 原始资料保真

- 保存足以重现当时页面内容和完成证据定位的原始资料。
- 每次采集保留时间、来源、板块和 Provider 版本。
- 新采集不得覆盖旧采集。
- 后续解析规则变化时，可以优先重放旧资料而不是重新访问来源。
- 认证信息、个人信息和与目标无关的敏感响应不能进入可发布知识包。

### 5.6 任务运行与维护

- 支持慢速、可暂停、可恢复和可重试的运行方式。
- 显示板块级和任务级成功率、失败原因和待处理数量。
- 支持按变化或过期规则进行增量采集。
- Provider 更新后保留版本信息，旧资料仍能说明由哪个版本采集。
- 页面变化被发现后，能够把板块标记为“需维护”，停止错误数据继续进入加工厂。

## 6. MVP：来源 Provider 的产品范围

### 6.1 必须支持

- 拒绝没有冻结来源策略、教育研究范围、敏感数据边界和停止条件的数据搜集板块。
- 在品牌官网、官方说明书和监管来源中发现候选商品；普通第三方和小型商家明确排除。
- 根据确认后的主流品牌/型号总体、官方目录或种子页面发现冰箱候选商品。
- 访问已确认页面或 API 并保存标题、卖点、规格参数、详情内容和相关图片的原始来源。
- 识别并保存当前选择的 SKU/规格信息。
- 对来源允许提供的价格、促销、库存或上下架状态保存时间属性；缺少获准来源时明确未知。
- 识别登录、验证、限流、下架和页面结构异常。
- 对失败任务重试或转交人工，不静默丢弃。
- 第二品类小样本复用同一个来源发现、访问、状态和原始资料 contract，只更换板块配置和品类定义数据。
- 京东网页 Provider 使用 Patchright＋Crawlee、本机 Chrome、专用 Profile、并发 1 和版本化页面适配；反检测与指纹能力不得自研。

### 6.2 MVP 不保证

- 永久在线、永不变化的页面解析。
- 自动解验证码、切换账号规避限制或保证所有风控都能通过。
- 采集订单、购物车、账户资料或普通第三方商家。
- 全量商品评论、问答、直播或推荐流采集。
- 对商品事实做标准化和真实性判断。

## 7. 用户可见状态

数据搜集板块至少应让用户区分：

- 尚未配置；
- 登录可用或登录失效；
- 等待执行；
- 正在发现资料；
- 正在采集；
- 等待人工处理；
- 部分完成；
- 完成；
- 失败；
- 因页面变化需要维护。

“部分完成”必须列出缺失范围，不能直接进入正式发布而不提示。

## 8. MVP 验收

使用 PRD 中确定的冰箱验收集验证：

- 每个板块都有可审计的来源策略、用途、访问方式、敏感数据边界和停止条件；
- 覆盖由版本化品类知识定义、R-010 的主流型号总体和验收设计确定的商品范围；具体数量与比例不得无依据写死；
- 包含普通详情、多规格、促销、缺货/下架、图片参数和异常页面；
- 当时可访问的官方资料达到随验收集冻结、可解释的保存成功门槛；
- 所有失败、跳过和人工接管任务均有明确原因；
- 任意抽取字段能够回到对应来源页面和采集时间；
- 人为中断运行后可以继续，已完成任务不重复破坏性执行；
- 模拟关键页面结构变化时，系统不能静默生成空记录；
- 原始资料可以在不重新访问外部来源的情况下被重新加工。
- 第二品类小样本无需修改 Provider interface、来源状态模型或通用采集流程。

## 9. 后续 Provider 的接入原则

新增品牌官网、京东网页、淘宝网页或其他 Provider 时，产品流程、商品知识加工厂和知识包使用方式不得改变。新增来源只应增加：

- 来源能力；
- 对应数据搜集板块配置；
- 必要的来源维护和跨来源知识规则。

如果新增来源必须修改通用项目流程，或同一 Provider 为电视再实现一套 adapter，说明 Provider 边界设计失败。
