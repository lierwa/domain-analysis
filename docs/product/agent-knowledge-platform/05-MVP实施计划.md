# Agent 知识生产平台 MVP 实施计划

版本：V1.2
实施目标：官方来源冰箱端到端闭环＋第二商品品类迁移门

## 1. 实施原则

MVP 不是先搭一个“万能平台”，也不是给冰箱定制一套系统；而是用冰箱跑通完整纵向链路，并用第二商品品类小样本证明切换只改数据定义。

实施顺序必须是：

```text
来源授权与真实资料可行性
  → 最小原始资料闭环
  → 最小知识加工闭环
  → 最小知识包与 Agent 查询
  → 第二品类零 Schema 迁移验证
  → 再补任务管理和完整验收
```

如果获准官方来源、混乱数据加工或轻量知识包中任一环节不可行，不应继续投入平台 UI 和通用插件框架。

## 2. 交付假设

- 首版由一名主工程师负责 Node/TypeScript 主体，可借助 AI 编程工具，但关键设计和验收由人确认。
- 用户担任产品负责人和知识范围审核者。
- 用户本机已经安装并登录 Codex CLI；MVP 复用该登录，不要求另备模型 API Key 或本地推理服务。
- 采集、清洗、评测和建包均在本地电脑执行。
- Codex CLI 任务必须限定工作目录、权限和输入；Cookie、认证 Header 与浏览器 Profile 不进入任务上下文。
- MVP 完整建设冰箱；第二品类只做结构迁移小样本，不并行建设完整知识资产。
- 冰箱事实来源只纳入品牌官网/说明书、获得访问授权的平台官方渠道和监管/标准资料，普通第三方商家排除；普通用户账号登录和公开可见不构成自动采集授权。
- 完整线上部署不属于本轮 MVP。

## 3. 预计工作量

当前不冻结总工期。既有 8～11 人周只是假设，尚未纳入主流型号总体调查、专业知识分层和跨品类迁移门；必须在阶段 0 调研与阶段 1 原型后重新估算。

| 阶段 | 预计工作量 | 是否为停止门 |
| --- | ---: | --- |
| 0. 验收范围冻结 | R-010/R-011 后估算 | 否 |
| 1. 四项可行性验证 | 调研后估算 | 是 |
| 2. 项目与流水线骨架 | 阶段 1 后估算 | 否 |
| 3. 官方来源－冰箱搜集板块 | 阶段 1 后估算 | 是 |
| 4. 商品知识加工厂 MVP | 阶段 1 后估算 | 是 |
| 5. 知识包与 Runtime | 阶段 1 后估算 | 是 |
| 6. 联调、评测与交付 | 阶段 1 后估算 | 是 |

## 4. 阶段 0：冻结验收范围

### 目标

把“冰箱调研”变成可执行、可验收的范围，避免开发过程中不断改变字段和样本。

### 主要工作

- 根据 R-010 生成可审计的主流品牌/型号总体；
- 生成产品类型、用户场景和参数矩阵；
- 生成专业商品知识的能力问题集；
- 根据 R-008 的数据化品类知识定义和 R-010/R-011 的覆盖与统计目标生成版本化验收集，不预设无依据的数量或百分比；
- 特意加入多规格、促销、缺货/下架、图片参数和异常页面样本；
- 冻结规格、功能、机制、适用条件、取舍和决策维度的抽检规则与能力问题；
- 选定一个第二品类迁移样本，只验证结构迁移成本，不假装完成该品类知识研究。

### 阶段产物

- 已确认研究范围；
- MVP 验收集；
- 核心知识层与能力问题集；
- 明确不采集的内容清单。

## 5. 阶段 1：四项可行性验证

这一阶段只做小规模纵向原型，不建设完整平台。

### 验证 A：官方来源与平台研究采集

验证品牌官网/说明书、监管数据和京东网页的候选发现、详情、多规格、图片资料、时点状态、异常状态和敏感数据隔离是否能被可靠识别和保存。京东使用成熟 Patchright＋Crawlee；淘宝只登记为下一来源，本阶段不并行展开。

通过条件：样本规模由 R-010 的来源/页面因素和组合覆盖方法产生；代表性官方资料完成原始保存，失败和人工接管状态可见，不能出现“空内容但标记成功”。

### 验证 B：混乱资料加工

从验证 A 的真实资料中选择样本，完成：

- 候选属性发现；
- 结构化抽取；
- 单位和表达标准化；
- 型号/规格对象识别；
- 冲突与低置信度审核；
- 来源证据返回。

通过条件：核心知识层质量达到随原型冻结的统计门槛，并能说明错误来自页面、规则还是 Codex；具体置信度、允许误差和样本量由 R-010/R-011 给出依据。

### 验证 C：知识包与查询

把验证 B 的结果制作成候选知识包，在无模型、无网络环境下完成精确查询、条件筛选、全文搜索和证据查看。

通过条件：知识包可复制到另一台机器加载；Runtime 不依赖向量数据库或查询 embedding。

### 验证 D：第二品类迁移门

选择电视或微波炉的小型官方资料样本，复用同一商品知识模型、Provider contract、加工流程、包结构和 Runtime。只新增版本化品类知识定义、来源范围和评测数据。

通过条件：生产 Schema、数据库结构、通用模块 interface、Runtime API 和同来源 Provider 实现零修改；如需新增品类类或通用流程分支，立即停止并返回架构设计。

### 停止规则

四项验证有一项不通过，暂停平台化开发，先调整范围或候选技术。不得用“后面再解决”跳过核心风险。

## 6. 阶段 2：项目与流水线骨架

### 目标

把验证原型变成可管理的连续任务，而不是散落脚本。

### 主要能力

- 创建知识项目；
- 保存品类、市场、用途说明、品类知识定义版本和已确认范围；
- 创建并运行一次任务流水线；
- 显示阶段、任务、进度、错误和待人工事项；
- 支持暂停、恢复、重试和版本记录；
- 区分原始资料、加工结果、审核结果和知识包版本。

### 通过条件

人为终止一次运行后能够继续；已完成的原始资料不会被覆盖或无意义重复抓取。

## 7. 阶段 3：官方来源－冰箱数据搜集板块

### 目标

达到 Provider 产品规范和 PRD 验收集要求。

### 主要能力

- 管理品牌官网/说明书、监管数据和已获权限平台 API 板块的范围、来源授权和启停状态；
- 检查 API 授权或获准网页会话，失效时暂停；
- 候选资料发现、去重和覆盖统计；
- 原始资料保存及来源上下文；
- 正常、多规格、促销、缺货/下架和异常页面处理；
- 失败重试、部分完成提示和页面变化预警；
- 基于上次运行进行增量采集。

### 通过条件

PRD 验收集中，当时可访问的官方资料达到 R-010/R-011 冻结的保存门槛；所有未成功项均可解释和重试。

## 8. 阶段 4：商品知识加工厂 MVP

### 目标

将真实、混乱的获准官方资料稳定加工为可审核知识。

### 主要能力

- 根据品类、市场和用途说明生成并维护专业商品知识范围；
- 确定性解析与规则处理；
- 必要的模型抽取、图片理解和候选判断；
- 属性、单位、枚举和别名标准化；
- 品牌、型号、规格和 Offer 对象识别；
- 重复对象合并和冲突检测；
- 低置信度与异常审核；
- 原始值、标准值、推断状态和证据保留；
- 功能、机制、适用条件、取舍、需求映射和比较维度进入结构化知识层；
- 使用旧原始资料重新加工并生成新版本。

### 通过条件

- 已发布候选知识的来源可追溯率达到 100%；
- 核心知识层人工抽检达到 R-010/R-011 冻结的统计质量门槛；
- 模型结果未经校验不能进入已确认知识；
- 冲突和无法判断项不会被静默填充。

## 9. 阶段 5：知识包与 Runtime

### 目标

把加工结果变成独立于生产环境的 Agent 交付物。

### 主要能力

- 构建只读、版本化知识包；
- 表达领域、来源范围、能力和质量状态；
- 支持精确查询、筛选、全文搜索、对象关联和证据查看；
- 在本地加载、激活、切换和回滚；
- 提供一个 Node/TypeScript Agent 接入演示；
- Runtime 查询不调用模型和 embedding。

### 通过条件

知识包复制到另一台机器后仍可加载和查询；旧版本可以安全回滚；通用 Runtime 中不存在商品专用固定接口。

## 10. 阶段 6：联调、评测与交付

### 主要工作

- 使用完整验收集从头运行流水线；
- 模拟中断、授权过期、页面/API 异常和模型失败；
- 运行购物引导 Agent 问题集；
- 检查覆盖率、准确率、证据、性能和资源使用；
- 整理已知缺口、操作手册和后续维护事项；
- 冻结 MVP 版本。

### 最终通过条件

- PRD 第 10 节全部通过；
- 能力问题和下游任务集达到 R-011 冻结的通过门；
- 不存在按版本化发布策略定义的未解决阻断项；
- 用户可以独立完成授权恢复、任务恢复、冲突审核、建包和版本切换；
- 已知缺口和未覆盖范围明确记录。

## 11. 风险与处理

| 风险 | 处理方式 | 触发停止条件 |
| --- | --- | --- |
| 平台页面、登录或风控变化 | 固定官方店铺白名单、专用 Profile、并发 1、无默认重试；Patchright/Crawlee 版本化 | 需要自研反检测、自动解验证码、切换账号或采集账户/订单资料 |
| 资料字段分散在图片或动态区域 | 保存证据，必要时模型/OCR，保留人工审核 | 核心字段准确率持续低于门槛 |
| “主流型号总体”无法证明 | 先完成 R-010，多来源估计仍不可靠时报告未知并停下确认 | 无法解释总体与遗漏来源 |
| 模型输出不稳定 | Schema 校验、证据、置信度和人工否决 | 推断值无法与事实区分 |
| AutoPKG 无法直接使用 | 只借鉴思想，小样本复现关键处理 | 因其 GPU/ODPS 前提阻塞本地 MVP |
| 知识包设计过早固化 | 先做两轮原型再冻结详细格式 | 格式写死冰箱或某个下游 Agent |
| 平台化投入过早 | 先完成四项可行性验证 | 纵向闭环或跨品类迁移门未通过却开始大规模 UI |

## 12. 人员责任

| 角色 | 主要责任 |
| --- | --- |
| 产品负责人 | 确认范围、优先级、验收集、人工审核和发布决定 |
| 主工程师 | 可行性验证、总体实现、测试和详细设计 |
| 领域审核者 | 检查规格、功能、机制、适用条件、对象合并和能力问题答案；专业知识不足时必须补充外部资料或专家依据 |
| Agent 接入者 | 验证知识包和 Runtime 是否真正可被 Agent 使用；MVP 可由主工程师承担 |

## 13. 工程团队必须补充的文档

开始正式编码后，由工程团队维护：

- 详细架构和 ADR；
- Provider 技术接口与契约测试；
- 原始资料格式；
- 知识 Schema 与迁移规则；
- Runtime API；
- 安全与隐私方案；
- 测试计划和运维手册。

这些工程文档可以细化实现，但不得反向修改 PRD 的产品目标和边界；如需改变，必须先形成产品变更决定。

## 14. MVP 之后

1. 完整建设通过迁移门的第二商品品类；
2. 根据覆盖缺口决定是否增加新的官方来源 Provider，而不是先增加普通卖家；
3. 建设线上知识包管理、轻量 Runtime 和板块维护信息；
4. 根据真实查询缺口决定是否增加可选语义检索，而不是预先引入向量基础设施；
5. 是否扩展到非商品领域另立产品调研，不从商品 MVP 自动推出。
