# 标准商品数据抓取与清洗平台总体技术方案

版本：V2.0
更新日期：2026-08-19
当前实施范围：阶段 1 数据抓取

## 1. 技术目标

系统在本地 Workbench 中完成“自然语言需求 → 专业调查与采访 → 已确认抓取任务 → 来源计划 → 原始数据集”。当前不承担清洗、知识加工或运行时查询。

架构必须同时保护四个边界：

1. 标准商品范围不写死冰箱、电视机或具体平台；
2. 用户决定、系统调查事实和模型建议相互分离；
3. 来源访问、原始数据和后续清洗相互分离；
4. Codex 只做无状态单轮专业判断，不拥有产品会话或任务事实。

## 2. 当前数据流

```text
用户首句
  -> Category Interview Module
  -> 隔离目录中的 Codex App Server ephemeral 单轮调查/提问
  -> 版本化 Capture Task Draft
  -> 用户整体确认
  -> Capture Task
  -> 用户显式启动 Crawl Planning Run
  -> 版本化 Crawl Plan Draft
  -> 用户确认 Crawl Plan
  -> Source Provider
  -> Source Run / Object / Snapshot / Asset
  -> Source Dataset
  -> Workbench 查看与导出
  -> [阶段 2，尚未设计] Data Cleaning
```

确认 Capture Task 不会自动创建计划或访问来源。确认 Crawl Plan 也不能越过许可、登录、验证码、风控和频控停止条件。

## 3. 模块与事实源

| 事实 | 唯一拥有者 | 其他模块职责 |
| --- | --- | --- |
| 对话消息、消息内有序活动、用户原文、状态和未决项 | Category Interview Module / PostgreSQL | 共同构成采访工作资料；Web 投影；Codex 每轮只读 typed snapshot |
| 用户确认的取舍 | Interview Decision | Agent 解释当前原文；Workbench 校验 proposal 引用并保存规范化决定 |
| 准备抓什么、从哪里抓 | Capture Task Draft | 用户确认前不能执行；历史版本不可变 |
| 当前已确认范围 | Capture Task | 指向最新确认 revision |
| 规划过程与结果状态 | Crawl Planning Run | Codex 无状态执行；Workbench 保存 |
| 每个来源抓什么、抓多少、何时停止 | 版本化 Crawl Plan | Provider 只执行冻结计划 |
| 一次访问发生了什么 | Raw Source Observation / Source Run | Web 和导出读取 |
| 来源当时返回的原始内容 | Source Snapshot / Source Asset | 阶段 2 只读，不覆盖 |

平台来源重要性属于产品规则与专业调查结果，不能由 UI 文案或模型临时猜测。冰箱等家电必须覆盖京东、后续扩展淘宝的产品决定，不应被实现为每次采访都重复询问的 `jd.scope` 表单题。最终规则承载方式需在 Skill 设计确认后由 Workbench typed contract 冻结；在此之前不得增加第二份事实源。

## 4. 标准商品采访层

### 4.1 Category Interview Module

负责：

- 接受首句并保存可恢复会话；
- 保存标准化消息、Interview Decision、未决项和草稿版本；
- 任何 Composer 输入都先作为用户原文进入采访 Agent；Agent 可以同时解释当前选择、事实补充、纠正和追问，Workbench 只提交经过当前 proposal 校验的 confirmed Decision；
- 把用户原文、调查说明、搜索活动、决定、未决项和草稿版本持续提供给后续无状态回合，不从单个选项或 UI 模式截断语义；
- 只在没有负责人未决项时接受 `taskCandidate`；
- 用户整体确认草稿后创建或推进同一 Capture Task revision；
- 继续对话时追加新版本，不覆盖旧版本。

### 4.2 专业抓取任务采访 Skill

Skill 定义专业行为，不拥有数据库状态：

- 先判断需求是否属于标准商品范围；
- 先调查标准/监管、品牌/型号、品类内容和候选来源；
- 区分可调查事实与负责人取舍；
- 解释调查过程、推荐答案、主要依据和代价；
- 一次只提出一个真实问题；
- 不为形成互斥选项强行制造问题；
- 把当前问题视为下一条自然语言的上下文，而不是限制用户输入的表单；语义明确时解释决定，含糊、追问或否定前提时继续对话；
- 把本轮查回和用户补充的相关事实写入对话说明，并在条件充分时综合进下一版草稿；
- 无负责人缺口时综合形成抓取任务草稿。

Skill 不负责确认决定、保存草稿、执行抓取、清洗或管理 Codex thread。

### 4.3 Codex 运行边界

- 继续使用锁定版本的官方 Codex App Server `stdio`；
- 每轮只执行 `thread/start(ephemeral:true)`，不 resume、不持久化产品 thread；
- Workbench 把完整 typed state 作为本轮唯一继续上下文；
- commentary 通过官方 `item/agentMessage/delta` 流式投影；
- final answer 只交付本轮理解增量：助手说明、可选的当前决定解释、可选的下一问题、未决项变化和可选完整草稿；服务端通过领域 Zod contract 后原子持久化，不要求模型重报整份会话状态；
- 产品运行时关闭 `shell_tool` 与 `unified_exec`，不读取工程 `AGENTS.md`、Git 或开发目录；
- 首轮调查需要真实 `web_search` item，但“发生搜索”不能自动证明页面已打开或候选内容正确。

## 5. Chat Timeline

继续复用 `assistant-ui` ExternalStoreRuntime。Workbench/PostgreSQL 是消息和业务状态事实源，不使用 Assistant Cloud 或浏览器内存保存第二份会话。

同一 assistant turn 的 commentary、搜索活动和最终文字按到达顺序保存。负责人问题使用普通消息呈现；Composer 同时接受建议答案和自定义答案。发送回答即完成该次负责人确认并继续，不出现独立题板或第二次“确认”。

## 6. 来源计划与访问层

正式 Crawl Plan contract 与交互见 `docs/development/CRAWL-PLANNING-DESIGN.md`。计划至少冻结：

- 来源角色、入口和观察状态；
- 捕获对象、覆盖分母、数量和唯一键；
- HTML、JSON、CSV、PDF、XLSX、图片或其他原始捕获单元；
- 遍历方式和停止条件；
- Provider、许可、登录、验证码、风控、频控、恢复或持久化尚未验证时的执行阻塞项。

Provider 是外部协议 adapter：执行已确认计划、识别访问状态、返回源站原始内容。Provider 不决定品类范围，不清洗数据，也不把站点 DOM 规则升级成跨品类模型。

Planning Run 复用采访已验证的 App Server `stdio`、ephemeral thread、Skill input、web search、commentary delta 和本地 Zod 校验，但使用独立规划 Skill 和独立 Workbench Module。当前规划前台可见，页面连接关闭即中止；不引入隐藏后台 Agent、DBOS 或新队列。正式 Source Run 内不得调用 Codex 无边界搜索新网站。

京东、淘宝、品牌官网和监管来源可以使用不同 Provider，但必须写入同一个跨品类 Source Dataset 事实层。不得为每个平台或品类复制一套任务、运行和原始数据模型。

## 7. 原始数据层

阶段 1 保存源站原始业务内容：

- 可安全内联的 HTML、JSON、CSV、文本等；
- PDF、XLSX、图片、视频等原文件；
- URL、最终 URL、时间、HTTP/访问状态、媒体类型、字节数和内容哈希；
- 来源对象身份、运行和快照之间的关系。

新观察追加新快照，不覆盖历史。阶段 1 不先做字段标准化、实体合并或知识判断，也不把全部来源压成一个参数 schema。

## 8. 物理与安全边界

- PostgreSQL `workbench` schema：会话、任务、计划元数据、运行、对象和快照索引；
- 本地附件区：原文件内容，具体 CAS/路径在 1B 调研后确认；
- Cookie、Profile、密码、认证 Header、验证码材料不得进入数据库、日志、Git、Codex 输入或导出；
- 本机数据库与附件不通过 Git 同步；
- 登录、验证码、风控、拒绝访问、许可不明或频控熔断时停止，不自动绕过。

## 9. 当前成熟组件

- PostgreSQL＋Drizzle：Workbench 结构化事实与 migration；
- Fastify：本地 HTTP/SSE adapter；
- assistant-ui ExternalStoreRuntime：Chat primitives；
- Codex App Server `stdio`：无状态单轮采访执行；
- Zod：跨模块与模型输出校验；
- Crawlee：后续来源访问基础；
- p-queue＋cockatiel：后续频控、取消和熔断基础。

当前不引入 Pi Agent、agent registry、多 Provider 模型层、自动 fallback、DBOS 工作流、知识包 Runtime 或新的通用基础设施。

## 10. 当前停止门

Roadmap 1A 只验收采访 Skill 的专业行为、真实交互和任务草稿：

- 标品边界判断正确；
- 系统主动调查，不让用户枚举可查事实；
- 平台来源按产品和调查事实规划，不强问“是否纳入京东”；
- 每个问题都是真实负责人取舍，推荐答案有依据；
- 用户能从过程理解抓取范围、覆盖和代价；
- 草稿完整且确认不触发抓取。

1A 专业问答质量仍待真实 PC 人工验收。用户已于 2026-08-19 明确授权冻结本轮最小 Crawl Plan contract；该授权不包含 Provider、真实来源访问或原始附件写入。
