# Agent 知识生产平台总体技术方案

版本：V1.0
文档性质：产品约束下的总体方案，不是详细设计

## 1. 本文档解决什么问题

本文档把 PRD 转换为系统边界和模块关系，确保工程团队不会把产品做成：

- 一个只会抓京东的脚本；
- 一个写死商品字段的数据库；
- 一个必须依赖向量库和查询模型的重型 RAG 服务；
- 一个把登录态和原始资料上传服务器的高风险平台。

本文档不规定函数、表结构、目录结构、消息协议和类设计。这些由工程师在可行性验证后形成详细设计和 ADR。

## 2. 已锁定的总体约束

| 约束 | 对总体方案的影响 |
| --- | --- |
| MVP 只做京东－冰箱 | 首先验证一条真实端到端链路，不同时开发淘宝 |
| 多个搜集板块汇入一个加工厂 | 来源变化与知识加工必须解耦 |
| 知识库面向任意 Agent | 通用层不得出现 Product、SKU 等固定业务假设 |
| 采集和加工只在本地运行 | 本地是唯一生产环境，服务器只承担轻量部分 |
| 原始数据可能非常混乱 | 加工厂必须包含规则、模型、校验和人工审核 |
| 查询应当轻量 | 重处理放在建包阶段，Runtime 默认不调用模型 |
| 不自研底层数据库和搜索引擎 | 优先组合成熟开源组件，项目只开发业务编排和适配层 |
| 用户技术栈为 Node/TypeScript | 首版优先选择有稳定 Node/TS 接入的组件 |

## 3. 总体结构

```text
本地 Workbench
  ├─ 项目与任务流水线
  ├─ 数据搜集板块
  │    └─ Source Provider
  ├─ 原始资料区
  ├─ 知识库加工厂
  │    ├─ 范围规划与 Schema 候选
  │    ├─ 抽取与标准化
  │    ├─ 对象合并与冲突处理
  │    ├─ 人工审核
  │    └─ 构建与评测
  └─ 本地知识包与 Runtime

可选线上部分（MVP 后）
  ├─ 项目和板块维护信息
  ├─ 知识包管理
  ├─ 轻量 Runtime
  └─ 权限、审计与备份
```

数据只沿一个方向进入正式知识：

```text
来源 → 原始资料 → 候选知识 → 审核知识 → 知识包 → Runtime
```

任何阶段都不能反向修改原始证据。新处理结果通过新版本表达。

## 4. 为什么必须分成三个核心层

### 4.1 数据搜集层

解决“到哪里找、怎样访问、怎样保存原始资料”。它必须理解京东页面和登录状态，但不负责决定什么是正确的冰箱知识。

### 4.2 知识库加工厂

解决“从混乱资料中得到 Agent 可用知识”。它理解当前领域的知识目标，但不应包含京东页面选择器或登录逻辑。

### 4.3 知识包与 Runtime

解决“怎样把加工结果交付给 Agent”。它不携带爬虫、模型任务或加工 Worker，只提供稳定、轻量的知识使用能力。

这一分层使同一个京东 Provider 可以服务不同主题，也使同一加工厂可以接收京东、淘宝或资料站等不同板块。

## 5. 任务流水线

产品层保留八个可见阶段：

1. 创建项目；
2. 规划并确认研究范围；
3. 配置数据搜集板块；
4. 搜集并保存原始资料；
5. 抽取、标准化和对象合并；
6. 人工审核；
7. 构建并评测知识包；
8. 发布和使用。

总体技术方案只要求每一阶段具备输入、结果、状态、错误和恢复点。内部是否继续拆成子任务、队列或状态机，由工程设计决定。

## 6. 开源组件基线

以下是 MVP 候选，不是 PRD 强制指定；工程师必须先做可行性验证，再冻结版本和使用方式。

### 6.1 采集候选

- Crawlee 作为采集任务、请求队列、会话和运行统计的候选基础。其 JavaScript 版本提供 PlaywrightCrawler、动态请求队列、Session Pool 和统计能力，符合“慢速、可恢复任务”的方向。[Crawlee 官方文档](https://crawlee.dev/js/api/3.13/playwright-crawler/class/PlaywrightCrawler)
- Playwright 作为需要浏览器渲染、规格切换和人工登录场景的候选。官方明确提醒认证状态可能包含敏感 Cookie 和 Header，因此登录资料必须留在本地并排除出版本库和上传链路。[Playwright 认证文档](https://playwright.dev/docs/auth)
- 对无需浏览器渲染的稳定页面，可由工程师评估更轻的 HTTP/HTML 解析路径，但不能牺牲证据和页面状态识别。

这些组件只能证明通用能力可用，不能证明京东页面一定可稳定采集。因此 MVP 第一阶段必须进行京东实页验证。

### 6.2 知识包存储候选

- DuckDB 适合作为结构化知识包候选，因为它是进程内数据库，支持文件持久化并提供 Node.js 客户端；工程实现应评估当前 Node Neo 客户端，而不是已弃用的旧 Node 包。[DuckDB Node Neo 文档](https://duckdb.org/docs/lts/clients/node_neo/overview)
- Orama 适合作为 TypeScript 侧全文检索候选。它支持全文、过滤和可选向量能力；本项目基线只使用全文能力，不因此引入 embedding。[Orama 官方文档](https://docs.orama.com/docs/orama-js)

产品锁定的是“可携带的结构化数据＋全文检索＋证据”，不是锁定某个文件名、表结构或索引格式。工程验证失败时可以替换组件，但不能破坏知识包产品能力。

### 6.3 AutoPKG 的定位

AutoPKG 官方仓库明确说明其公开代码是从内部实验代码抽取的最小可复现版本；当前实现依赖 LLM、FAISS、NetworkX、ODPS 和多 GPU 处理。[AutoPKG 官方仓库](https://github.com/Product-Understanding-Lazada-Alibaba/AutoPKG)

因此：

- 借鉴其产品属性发现、同义合并、关系抽取和动态更新思想；
- 在冰箱领域加工中参考其决策流程和评测方法；
- 不把该仓库当作本平台可直接运行的基础框架；
- 不把它的电商图谱结构扩散为通用知识包结构；
- 不继承其 GPU、ODPS、FAISS 或查询 embedding 依赖。

## 7. 模型在系统中的位置

模型只在本地建包流程中用于难以稳定编码的任务，例如：

- 从 Agent 目标生成研究范围草案；
- 发现候选属性、别名和表达映射；
- 解析非结构化文本或图片；
- 辅助对象合并、冲突解释和异常修复。

确定性解析优先；模型输出必须校验、保留来源并允许人工否决。运行时查询默认不用模型。

模型接入需允许更换 OpenAI-compatible、Qwen、豆包或本地模型。ChatGPT/Codex 订阅不等同于可供应用调用的 API 额度，MVP 预算应单独计算模型 API 或本地推理资源。

## 8. 本地与线上部署边界

### 8.1 永久留在本地

- 浏览器及认证状态；
- Provider 执行；
- 原始资料；
- 模型处理与人工审核；
- 知识包构建和评测。

### 8.2 后续可以部署

- 非敏感的项目、任务和板块维护信息；
- 知识包上传、下载、激活和回滚；
- 轻量 Runtime；
- 权限、审计和备份。

本地工作站离线后，线上只能继续查询已有知识包，不能生成新知识。

## 9. 总体质量要求

- 可恢复：进程退出、人工验证或单任务失败不导致整条流水线报废。
- 可追溯：正式知识可以回到来源、采集时间和处理版本。
- 可复现：同一原始资料和同一处理配置可以重新生成结果。
- 可替换：Provider、模型服务、存储和索引组件可以演进。
- 可携带：知识包不依赖生产工作目录和本地数据库服务。
- 可审计：规则、模型推断和人工决定可以区分。
- 轻量运行：未来 2 核 4G 服务器只加载已构建知识包并处理查询。

## 10. 决策层级

| 已锁定 | 候选方案，需验证 | 由工程详细设计决定 |
| --- | --- | --- |
| 本地生产、轻量运行 | Crawlee＋Playwright | Provider 函数接口 |
| 多板块汇入加工厂 | DuckDB Node Neo | 数据表与字段 |
| 通用知识包 | Orama 全文检索 | 文件目录与序列化格式 |
| 无强制向量/embedding | 规则＋可替换模型 | 队列、并发和重试算法 |
| 原始资料不可丢失 | AutoPKG 思想参考 | API、类和模块划分 |

## 11. 工程设计开始前的验证门

工程团队必须先提交三项小规模验证结果：

1. 京东真实页面的登录、搜索/发现、详情、多规格、图片资料和异常页面采集验证；
2. 使用少量原始资料完成规则＋模型＋人工审核的加工闭环；
3. 生成候选知识包，并在无模型、无网络条件下完成结构化查询、全文搜索和证据返回。

三项验证通过后，才能冻结详细接口、数据格式和正式技术栈。
